# TMP Protocol Quick Reference

Snapshot of currently-known values across the TMP ecosystem. Verify these are still accurate after firmware/app updates — the re-verify recipe at the end of this file tells you how to re-derive each one if it changes.

**Version baseline:** firmware 1.8.58 (the support floor); byte shapes captured from Pro Control v1.7.2.

## Preset format

- **XOR key**: `0x4A 0x4C 0x44` (ASCII `JLD`) — same operation encodes and decodes
- **Verify**: decoded result must be valid JSON starting with `{` and ending with `}`
- **If key changes**: re-derive the 3-byte XOR key by known-plaintext (the `{"` prefix) or Kasiski analysis (key length 3) + frequency analysis

## USB

- **VID**: `0x1ed8` (Fender)
- **PID**: `0x0044`
- **HID report size**: 64 bytes, vendor usage `0xFF00`

## Protocol Buffers

- **Top-level wrapper**: `FenderMessageTMS` with 13 category sub-messages
- **Key messages**: `ChangeParameter`, `LoadScene` (PresetMessage field 101, addresses the CURRENT preset only — encoder golden-tested in the companion's `proto.rs`), `SetNodeSceneEdit`, `SetPresetLevel`, `SaveCurrentPreset`, `CurrentPresetDataRequest` (field 2 → the field-3 working copy)
- **Scene addressing**: `LoadScene.sceneSlot` / `SceneLoaded.sceneSlot` / `lastLoadedScene` are **0-based `scenes[]` indices**; the BASE scene is the **CONSTANT wire slot 8** — even for a 0-scene preset, never `scene_count + 1`. The encoder **MUST emit `sceneSlot` explicitly even for 0** — the device ignores an empty `LoadScene{}`. `probe --loadscene 1` activates `scenes[1]`. Scene-0 leveling carries an OPEN anomaly (`.claude/rules/danger.md`).
- **Firmware version retrieval**: `currentFwRequest` (SettingsMessage field 1, `dummy=true`, no batchStatus) → `currentFwResponse` (SettingsMessage field 2) `data` (field 1) = e.g. `"1.8.58"`. It is answered at once; the app sends it in the burst BEFORE the batch-3 `CurrentPresetDataRequest`, because after it the reply queues behind the ~1.2 s handshake drain and a short window misses it (static RE + HW, fw 1.8.58).
- **Preset JSON retrieval**: the working copy arrives as `currentPresetDataChanged` (PresetMessage field 3, one LZ4 block): the reply to `currentPresetDataRequest` (field 2), the last item of the handshake drain, and a broadcast on every load, save or edit. The server never cuts it, and a transport cut fails LZ4 decode rather than leaving a JSON prefix. `currentPresetDataJsonRequest` (field 78) is answered with field 79 only when sent with batchStatus 0–3; the app does not send it. Field 136 = `AllBlockPresetsResponse` (block-preset library, not preset data). Scene names and the live scene index are in field 3 (`scenes[].sceneName`, root `lastLoadedScene`, base = 8), and `sceneListResponse` (125) pushes the names on every preset load. **The field-3 graph carries NO slot/list-index** — the active list-index arrives via `PresetLoaded` (11), which LAGS field 3 in a preset-switch burst, so a consumer treats the `PresetLoaded`-derived index (frontend `activeListIndex`) as the authoritative active slot, NOT the graph. Non-destructive live capture: `probe --dump-currentpresetdata <slot>` (loads the slot, dumps the decompressed JSON, reports scenes/ftsw completeness).
- **Slot-addressed preset read**: `presetDataRequest` (PresetMessage field **8**, `{listEnum, slot}` 1-based, no batchStatus) → `presetDataChanged` (field **9**, `presetJson` = field 3, **plaintext** not LZ4), read from the stored row. It arrives whole on a kept-alive session; a session lapse cuts the stream short of its `0x35` final. Keys are emitted byte-sorted at every level (`info` 8th of 15 top-level keys, `scenes` last), so a cut loses `scenes` first while `ftsw` survives (static RE + HW, fw 1.8.58) — and `session::tolerant_parse_json` repairs a cut SILENTLY (rewinds to the last top-level-complete comma, closes open containers, returns a value with no signal to the caller), so a present `scenes` key is never proof the section is complete. A session quiet for 750 ms has lapsed and needs a `connectionRequest` before the read; on a still-live session a `connectionRequest` draws `connectionError{1}`, so the monitor's live session reads without one (`read_slot_preset_json_live`, oracle `probe --slotread-live`). Harvest with the 0x35-is-final reassembly rule.
- **Scene mode**: `SetNodeSceneEdit { nodeId, groupId, sceneEditEnable: true }` (field 107) turns the node's overlay in the active scene into a full snapshot, so writes there stop reaching base; the device always broadcasts `nodeSceneEditSet` (108) back (static RE, fw 1.8.58). `nodeId` here is the live `ChangeParameter` coordinate and may differ from the stable Fender model id; classify amps by `FenderId` / companion `model_id`, then write the active block's `nodeId`. Enabling is NOT harmless on a node that already has a full overlay: it reseeds the overlay from base, wiping that scene's other edits on the node, so `set_knobs` enables only for a node with no overlay (`notes/leveling.md`). A value write that lands BEFORE Scene Edit is enabled hits base, which every un-flagged scene inherits — enable first, then write. The production sequence writes ~450 ms after `loadScene` (150 ms recall settle + 300 ms Scene Edit settle) and keeps OUT traffic flowing so the 750 ms session lapse never drops the write. The BASE scene's blocks have no Scene Edit flag. As a CLEANLINESS practice (not safety), only CHANGE a scene's value when it needs it — measure as-is first and skip scenes already on target.
- **Proto count**: 379 files (Pro Control v1.7.2, SDK v3.13.0)

## USB HID wire envelope

```
host → device   (IOHIDDeviceSetReport, 63-byte payload, no report-id prefix):
    0x35 0x00 <body_len> <protobuf FenderMessageTMS>       padded to 63 with 0x00

device → host   (IOHIDDevice input-report callback, 64 bytes incl. report-id 0):
    0x00 0x35 0x00 <len> <body>            single-frame small response
    0x00 0x33 0x00 0x3c <60 bytes>         stream start (multi-packet response)
    0x00 0x34 0x00 0x3c <60 bytes>         stream continuation chunk
```

- **Host magic**: 0x35 for small bodies — but the host **also chunks outbound**, symmetric with the device: a body > 60 B is sent as `0x33` (start) / `0x34` (continuation) / `0x35` (final) frames, each `MAGIC 0x00 <len> <≤60 B>`. Pro Control uses this for large requests like `importPresetRequest`. **Device magic**: 0x35 / 0x33 / 0x34 (single, stream-start, stream-cont).
- **Reassembler**: 0x33 begins a logical stream; concatenate 60-byte bodies of subsequent 0x34 chunks. **`0x35` is the FINAL frame of that stream — it carries payload (often small) and terminates it; a `0x34` never follows a `0x35` within a stream.** ⚠️ A reassembler that treats an inbound `0x35` as a _standalone_ single-frame (instead of appending it as the final frame) **drops the last frame → systematic tail truncation** of multi-packet list responses (last record's name cut, or whole trailing records dropped).
- **Reading multi-packet responses reliably**: parse **fail-closed** — reject any reassembled body with a truncated length-delimited protobuf field (declared length > bytes present), and only accept a response that parses _complete_ to the end; then **retry** the read. A tolerant parser silently clips a truncated field into a plausible-but-wrong record (e.g. a cut song name), so "largest prefix" is unsafe. Frames of two messages never interleave (static RE, fw 1.8.58): a short stream was cut by a session lapse.

### First-connect handshake (Pro Control 1.7.2)

ConnectionRequest → PresetListRequest(listEnum=1) → FavoriteListRequest → PresetListRequest(listEnum=4) → PresetListRequest(listEnum=3) → ProductProfileRequest → CurrentPresetInfoRequest → SettingsMessage(field 66) → UserIRMessage(field 2) → CurrentPresetDataRequest, then an OUT report at least every 750 ms (the app's monitor heartbeats every 250 ms).

**Connect cost (fw 1.8.58):** the batch-3 request drains every queued reply — ~567 frames, ≈1.2 s at 2.143 ms per frame, ending with the current preset's field 3 — and grows with the library's names and the current preset's body. For repeated commands, multiplex onto a live heartbeated session (see the push bullet below) instead of reconnecting per command.

### Wire-format gotchas

- **The HID is single-seize / exclusive-open — serialize ALL device access.** Only one client may hold the device. A second _concurrent_ `IOHIDDeviceOpen` (or acquire-before-release on reconnect) throws `kIOReturnExclusiveAccess` (`0xe00002c5`); `kIOReturnNotPrivileged` is `0xe00002e2`. Any driver must funnel every read/write through one seized handle, **release-before-acquire** on reconnect, and **never fire two device commands concurrently** (e.g. a `Promise.all` of two reads, or two parallel connections each via its own seize). This is the OS-level seize invariant, distinct from the message-level `batchStatus` queue. **There is no post-close lockout**: a re-open right after a close succeeds; `0xe00002c5` means another handle holds the seize — Pro Control, or an overlapping `Session` in this process (`.claude/rules/danger.md`, the `0xe00002c5` entry).
- **`ConnectionHeartbeat` carries no `batchStatus`.** Bytes are exactly `35 00 06 22 04 22 02 08 01`.
- **A heartbeat on a live session draws NO reply.** An empty `ConnectionError` (`22 02 1a 00`, `errorEnum=0`) means the session is CLOSED: it lapsed after 750 ms with no OUT report, the message that drew it was dropped, and only a new `connectionRequest` reopens it (static RE + HW, fw 1.8.58).

#### Control-plane writes

- **Fire-and-forget setters/commands are sent without `batchStatus`** — `SetReAmpMode`, `SetPresetLevel`, `LoadPreset`, `SaveCurrentPreset`, `ChangeParameter`. With one they follow the queue rule above: 1/2 wait for a later batch 3, ≥4 is dropped with no error.
- **Re-amp toggle** = `SettingsMessage(3) → reampModeActive(30)`. ON = `1a 05 f2 01 02 08 01`, OFF = `1a 03 f2 01 00`. The `ReAmpModeChanged` echo is not proof of engagement — a finite captured USB-Out loudness is, and Mixer `reAmpModeRequest(4)` → field 9 reads the real state. ⚠️ **Stranded re-amp = the TMP produces NO SOUND** from the guitar input; always send a guaranteed OFF on a fresh connection at the end of any re-amp run (`.claude/rules/danger.md`).
- **Re-amp capture**: set `presetLevel` before engaging for preset leveling; set only the active amp's exact-case `outputLevel` for scene leveling, with Scene Edit on the active amp and one engage per scene (`.claude/rules/danger.md`, "One engage per capture" and "Latch nuances"). Never use preamp/master/volume params (`brightvolume`, `mastervolume`, `normalvolume`, `volume`) for scene leveling because they alter tone; every amp schema has `outputLevel`, `output` is not an amp control, and `level` is not the output leveling control (`ACD_TMRumbleV3` has `level` as a separate amp knob plus `outputLevel`, and `level` must not be changed). `presetLevel` is only the global fallback: if the active amp's `outputLevel` cannot hit target, raise `presetLevel` and restart scene leveling from scene 0; see `notes/leveling.md`.
- **`LoadPreset` then `SetPresetLevel` on one connection**: on fw 1.8.58 the set sticks; the code still loads on its own connection, then sets on a fresh no-load one. The loaded preset stays "current" across USB reconnects.
- **`LoadPreset` then `LoadScene`**: the device runs a load to completion before the next message (static RE, fw 1.8.58); the code keeps the load and the scene recall on separate connections, conservatively.
- **`SetPresetLevel.presetLevel` is a linear amplitude control**: captured loudness ≈ `20·log10(presetLevel) + C` (verified ≤0.04 LU), so preset-to-preset leveling to a target LUFS is one-shot, not iterative. **The active amp's `outputLevel` is ALSO linear/one-shot (HW): ~25 LU authority, `20·log10(outputLevel) + C` — so per-scene leveling is a ONE-SHOT solve too (measure once → solve `C` → set). `presetLevel` is a GLOBAL multiplier over all scenes → level Base first; per-scene amp values isolate via Scene Edit (`SetNodeSceneEdit`).** The reachable maximum is per preset: `notes/leveling.md`.
- **Measure each point on its own fresh re-amp capture** (fresh stream pair; `measure_knob_at` shape) — a shared continuous stream read with sliding windows mis-measures scenes. The capture WINDOW is load-bearing too: the full 6 s stimulus + 0.8 s tail. Presets aren't stationary (delay/reverb buildup + decay tail the gated integrated includes), so any early-exit/tail-drop/preroll-skip is a ≤0.3 LU re-baseline, not a free speedup (HW-A/B'd; clean +0.30 / delay +0.16 / reverb −0.02 LU). Validate against the full-capture oracle, not a same-method round-trip. See `.claude/rules/leveling-dsp.md`.
- **`LoadPreset` uses field 6 = `presetSlot`**, not field 1. Field 1 is `tabEnum` (0=NotSet, 1=UserPresets, 2=FavoritePresets, 3=CloudPresets, 4=FactoryPresets, 5=Songs, 6=Setlists). The **1-based** `presetSlot = list index + 1` rule also holds for the **Factory bank** (`tabEnum=4`, HW). The `presetListRequest{listEnum=4}` factory list is enumerable and the handshake already requests it.
- **`PresetListResponse.record[]`** is a `repeated PresetListRecord { string displayName }` — slot is the array index (0-based); no preset ID is sent on the wire. The empty-slot marker is `--` (also "Empty"). Every slot-addressed setter — and `songPresetListResponse.userPresetSlot` — is **1-based**: device `userSlot = list index + 1` (`.claude/rules/danger.md`).
- **Preset CRUD setters** (byte-exact from a Pro Control capture; all single-packet, no `batchStatus`): `renameCurrentPreset` (PresetMessage **13**) `{displayName=f1}`; `moveUserPreset` (**16**) `{oldSlot=f1, newSlot=f2}` (persists alone); `clearUserPreset` (**15**) `{userSlot=f1}` = **device** slot. **A Pro Control "rename" is `rename(13)` + `saveCurrentPreset(14){slot=f1}` ~10 ms later** — rename(13) alone is not persisted; send both.
- **`importPresetRequest`** (PresetMessage **117**) `{presetJson=f1}`: writes a full preset back. **`presetJson` = LZ4-block(raw `.preset` file bytes)** = `LZ4(XOR_JLD(compact JSON))` — NOT plaintext, NOT XOR-only. No `batchStatus`; sent post-handshake as a chunked `0x33/0x34*/0x35` stream. An all-literal LZ4 block is a valid trivial encoder (no compressor dep). **It lands in the lowest empty user slot** — it cannot target or overwrite a slot, and with no empty slot it gets `presetError` 26. The device reloads only when the import lands on the currently loaded slot, and its `importPresetResponse` (118) echo is unreliable (static RE + HW, fw 1.8.58). In-place edit recipe (`replace_inplace`) = import-to-scratch → `loadPreset(scratch)` → prove the loaded blocks (`replace_inplace::load_and_prove`) → `saveCurrentPreset(origSlot)` → `clearUserPreset(scratch)`. The Song link survives when the slot and the bound scene index survive (next bullets).
- **The engine normalizes the `info` block on EVERY `saveCurrentPreset`** (static RE, fw 1.8.58): on-device `presetJson` is PLAINTEXT JSON in the SQLite BLOB, and the firmware re-serializes `info` to EXACTLY `{author, created_at, displayName, preset_id, product_id, source_id, timestamp, version}`, minting a fresh `preset_id` on every save (same slot included). Extra keys injected into `info` (`comments`/`artist_name`/`byline`/`song_name`, recognized only by the Qt client — or arbitrary unknown keys) SURVIVE import/restore (the blob is stored verbatim) but are DROPPED by the next save. So presetJson is not a durable channel for host metadata, and `preset_id` is no stable key: import and restore keep any id, so ids can repeat — key a sidecar by slot and use the id only as a per-slot "did this body change" check.
- **`exportPresetRequest`** (PresetMessage **115**) `{listEnum=f1, presetSlot=f2}` → `exportPresetResponse` (116) to the sender: the full preset, encrypted then LZ4-compressed — complete but opaque without the device key. For readable content use a kept-alive field-8 read or the backup archive. **`requestNextEmptyPresetSlot`** (81) always broadcasts `nextEmptyPresetSlotResponse` (82), from the same lowest-empty finder the import uses (static RE, fw 1.8.58).
- **Song-preset binding** (`assignSongPreset` / `songPresetListResponse` records, SongMessage field **11**): a Song row binds a preset by `userPresetSlot` (1-based device slot) + `presetSceneSlot` (0-based scene index, **8 = the whole preset**) — NOT by `info.preset_id`. `assignSongPreset` with a scene index the preset doesn't have (≥ its scene count, other than 8) is refused with `SongError{5}` and writes no row (static RE + HW, fw 1.8.58) — read the row back. The Song read is `songPresetListRequest` 12 → response 13, sent mid-session with batch 3 or none. Overwriting a slot with a preset that lacks the bound scene **breaks the Song link** — slot-preservation ≠ link-preservation.
- **Song + setlist CRUD over USB** (byte-exact from the device, HW). Songs = `SongMessage` (TMS field **11**): `addSong[4]{songName=1}`, `renameSong[7]{songSlot=1,songName=2}`, `removeSong[6]{songSlot=1}`, `songNotes[22]{songSlot=1,songNotes=2}`, `setSongBpmActive[23]{songSlot=1,active=2}`; list read `songListRequest[2]`→`songListResponse[3]`, record `{songName=1,songNotes=2,songBpmActive=3,songBpm=4}` (songName capped 24 chars, accents folded to ASCII). Setlists = `SetlistMessage` (TMS field **12**): `addSetlist[4]{setlistName=1}`, `renameSetlist[7]{setlistSlot=1,setlistName=2}`, `removeSetlist[6]{setlistSlot=1}`, `addSetlistSong[14]{setlistSlot=1,songSlot=2}`; list read `setlistListRequest[2]`→`setlistListResponse[3]` (record `{setlistName=1}`), membership `setlistSongListRequest[12]{setlistSlot=1}`→`setlistSongListResponse[13]` (records `{songSlot=1}`). Setlist-membership edit: `removeSetlistSong[16]{setlistSlot=1,setlistSongSlot=2}` and `moveSetlistSong[15]{setlistSlot=1,oldSetlistSongSlot=2,newSetlistSongSlot=3}` address the song by its **1-based POSITION within the setlist** (`setlistSongSlot`, NOT the global `songSlot` that `addSetlistSong` takes); `moveSetlistSong` is array-splice (remove at old, insert at new): `[1,3,6]` remove pos 2 → `[1,6]`; `[1,6,11]` move 3→1 → `[11,1,6]`. All writes are fire-and-forget setters (NO `batchStatus`); list reads use batch 3 or none on an open session. Write slots are POSITIONAL (read-list 1-based index); a new song lands at protocol list slot 1 (shifting every other song +1) but shows 2nd-to-last on the device screen — resolve a just-created song BY NAME.
- **Per-song BPM has NO dedicated setter** — it's the GLOBAL tap-tempo applied to the ACTIVE song: `SettingsMessage[3].tapTempoBpm[12]{value(1)=float, originatorId(2)=1}` (byte-exact `1a09 6207 0d<f32le> 1001`). To set song X's BPM: (1) X needs ≥1 footswitch (`assignSongPreset`), (2) activate X via `presetMessage[2].loadPreset[10]{tabEnum=5, songSlot=4, songPresetSlot=5, presetSlot=6}` (`tabEnum` 5=Songs, 6=Setlists; `LoadPreset` also has `setlistSlot=2`, `setlistSongSlot=3`), (3) `setSongBpmActive(true)`, (4) send `tapTempoBpm`, then read back once — all on ONE connection, no retry and no wait. `tapTempoBpm` writes the active song's BPM **only if that song's `bpmActive` is already on**, and `setSongBpmActive(true)` re-applies the song's STORED BPM (120 for a new song), never a tempo tapped before it — so tap-then-enable never lands on a flag-off song (static RE + HW, fw 1.8.58: 0/5 vs enable-then-tap 5/5).
- **`CurrentPresetDataChanged.presetJson`** (bytes field 1) is **LZ4-block compressed** JSON (not the LZ4 frame format — no `04 22 4d 18` magic, length comes from the protobuf wrapper); its first byte `0xE8` is the first LZ4 token (`LL=14, ML=8` — the 14 literal bytes are the `{"ampControl":` that starts every preset). `AllBlockPresetsResponse.field1` (PresetMessage.field136) is also LZ4-compressed. `ProductProfileResponse.field1` (PresetMessage.field42), in contrast, is plain pretty-printed UTF-8 JSON starting `{\n\t"effectCategories":`. Decoder: a pure-Python LZ4-block decode (~30 lines). Try LZ4 first, fall back to a literal block.
- **The decoded `presetJson`** contains `audioGraph.guitarNodes.G1[]` — an ordered list of effect blocks with `FenderId`, `dspUnitParameters`, `nodeId`, `nodeType`. This is the ordered signal chain the companion renders and edits (the Copy feature's `copyModel.ts` → `copy_apply` → `audiograph.rs` path).
- **Pushes are broadcasts to every OPEN session.** The device pushes `PresetLoaded`(11), `SceneLoaded`(102), `CurrentPresetInfoChanged`(22), `sceneListResponse`(125) and the field-3 preset JSON on every change, with no subscription message; a session closes after 750 ms with no OUT report and misses every broadcast until it reconnects. Any heartbeat cadence well under 750 ms keeps receiving them — the monitor's 250 ms is margin (static RE + HW, fw 1.8.58). A live heartbeated session also EXECUTES fire-and-forget commands inline (`LoadPreset`/`LoadScene` via the monitor's command lane): `loadScene` changes the amp within ~300 ms and `setPresetLevel` steps the audio within 100 ms (HW, fw 1.8.58).

## Test & Loopback messages

TMS-native diagnostic / factory surface, all under `TestMessage` (the top-level oneof category, `TestMessage.proto`). 51 sub-types in total; the four most general-purpose are below. The rest cover XMOS programming, SD card test, rear-panel pad / phantom / instrument-select / impedance switching, CPU temperature, brightness, MIDI output — see `TestMessage.proto:55-108` for the full catalog.

| Message                 | Request fields    | Response                                         | Use case                                                         |
| ----------------------- | ----------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| `LoopbackTest`          | `string data = 1` | server echoes the same `LoopbackTest` back       | generic HID round-trip parity / latency check                    |
| `MidiLoopbackRequest`   | `bool dummy = 1`  | `MidiLoopbackResponse { uint32 statusEnum = 1 }` | MIDI loopback hardware test (rear-panel MIDI in→out)             |
| `SystemInfoRequest`     | (no fields)       | `SystemInfoResponse`                             | firmware/hardware version reporting                              |
| `CpuTemperatureRequest` | (no fields)       | `CpuTemperatureResponse`                         | thermal telemetry — pair with high-load presets for parity tests |

All are `TestMessage`-routed (top-level oneof field 1); the request carries no `batchStatus` echo requirement. None have a Mustang-LT-style `QASlots*` equivalent — TMS rolls factory tests under `TestMessage.testControl` / `testOutput` / `setTestAppMode` (`TestMessage.proto:59,58,100`) instead of an LT-style QA slot model.

See `references/protocol-lineage.md` for how the test surface compares to LT's `LoopbackTest` + `QASlots*` family.

## How to verify after an update

```bash
# Pro Control version
defaults read "/Applications/Pro Control.app/Contents/Info.plist" CFBundleShortVersionString

# Re-verify the wire codec against the device's golden vectors
cd src-tauri && cargo test --lib proto

# Decode a known preset to check the XOR key
python3 .claude/skills/tmp-companion-protocol/scripts/preset_toolkit.py decode known.preset --pretty
```

If the decode output isn't JSON, re-derive the key by known-plaintext (the `{"` prefix) or Kasiski analysis (key length 3) — see **Preset format** above.
