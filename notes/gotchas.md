# Gotchas — the HW evidence behind the rules

The evidence appendix for the repo's always-loaded rules. This file carries each rule's full
statement, the hardware evidence behind it, and the failure it prevents.

Where a rule is stated in more than one place, the split is deliberate:

- **`.claude/rules/danger.md`** — the danger rules in full (data loss, device wedging, machine
  crashes). Always loaded, re-injected after compaction.
- **`CLAUDE.md`** — the traps that fire while _running_ a command rather than editing a file,
  plus a one-line index of the rules below.
- **the OTHER `.claude/rules/*.md`** (every one except `danger.md` above) — path-scoped
  conventions that load only when you edit a file the rule's `paths:` glob matches.
- **This file** — the long form. Where both state a rule, this one is the fuller text; they do
  not contradict.

Read the entry in full before changing the behaviour it governs.

## Linux hidraw transport: inbound reports carry their own leading `0x00`, and there is no open lockout

- **The leading `0x00` on inbound frames is the DEVICE's byte, not a report-ID artifact of the reading API.** Inbound frames parse as `[0x00, magic, _, body_len, …]` while outbound frames put the magic at index 0 (`proto::make_envelope`), and that asymmetry invites the conclusion that the macOS reader prepends a report-ID byte — which would mean every other HID backend must re-add or strip one. **It does not.** Measured on a real unit over a full preset-list harvest (**fw 1.8.58** — newer than the fw 1.8.45 the rest of this file's entries were measured on, so treat these three Linux bullets as 1.8.58 observations): **668/668 reports arrived as `n=64` beginning with a literal `0x00`** (`00 35 …`, `00 33 …`, `00 34 …`), and **zero** in the bare `[magic, …]` shape. So `hid.rs`'s Linux `imp` pushes reports **RAW**, exactly as the macOS input callback does, and `proto.rs` plus its golden vectors stay byte-identical across platforms. A normalization layer was written for this on the (wrong) assumption above and then **deleted once the hardware disagreed** — do not reintroduce one; `hid.rs`'s `a_real_inbound_report_needs_no_report_id_fixup` test pins the measured shape. No filtering is needed at the transport either: `proto::reassemble_streams` already skips anything failing `len >= 4 && data[0] == 0x00`.

- **The macOS `0xe00002c5` open-lockout model does NOT apply.** `kIOHIDOptionsTypeSeizeDevice`, the 8 s quiet backoff, and "every failed open resets the lockout" all describe IOKit _exclusive_-open behaviour. On Linux there is no seize (and none is needed — Fender ships no Pro Control for Linux, so nothing competes for the unit), and back-to-back `probe` sessions reconnected immediately with no backoff. The Linux `imp` therefore has **no open-retry loop at all**; adding one would only make a genuine error slow to surface. Re-measure before importing any macOS timing constant here.

- **But exclusivity itself still has to be enforced, or it silently disappears.** The seize does two jobs on macOS: it locks Pro Control out AND it guarantees only one opener. hidraw provides neither — **verified: two `probe` processes launched together both opened the node and both proceeded**, where the second would have failed `0xe00002c5` on macOS. Everything downstream assumes that cannot happen (the write-safety rules above most of all — interleaved writes from two openers are exactly how a slot gets a wrong-content save). The Linux `imp` therefore takes an advisory `flock(fd, LOCK_EX | LOCK_NB)` immediately after `open`, and reports `EWOULDBLOCK` as "already in use by another TMP Companion process". Advisory is sufficient because every path into the device goes through that one function and nothing else on Linux speaks this protocol; the lock releases on close, including on abnormal exit. Re-verified after the fix: of two simultaneous `probe` runs, one read all 504 presets and the other failed with the friendly message. **Do not remove this believing hidraw is exclusive — it is not.**

- **`/dev/hidraw*` is root-only, so first run fails `EACCES` until a udev rule lands.** `packaging/udev/70-fender-tone-master-pro.rules` tags the node `uaccess`, which grants the logged-in user via a POSIX **ACL** (`getfacl` shows `user:<name>:rw-`) rather than a group — verify with `getfacl`, not `ls -l`, since the mode bits still read `crw-------`. `udevadm trigger` re-applies it to an already-connected unit, so **no replug is needed**. The unit enumerates **two** interfaces, `1ed8:0044` and `1ed8:0047`; only `0044` carries this protocol (`hid::PID`), and the rule tags both so the whole device is consistently owned. The device node is found by walking `/sys/class/hidraw/*/device/uevent` for `HID_ID=<bus>:<vid>:<pid>` (zero-padded uppercase hex) — no `udev` crate, no C `hidapi`, hence zero new dependencies.

## Linux ALSA re-amp audio: the TMP's `hw:` interface is I32-only, on the OPPOSITE USB product id from HID, and PipeWire will fight you for it

- **The TMP's audio interface is USB id `1ed8:0047` — NOT `0044`, which is HID's id.** The two interfaces split control and audio, but on the OPPOSITE product id from what the HID split might suggest: `/proc/asound/cardN/usbid` shows `0044` as a MIDI-only card (no PCM device — this is where the HID control protocol actually rides, separately from ALSA entirely) and `0047` as the real 4-in/4-out USB-audio-class card. **Do not assume the audio interface shares HID's product id** — `audio.rs`'s Linux `find_device` resolves by walking `/proc/asound` for the Fender-vendor (`0x1ed8`) card that has a `pcm*` entry, not by a specific product id.

- **`hw:CARD=<id>,DEV=0` is `S32_LE` (I32) ONLY — no F32 at all, at any channel count.** Measured (fw 1.8.58, `aplay --dump-hw-params` and cpal's own `SupportedStreamConfigRange` agree exactly): `FORMAT: S32_LE`, `CHANNELS: 4`, `RATE: [44100 96000]`. `audio.rs`'s `pick_config` (written against CoreAudio, which is always F32) now accepts I32 as a fallback, converting to/from f32 at the stream-callback boundary using `dasp_sample`'s exact `2^31` scaling (`f32_to_i32`/`i32_to_f32`) — a different scale factor (e.g. `i32::MAX`) would silently mis-calibrate every LUFS reading captured over this path.

- **`plughw:` is NOT a safe substitute for `hw:`, despite offering F32.** `plughw:CARD=<id>,DEV=0` reports channels `1..64` (ALSA's `plug` layer converts channel COUNT as well as format), so `pick_config`'s "smallest channel count that fits ≥3" would ask `plughw` for exactly 3 channels — not the physical 4 — and get them via `plug`'s own, unverified channel remix, not the 1:1 mapping `REAMP_INSTRUMENT_OUT_CH` depends on for precise USB-In-3 routing. `hw:` only ever advertises the physical channel count, so it cannot make this mistake. Chosen over `plughw:` specifically for this reason, not measured to be broken — the risk was assessed as unacceptable to leave unverified given how leveling-critical exact channel routing is.

- **cpal's Linux device enumeration is genuinely ambiguous by name, and the OLD `find_tmp`/`find_device` name-substring match picks the WRONG device.** `probe --audio-devices` (before this port) showed `find_tmp()` selecting `"Tone Master Pro"` (an ALSA `usbstream:CARD=Pro` **hint** device, 0 channels, not audio-capable at all) over `"Tone Master Pro, USB Audio"` (the real `hw:`/`plughw:` PCM) — the non-functional hint's name is byte-identical to the real device's short name and sorts first in cpal's enumeration order. `find_device`'s Linux `imp` resolves by exact ALSA pcm_id (`description().driver()`, e.g. `hw:CARD=Pro_1,DEV=0`) matched against the vendor-id-resolved card, sidestepping the name ambiguity entirely.

- **A separate bug, unrelated to Linux: `audio::enumerate()`'s original device map was keyed by NAME ALONE.** On Linux, several distinct ALSA PCMs legitimately share one display name (`hw:`, `dmix:`, `surroundNN:`, a `sysdefault:` hint…), so merging by name alone unioned their channel/rate/format ranges into a chimera describing none of them — the real `hw:CARD=Pro_1,DEV=0`'s S32_LE/4ch/[44100,96000] got merged with an unrelated hint into a bogus 64ch/F32/[4000,4294967295] entry. Fixed by keying on `(name, driver)` instead — `driver` is the exact ALSA pcm_id, so it disambiguates while still merging a device's own separate input/output enumeration views (same pcm_id in both).

- **PipeWire/WirePlumber claims USB-audio devices as system sinks/sources by default, and that blocks `hw:`'s exclusive open with `EBUSY`.** Confirmed via `fuser /dev/snd/*`: `wireplumber` held `pcmC4D0p` (the TMP's playback device) even with no other app actively streaming through it — PipeWire's ALSA plugin opens a claimed card's node persistently, not just while in active use. Re-amp measurement worked immediately after the card was claimed-and-released once, then failed `EBUSY` on the next run once WirePlumber re-claimed it. The fix is a WirePlumber rule (`~/.config/wireplumber/wireplumber.conf.d/`) matching `device.vendor.id = "0x1ed8"` + `device.product.id = "0x0047"` with `update-props = { device.disabled = true }` — see `CONTRIBUTING.md`'s "Developing on Linux". This is a machine-level config change outside the app's own control, and `audio.rs` still cannot work AROUND a live hold — but it does now RECOGNISE one: `stream_error` appends the WirePlumber rule to the busy stream-build failure, so the error names its own fix instead of stopping at ALSA's bare `Device or resource busy`. Same shape as `hid.rs` turning `EACCES` into the `udevadm` commands.

- **HW-validated end to end (fw 1.8.58, real unit) once the above were fixed:** `probe --measure-current` produced a stable, repeatable LUFS reading (identical across two runs) through a real preset's DSP chain; `probe --levelpreset` ran the full measure → solve → apply loop and correctly restored the pre-measurement preset state; `probe --doctor` produced a real, non-degenerate spectral profile (distinct band powers, sensible diagnoses) — not noise or silence. The `danger.md` re-amp rules (fresh connections, one engage per connection, guaranteed re-amp OFF) held with no new anomaly on Linux across these runs.

## A batched scene-leveling save can revert the ONE scene it just leveled, if that scene is also `restore_scene` — a pre-existing, platform-agnostic bug, not a Linux-audio defect

- **Found while HW-validating Level on Linux, but reproduces identically regardless of platform — it is pure device-protocol logic, no audio involved.** `level_scenes_oneshot`'s final save (`save_deferred_scene_writes` → `recall_reassert_save` → `recall_original_scene`) recalls `restore_scene` (the preset's scene at prepass time — the scene the batch should leave the device sitting on) immediately before `saveCurrentPreset`. `recall_original_scene`'s own doc cites HW proof that **"unsaved writes survive the recall"** (`probe --defer-scenes`) — but that proof is for scenes OTHER than the one being recalled. Recalling the SAME scene the batch itself just wrote is a narrower, untested case: `loadScene(N)` re-instantiates scene N's STORED overlay onto the graph, which overwrites N's own live, unsaved edit — that scene's write never had a chance to be included in the save that follows it.

- **HW-reproduced twice, byte-identical (fw 1.8.58, `probe --level-scenes 404 -17 guitar-humbucker 0 --commit` on the "E2E Hiwatt 3S" scenario preset, list index 404):** both runs solve scene 0's `outputLevel` to `1.0000` (achieving −17.25 LUFS, well inside any real tolerance — the SOLVE is correct), but the saved document holds `0.9600` — the value scene 0 already had. **`--loadscene 2` immediately before the run has NO effect** (identical failure) — `prepass_scene_docs`'s own fresh `load_preset` re-lands on preset 404's STORED `lastLoadedScene`, which is `0`, regardless of the device's state going in. So for this preset, `restore_scene` is deterministically `0` on every run, and levelling scene 0 specifically collides with it every time — this is not session-history-dependent flakiness, it is 100% reproducible for this exact (preset, scene) pair, and would be for any preset whose stored on-load scene is the one a batch levels.

- **`level-strict.spec.ts` (the online "strict output harness", since absorbed into `level.online.spec.ts` — re-measures every leveled sound from the SAVED state) surfaced this as scene 0 re-measuring 0.60 LU off a −17 target against a 0.5 LU gate, HW-reproduced twice with near-identical numbers (−17.60 LUFS, Δ0.6034 then Δ0.6019).** That test's own header notes it has been "deferred; device offline" since the metering re-baseline PR — this may be the first real-hardware run of it since, which is why nothing caught this earlier; it is not new to this Linux work.

- **Not a silent-corruption bug: the codebase's own `persist_mismatches`/`verify_persisted_writes` (leveller.rs) already detects exactly this class of miss** (a chunked-edit drop or lapse) and stamps `persist_mismatch` on the outcome — the existing safety net worked as designed and reported it; nothing here corrupted data undetected.

- **Not fixed here.** `recall_reassert_save` already has a precedent for this shape of problem — `reassert_pl` re-applies `presetLevel` after the recall reverts it — but nothing analogous re-applies a per-scene block write when `restore_scene` collides with a scene the batch itself wrote. `recall_original_scene` is shared by THREE save paths (`apply_levels`, `save_deferred_scene_writes`, `write_fs_values_on_session`), so a fix needs to reason about all three, not just the scene-batch one this was found in — out of scope to patch blind without a regression fixture and macOS re-validation, per this repo's own "every bug becomes a gate" bar.

## LIVE per-node structural edits (the protocol behind the block-edit features)

- These wire facts are driven by **TWO** commands: `bulk_replace_live` (one replace across a selection) and **`copy_apply`** (the Copy tab — an ordered replace/insert/remove op list PER target preset, from `copyModel.diffToOps`; reuses `session::{replace_node,insert_node,remove_node}` + the held-session machinery, same `nodeReplaced(40)`/`nodeRemoved(36)`/`nodeInserted(33)` confirm gate, never-save-on-`presetError`(53), first-edit-after-load retry-harden). Replace any block across selected presets with a stock model (`replaceNode` 39), a user saved block / dual cab (`replaceNodeWithBlock` 100, +library index), or a user IR (`replaceNode`→`ACD_UserIRTMS` + a string `changeParameter` on the node's `file` param), or REMOVE it (`removeNode` 35), or ADD a block (`insertNode` 34 — sent BARE, NO `nodeJsonRequest` preamble, `groupId` is the group KEY; HW-confirmed + UI-wired via Copy; field-2 = the SAME-group FenderId to insert BEFORE the named node (omit = append; a cross-group anchor is silently dropped), entry points `probe --insert-active`/`--insert-map`) — on ONE held session re-armed per preset; confirm on `nodeReplaced`(40)/`nodeRemoved`(36)/`nodeInserted`(33), **never save on `presetError`(53) or an unconfirmed edit** (a wrong-content save corrupted a real slot), stoppable via `cancel_bulk_replace`. Firmware-aware palette (stock models filtered to `since` ≤ connected fw; user IRs + saved blocks are read live so they're inherently fw-correct). **Two INVARIANTS for ANY block-mutation code (`audiograph.rs`):** (1) **A block lives in THREE differently-keyed places — touch ALL or leave dangling state:** `audioGraph.{guitarNodes,micNodes}` (the roster, by FenderId), `scenes[].<group>.<FenderId>` (per-scene overrides, by FenderId), `ftsw[i][].nodes[].nodeId` (footswitch assignments, by EXACT nodeId). Miss the scene path → stale inert overrides; miss ftsw → a footswitch ghost-toggles a block that's gone. `drop_scene_overrides`/`retarget_ftsw` handle 2+3 for `remove_block`/`replace_block` — `create_variant` drops the old block's per-scene overrides via the same shared helper. (2) **The backend matches by EXACT FenderId** — the CabIR/Convolution suffix-normalization (`resolveDeviceId`, see the amp-id-matching gotcha below) is FRONTEND-ONLY, so a frontend-normalized id passed into an OpSpec silently fail-matches (no error, no replacement). **Offline-impossible:** saved blocks are metadata-only (`blockPresetsMap` = 5 keys, no params; `product_profile.json` carries zero default params), so a faithful saved-block/IR insert is LIVE-ONLY — there is no offline payload to reconstruct (don't re-attempt an offline splice). **Form-blind catalog trap:** the same amp `block_id` is catalogued as BOTH a combo and a head (identical `block_name`) — art keyed by `block_id` alone can't tell them apart, and dedup-by-`block_id` silently DROPPED ~45 head amps from the replacer (Amp Heads 48→3). Fixed by threading a `form` prop (combo/head/half_stack) through `BlockArt` (`AMP_FORM_ICON`) + appending "(Combo)/(Head)" to dual-form names (`catalog.ts` `displayName`). **Saved-block palette speed (unrealized fix):** `read_backup_archive` extracts only `normalDb.db3` and DISCARDS the backup's `settings.json`, which already holds `blockPresetsMap` as plaintext — so saved blocks are re-read LIVE at palette open even though the ~22 s startup backup fetched that exact data; parsing it out of `settings.json` is the deeper fix (the current path cache-prefetches the live reads on the quiet post-backup line instead).
- **The Copy post-save read-back is a buffer scrape, not a read — validate it against the acked ops before trusting it.** `copy_apply_one` reads `current_preset_value()` after the save, i.e. the LONGEST `presetJson` carrier that landed in the held session since the last op's `clear_raw()` (that op's confirm pumps + the 120 ms post-save pump); nothing requests a fresh field-3 after the save. HW 2026-09-02 (fw 1.8.45, ONLINE `copy.spec.ts`, twice in a row): that document was the LOAD-TIME graph, `CopyView` preferred it over the edit it had just applied, and the re-opened editor listed target 401's original 8 blocks with the deleted `ACD_UniVibe` back. Nine green online runs 2026-08-30 → 09-01 preceded it, and it passed once more after an older device backup was restored — a timing race, not a deterministic fault. Offline never saw it: the sim pushes nothing after a save, so the read-back was always absent and the optimistic patch always won. Now `read_back_graph` adopts the read-back only when its per-group FenderId roster equals `expected_roster(pre-edit roster, acked ops)`, `CopyView` is optimistic-first (`reconcileReadBack`), and the verdict line `[copy_apply] slot N: post-save read-back …` names every carrier present (`Session::json_payload_carriers`: 3 = live push, 9 = the stored slot's field-8 reply, 79 = json response). WHICH carrier delivers the stale document on the unit is still unproven — a late field-3 push or a field-9 reply inside the lazy-commit window are the candidates; grep the online server log for that line to settle it (the first instrumented online run, 2026-09-03, logged `carriers []` for both saved slots — the buffer held nothing after the save, so the stale case is a rarer race than every-run). Two limits of the roster oracle: an edit the roster cannot see — a same-model re-stamp, since on the unit a node id IS its FenderId — is UNVERIFIABLE (pre- and post-edit documents are identical by roster), so `copy_apply` omits the graph — the backend alone decides adoptability, the frontend only checks the read-back it is handed; and the read-back goes through `current_audio_graph` (not a bare `extract_active_graph`) so a buffer-scraped document truncated before a complete `template` is refused rather than adopted with a default series shape.
  - **A NONEXISTENT SAME-group `insert_after` anchor is REJECTED with `presetError(53)`** — contrast with the cross-group anchor above (silently dropped, no error). HW evidence, production probe runs: 2026-07-25 12:55 `--insert-active ACD_UA1176 --slot 31` with no `--after` accepted (`reply_fields=[22, 33, 108]`, persisted); 2026-08-17 10:49/10:50 same model with `--after ACD_BE100` rejected (`reply_fields=[53]`, no readback — the 10:50 target preset had no such node). No code-level gate exercises anchor-causes-53 yet: `SimDevice::with_reject_at` tests prove only never-save-on-53, not this trigger.

## Requests must REUSE `batchStatus` in Pro Control's groups, not increment per request

- The handshake grouping is `preset_list(1)=1`, then favorite/preset_list(4)/preset_list(3)/product_profile/current_preset_info/settings66/userir all=`2`, `current_preset_data_request=3`, `current_preset_data_json_request=4`. If you increment the batch on every request, the device answers only the first couple (the preset lists) then **goes silent** — so leveling's `list_my_presets` works but nothing else (product profile, current-preset data, preset JSON) ever arrives. Mirror the device's exact values. (HW-confirmed.)
  - **Preset JSON / block enumeration:** the preset JSON arrives as `currentPresetDataChanged` (PresetMessage field 3, LZ4-block), triggered by sending `currentPresetDataJsonRequest` (field 78) right after `current_preset_data_request` (field 2) **inside the handshake burst** — a standalone request later gets no reply. It's a ~1.5 KB-compressed PARTIAL (decompresses ~3.4 KB, truncates at `"scenes"`); `audioGraph.guitarNodes` survives in the prefix (tolerant brace-match to recover it). **NUANCE (`probe --dump-currentpresetdata`): the ~3.4 KB truncation is the LEAN/stale-connection behavior — a HEALTHY dense-heartbeat session (the `monitor.rs` live-listener) delivers ~17 KB including the complete `ftsw` (byte ~4330) + all scene NAMES, truncating only at the final scene's `uuid`.** So it is session-health-dependent, not a hard limit; FS-tags parse `ftsw` out of this live field-3. Still not byte-complete (final scene cut), so the OFFLINE `.preset` stays the canonical FULL-read source for write paths. Hence `Session::connect()` is lean (leveling) vs `connect_for_discovery()` (sends field 78 for block enumeration, ~2 s). **On fw 1.8.45 field-78 actively HURTS first paint** — its multi-packet reply drowns the field-3 push. Startup uses the monitor's single `connect_with_firmware()` session: firmware, preset list, and common-case graph are assembled into `StartupSnapshot`; if the graph is absent after bounded heartbeat warmup, the fallback is a non-destructive field-8 read of the active slot. **No startup path sends LoadPreset.**
  - **Slot-addressed read + full-read verdict (RESOLVED on 1.7.75):** a _slot-addressed_ partial is available via `presetDataRequest` (PresetMessage field **8**) → `presetDataChanged` (field **9**, `presetJson` = field 3, **plaintext** — not LZ4). Same in-burst rule, but it must carry **no `batchStatus`**. See `proto::preset_data_request` / `session::connect_with_burst_request` + `harvest_slot_read`, driven by `probe --export <listEnum> <slot>`. It is a **device-truncated PARTIAL** (per-slot-deterministic size — e.g. slot 1 = 17264 B with all 8 sceneNames, cut inside the final scene). Fired on a quiet line with the `connection_request` re-arm (`read_slot_preset_json`) it answers 26/26 reliably on fw 1.8.45 (the loss seen under the handshake flood was device-side request-dropping, not reassembly). The batch sweep `scan_preset_scenes` (one session, selected presets only) and the single-preset `read_preset_scenes(list_index)` remain the backend lanes over this read, but both are UI-ORPHANED (see notes/protocol.md) — production Level rows source scenes from the startup backup scan's COMPLETE `presetJson` (`BackupPresetRow.scenes`), never from an eager field-8 sweep. Still a partial, so the OFFLINE `.preset` remains the canonical FULL-read source for write paths. `exportPresetRequest` (field **115**) gives the companion **no response** (replaying the byte-identical frame a live Pro Control capture showed PC sending gets nothing) — but it is **not "unimplemented":** PC's export-to-file sends 115 standalone no-batch and writes a complete `.preset`, almost certainly from PC's own in-memory model, not a USB round-trip. Characterise as "not companion-replayable as a full read." **Verdict: no reliable complete-preset read over USB — the companion app's canonical full-preset source is OFFLINE `.preset` files** (see `notes/write-safety.md`). Probe scene-leveling enumeration (`commands::presets::read_preset_scenes_complete`) now detects a scene-tail cut into this partial — an empty repaired `sceneName`, or `scenes.len()` short of every scene the doc itself references (`footswitch::max_referenced_scene`) — and falls back to the COMPLETE `presetJson` off the device backup, guarded on slot + the field-8 partial's own `displayName` + `info.preset_id` (the stable identity; the id check is skipped with a `log::warn!` when the partial can't name one, never compared as an empty-string default).

## Live setters + import framing (byte-exact from a real Pro Control capture)

- `renameCurrentPreset`(13){displayName=f1} — and a PC rename is **rename(13) + saveCurrentPreset(14){slot=f1}** (save-under-new-name; send both to persist); `moveUserPreset`(16){old=f1,new=f2} (persists alone); `clearUserPreset`(15){slot=f1}; all single-packet no-batch. **Outbound multi-packet framing = `0x33` start / `0x34` continue / `0x35` final**, each `MAGIC 00 LEN ≤60B` (symmetric with inbound). `importPresetRequest`(117){presetJson=f1} where **`presetJson` = LZ4-block(raw `.preset` file bytes)** = LZ4(XOR-encoded compact JSON); the device follows with `loadPreset`. **A `saveCurrentPreset` chained before a `loadPreset` on the SAME connection is SILENTLY DROPPED** (the load lands, the save doesn't, no `presetError` — HW `probe --save-load-test`, fw 1.8.45): a save must end its connection (the leveling/doctor timing budget + adopted speedups live in `notes/perf.md`).

## `saveCurrentPreset` commits LAZILY — a same-slot `loadPreset` inside the commit window materializes PRE-save bytes

- **HW-reproduced 2026-08-02, fw 1.8.45.** The commit was observed to land between **T+45 s and T+100 s** after the save; a `loadPreset` of the SAME slot fired anywhere inside that window returns the working copy/DSP to the PRE-save preset, not the one just written. Proven bidirectionally: saving `presetLevel` **0.8733** then loading at **~T+40 s** rendered the OLD **0.4377** state (base measured **−26.00 LUFS** instead of the expected **−20.00**, mono-era convention — see the PR2 metering re-baseline in `notes/leveling.md`); saving **0.4377** then loading at ~T+40 s rendered the **0.8733** state right back; a load at **~T+105 s** (past the window) rendered the fresh saved state correctly. **Revert corollary:** any load→…→save session that falls inside the window re-saves the PRE-save bytes, silently UNDOING the earlier save — a write session's OWN trailing load is just as dangerous as another session's stray one.
- **Two device-side stores, not one.** Field-8 slot reads (`presetDataRequest` → `presetDataChanged`, see the slot-addressed-read entry above) are READ-YOUR-WRITES: a field-8 read at **T+22 s** already returned the fresh saved bytes while a `loadPreset` at T+40 s on the SAME slot was still stale. So a field-8 read proves nothing about what a subsequent LOAD will materialize into the working copy/DSP — they are backed by different device-side stores with independently very-different commit latencies.
- **The field-9 self-compare trap.** `Session::best_json_payload` prefers the LONGEST of the harvested carriers — `(3,1)` (field-3 push), `(79,1)`, and `(9,3)` — and **`(9,3)` is exactly the field-9 `presetDataChanged` reply to a field-8 `presetDataRequest`**. A harvest session that has ever issued a field-8 read therefore risks comparing a freshness check's own oracle against ITSELF: the read-your-writes field-9 doc silently wins the "longest" pick over a genuinely stale field-3 push, so the check would report "fresh" when the load path is still stale. The fix must `raw.clear()` before EVERY harvest attempt, including every retry, so no stray field-9 stream survives into the compare.
- **Incident forensics (preset 24 "TR+BD2+BMP", 2026-08-02 — the leveling corruption this documents).** Base leveling saved `presetLevel` **0.4377 at 14:39:24**. The footswitch batch's single preset load ran **2 s later** — squarely inside the commit window — and materialized the PRE-run `presetLevel` of **≈0.798**. Every one of the run's four pedal sweeps (Plumes/BD2/OCD/Rat, a mix of cliff- and plateau-shaped responses) measured the resulting chain uniformly **+5.2 LU** hot (5.20 / 5.27 / 5.22 / 5.21 LU) — that uniformity across differently-shaped knob responses is the fingerprint of a POST-chain linear error (the stale `presetLevel` multiplier), not a per-pedal solve mistake. Every solved pedal value was therefore correct FOR THE WRONG BASE and persisted **~5 dB too low** once written — and the write session's own load, run **7 minutes later**, was safely past the commit window, so nothing in that later session's own read-back caught it: the Summary showed self-consistent captures of the wrong state throughout. Base itself was NOT the bug — its `C` (**−18.82 LUFS**, mono-era convention — see the PR2 metering re-baseline in `notes/leveling.md`) reproduced exactly across three independent measures.
- **Enforcement:** a per-slot save registry + an `ensure_fresh_load` barrier (see `.claude/rules/danger.md`) — a witness-compared re-load-until-fresh at every load site downstream of a same-slot save, with a time-gated fallback so it can never hang past the commit window. Full model in `notes/leveling.md`'s footswitch section.

## Slot addressing: device userSlot = list index + 1

- **HW-confirmed 1.7.75.** `list_my_presets` is 0-based; the slot-addressed setters (`loadPreset.presetSlot`, `saveCurrentPreset.userSlot`, `clearUserPreset`, `moveUserPreset`) and the Song read's `userPresetSlot` are all **1-based**. `session.rs` owns this translation (`load_preset`/`save_current_preset`/`clear_user_preset`/`move_user_preset` take a **0-based list index** and send `+1`); callers pass list indices. This **fixed a latent off-by-one in the leveller** (it sent the 0-based index straight through, so it loaded/levelled/saved the _previous_ preset — verified post-fix: `load_preset(2)`→"Cello", `(3)`→"Synth"). The list's empty-slot marker is **`--`** (also "Empty"). `requestNextEmptyPresetSlot` (81→82) is **dead** on 1.7.75. The Song-preset read (`songMessage` 11 → `songPresetListResponse` 13) only replies **in-burst with a top-level `batchStatus`** (preset reads are batch-bearing; setters omit it). **In-place edit + Song links:** overwriting a song-bound slot with a _different-identity_ preset empties the Song row — link-safe editing must preserve `info.preset_id` + scene structure (LIVE `changeParameter`+save, or identity-preserving OFFLINE re-import). See `notes/write-safety.md`.

## A preset-list read on a session that just streamed a large preset body comes back SHORT — and an empty name makes the backup fallback refuse

- **`list_my_presets()` issued on the SAME session that has just completed a large field-8 preset read can come back without the slot you are asking about.** That is the documented back-to-back-lean-session shape the list reassembly is weak on (see the tolerant-vs-strict entry and `.claude/rules/e2e.md`'s seeding section) — but it had a second, non-obvious consumer. `slot_read::read_slot_preset_sections` reads the occupant's NAME that way, purely to guard the backup fallback's slot mapping, and `read_slot_preset_complete` REFUSES outright when that name is empty: _"the preset list did not answer with the slot's name, so a backup re-read cannot be addressed safely."_
  - **HW, 2026-08-19, user-reported.** Opening the Level wizard's scene-handle picker on a "JFF LP Hiwatt 3 scenes" preset (list index 28) failed with exactly that message. The preset was fine and the backup carried it whole; only the NAME lookup came back empty, and the refusal then read to the user as "Couldn't read this preset's controls" — indistinguishable from a corrupt preset. Note the truncation itself is normal and expected for this preset: its `scenes` tail does not fit the field-8 read, which is precisely why the fallback exists.
  - **The name must NOT come from a live list read here.** It now comes from `monitor::startup_preset_name` — the startup snapshot, the same list the UI shows, no device I/O and no device lock — with the live read kept only as a fallback. A name is identity, not freshness: the snapshot is refreshed on connect and a slot whose name changed under the app has bigger problems than this guard.
  - **The probe has NO startup snapshot, so the same refusal came back on `probe --level-preset-scenes` for the Friedman HBE (HW 2026-09-02, fw 1.8.45)** — the snapshot lookup was empty, the same-session list came back short, and the run failed before leveling a single scene although the backup carried the preset. The chain is now snapshot → the partial's own `info.displayName` (the cut spares `info` when it lands in `scenes`, the usual case) → a list read on a FRESH session after `RECONNECT_GAP_MS`. The same-session list is never consulted.
  - **Diagnostic tell:** the error names the SECTION that was cut (`its scenes section(s) were cut off`) AND blames the list read in the same sentence. Two different failures wearing one message — check whether the backup itself was reachable before concluding the preset is too large.

## A device backup is bounded by a STALL budget, not a whole-transfer cap

- **The backup stream runs at ~27 KiB/s (~2.7 chunks/s) whatever the library holds, and the archive is mostly `acdDefaultsBackup` plus the user's IR files, not presets** (HW 2026-09-02, fw 1.8.45: 25 presets, 230 chunks / 2.2 MiB, 84 s; earlier reads on the same unit were 57–59 chunks). A whole-transfer cap of 60 s cut that stream at 163/230 on every caller — the startup library read and the truncated-scene repair preset 28 depends on included. `Session::device_backup`'s `max_secs` bounds the time between progress events (chunk, state change, build tick), so leave the callers' 60 and do not reintroduce a wall-clock cap.

## Address spaces: `read_library_via_backup` reports the 1-BASED device slot, the leveling commands take the 0-BASED list index

- **A guard that compares the two raw checks the NEIGHBOUR preset.** `read_library_via_backup`'s rows carry `.slot` as the **device** slot (what the UI shows, what `preset_json_from_backup` addresses by), while `level_preset` / `level_scenes_apply_batched` / `level_footswitches_apply` all take the **0-based list index** — the same index the app logs as `slot=26`. They differ by one, in the same direction as every other pair in this codebase (see the slot-addressing entry above).
  - **Caught live, 2026-08-19**, by an acceptance script whose identity guard read `.slot == 26` out of a backup library and found `"Plexi"` where it expected `"Plumes+BD2+OCD"` — the preset one position earlier. The guard did its job and refused before any write, which is the whole point of danger.md's rule that the guard must live in the SAME address space as the mutation: had it been written the other way (guard in device space, write in index space) it would have verified one preset and then levelled a different one.

## The scene-context rule: a bare write/measure with no preceding `loadScene` lands in whatever scene the connection currently holds, never base by default

- A preset loads into its SAVED `lastLoadedScene` (HW-confirmed, fw 1.8.45: scratch slot 30 with `lastLoadedScene = 3` — a bare `changeParameter` landed in scene 3's overlay, untouched base). Every base-context write or measure must therefore explicitly recall base (`session::BASE_SCENE_SLOT`) first, hoisted to the top of its connection before that connection's first write (a recall AFTER a write reverts the write — see the re-amp latch nuances above). `leveller.rs`'s `capture_full_at`/`set_knob`/`set_knobs`/`write_footswitch_values` and `commands/doctor.rs`'s `apply_ops_under_scene` all do this; `SimDevice` models the same `lastLoadedScene` behavior offline (`sim_device.rs`) so the omission is gate-catchable.

## The Scene-Edit flag state decides where an enable-less scene write lands — not whether the overlay carries the param

- **HW, fw 1.8.45.** The overlay SHAPE encodes the flag: a full overlay (any non-bypass-family key) = Scene Edit ON, a bypass-only/empty overlay = Scene Edit OFF. Three probed landings for a scene-context `changeParameter` with NO `setNodeSceneEdit`:
  - **Full overlay, param present** → lands on the overlay (slot-30 matrix, `probe --scene-write-cell`).
  - **Full overlay, param ABSENT** → EXTENDS the overlay per-param; sibling overlay params survive (no reseed) and base is untouched (crafted Full-partial probe, scratch slot 407: TubeScreamer scene-0 overlay without `level`, write 0.22 → overlay gained `level: 0.22`, base stayed 0.65, other scene untouched).
  - **Bypass-only overlay** → lands on BASE, the overlay unchanged — this scene SHARES the node's knobs with base, so the write changes every sharing scene (crafted probe on a `{bypass}`-only overlay: base gain 2.5 → 7.0). Same base leak as the overlay-ABSENT case (G3 `hpf` probe), but here the enable is no fix: it would reseed nothing useful and break the player's deliberate share.
  - Consumed by `scene_jobs::scene_overlay` (`SceneOverlay::{Full,BypassOnly,Absent,Unknown}`) and `leveller::set_knobs`' per-node write-shape decision; `SimDevice` models the same landings offline.

## Scene leveling is ONE-SHOT open-loop on the active amp's `outputLevel`

- **The app command `level_scenes_apply_batched` calls `leveller::level_scenes_oneshot`** (measure each scene AS-IS via an ISOLATED fresh re-amp capture → `solve_level` → `apply_level`, bounded secant correction that always lands the best point). Hard rules: level Base via `presetLevel` FIRST (a GLOBAL multiplier over ALL scenes — never raise it to boost a quiet scene); change ONLY the amp `outputLevel` (preamp/master/volume forbidden; the exact param allowlist + the `ACD_TMRumbleV3` nuance live in `notes/leveling.md`); enable Scene Edit then write QUICKLY (**enabling Scene Edit is not itself harmless** — `set_node_scene_edit(node, true)` alone reseeds that node's ENTIRE scene overlay from base, silently wiping any other already-scene-edited param on that node; so the enable is sent ONLY for a node with NO overlay in the target scene, where the reseed has nothing to lose — `set_knobs` reads that per-node state from the run's ONE field-8 read (`scene_jobs::scene_overlay`) and REFUSES the write when the answer is unknown (truncated read / no read), since the alternative is corruption. The earlier repair-by-diff mitigation, which re-wrote the wiped siblings in the same batch, is deleted: it was unnecessary in both branches and never landed on HW (8/8)). The device silently drops a scene write after a ~400–450 ms PER-COMMAND IDLE GAP (HW: `probe --bisect-scene` + the Hiwatt slot-31 discriminating run — a 450 ms gap dropped 6/6 bare writes at only ~450 ms since `loadScene`, refuting the earlier "~700–750 ms total window" reading; no presetError, nothing persists; same session-lapse family as the idle re-amp-OFF drop), so every pre-write gap stays ≤300 ms (`SETTLE_AFTER_SCENE_RECALL_MS`=150 + `SETTLE_AFTER_SCENE_EDIT_MS`=300, the latter slept ONLY when an enable was actually sent; scene settles down to 50 ms still land on the scene overlay, never the base), plus a ONE-shot dropped-write retry (`apply_first_verified`: a ≥2 dB intended move reading back ~flat re-applies once before any clamp verdict). A ≥6 dB knob change that doesn't move the USB 1/2 capture is an honest `no_authority` off-branch clamp, never a success. The device pushes NO field-3 while re-amp is engaged, so knob picks resolve in an un-engaged pre-pass — which serves the ALREADY-ACTIVE scene (the preset's saved `lastLoadedScene`) from the post-load doc instead of recalling it (field-3 pushes only on a CHANGE; a no-change recall harvests nothing → a roaming per-scene "can't classify routing" build fail that follows the preset's last save) and is ALSO the runners' preset load (`level_scenes_oneshot`/`level_scenes_rebalance` never re-load the preset; the UI batches adjacent same-preset scene rows sharing instrument+target into ONE `level_scenes_apply_batched` call — the old per-scene dispatch flashed the unit back to base twice per scene). **ONE save per preset:** scene writes accumulate UNSAVED (`LevelOptions.defer`) and the runner saves ONCE at batch end (`save_deferred_scene_writes`: recall the prepass's original `lastLoadedScene` first so the save stamps the pre-run base/scene/FS state, save on a clean never-re-amped connection, retry once; also fired on cancel) — HW `probe --defer-scenes`: unsaved scene-edit writes survive scene recalls/reconnects, a re-recall does NOT revert them, one save persists all accumulated overlays. Footswitches mirror it (`write_footswitch_values`: measure every switch first, then ALL confirm-gated writes on ONE live-edit session + ONE save; any unconfirmed write aborts before the save; the UI batches a preset's adjacent FS rows into one `level_footswitches_apply` call). A scene that can't reach target clamps honestly ("clamped at <LUFS>"). The retired closed-loop **BatchedLive** harness (`level_scenes_live_batched`, kept only for `probe --bench-scene-leveling`) MIS-MEASURES on its shared stream — mechanics + evidence in `notes/leveling.md`.

## `outputLevel`=0 is DEEP DIGITAL SILENCE on the real TMP, and `leveller::loudest_loudness` ERRORS ("no signal captured") on a silent capture

- **A finite LUFS isn't recoverable from silence.** So a both-lanes-muted rebalance floor (`probe --mute-floor`) reads as silence (the IDEAL mute, no bleed → trustworthy equal-solo balance), and any code that measures a deliberately-muted state must treat the "no signal captured" error as a sentinel deep floor (`leveller::MUTE_FLOOR_SILENT_LUFS`), NOT propagate it — else it aborts the scene. Corollary for off-branch detection: a `gtrSplit` amp can sit in the PRE-SPLIT TRUNK (e.g. preset 028's G1), so it always reaches USB 1/2 and never trips the no-authority clamp — the off-branch positive case is unit-tested, not HW-reproducible on 028.

## Re-amp engages reliably only ONCE per connection

- Fresh-connect per engage. **Re-tested 2026-07-28 (`probe --reamp-multi-engage`, 6 arm variants × 3 cycles): the rule cannot be relaxed — nothing WEAKER than the full production composite even engages ONCE.** On a session outside that composite (own-connection fresh `load_preset` → reconnect → arm (`recall_base` + setter) → engage, with the floor-guard retry), the engage is silently ignored: bare engage, heartbeat-then-engage, recall-then-engage, setter-then-engage (the floor observably SCALED with the setter, so the write landed while the engage didn't), the exact `arm_measurement` triple, and a fresh pre-load each read the stationary floor from cycle 1 — while interleaved `--levelpreset` runs measured perfectly every time. Whatever arms the engage lives in the full composite, not any single command; treat the composite as atomic and do NOT budget for engine-side connection-count optimizations here. Its `ReAmpModeChanged` echo is flaky and is NOT proof of engagement — a finite captured loudness is. (BatchedLive honors this: one lean engage-connection per scene; only the preset load and the audio streams are shared across scenes.) **DO NOT re-engage on a held connection** (disengage → settle → re-engage): a `probe --held-reengage` test produced 2 valid distinct readings then WEDGED the device's re-amp AND triggered a USB crash that REBOOTED the Mac. Pro Control holds ONE session only because it never re-amps; so only the measurement PREPASS must reconnect (one engage/scene) — the leveling APPLY (set presetLevel + per-scene `outputLevel` + save, all pure SENDS) runs on ONE persistent session, no reconnect.

## A silent/failed re-amp inject reads as the device's STATIONARY OUTPUT FLOOR, and `measure_c` would accept it as a valid `C` without the production floor guards below

- In a rapid 20-engage `probe --stim-ab` sweep, 19/20 captures measured the post-DSP floor, not the stimulus. The tell: `dynamic_spread_lu ≈ 0.01` (a plucked stimulus through ANY chain shows spread ≫ 0) + a preset-INDEPENDENT `C` (identical −24.16 across 9 very different presets at ref 0.5, mono-era convention — see the PR2 metering re-baseline in `notes/leveling.md` — the floor is post-DSP, so `presetLevel` scales it and the `20·log10` C-model still "holds"). Seen only under the rapid multi-cycle sweep (the open-churn/stream-churn fragility above); isolated 1–2-engage runs injected fine; root cause not pinned. The production leveller now guards every measurement (`leveller::measure_floor_guarded`/`require_live`, `FLOOR_TRIP_LU` = 0.08 with a stimulus-aware disarm for near-stationary EBow captures, quiet-gap retry + `measure_c`'s level-shift confirm); `probe --stim-ab` stays the diagnostic sweep. **The DISTINCT deep-silence class (`"no signal captured"`, peak ≈ −93 dBFS) is a silently DROPPED `set_reamp_mode(true)` — never a wedged device, and a power-cycle is NEVER the cure** (HW-root-caused 2026-07-18: `probe --measure-scene <slot>`'s two back-to-back full handshakes + early engage fail in a post-run churn streak that survives a power-cycle, while `--channels`/`--measure-current` read healthy chain audio mid-"wedge"; production paths are `connect_lean` single-handshake and unaffected — full story in `notes/leveling.md` "Re-amp protocol facts").

## Amp-id matching must be CHECK-FIRST then strip (CabIR/ConvRvb)

- A discovered amp block can carry merged cab/IR/convolution suffixes the catalog's bare bid lacks (e.g. `ACD_HiwattDR103CanModCabIR` → strip `CabIR` → `ACD_HiwattDR103CanMod`), so an amp+cab combo silently SKIPS FS scenes (HW, preset 006). ## Output Assign is per-preset and is applied to the global mixer on every preset LOAD

- Loading a preset overwrites the unit's output-assign matrix from that preset's `outputMixerSettings` (`USB12Input→usb12Active`, `instrumentOutput→instrumentActive`, `comboOutput→micActive`; all 9 cells verified). **The measurement tap's routing is therefore NOT stable across a batch** — a leveling pre-flight that checks mixer routing must re-check it **per preset**, not once at startup. The master volume knob is NOT in the USB 1/2 path (0.001 LU across 50 %→80 %); the USB 1/2 channel _fader_ is (−6.48 LU at its −10 dB mark). See `open-questions.md` A1/B0.

## The leveling capture WINDOW (6 s stimulus + 0.8 s tail) is LOAD-BEARING — trimming it is a ≤0.3 LU re-baseline, not a free speedup (HW-A/B'd, `probe --measure-adaptive`)

- TMP presets are NOT stationary under gated-integrated LUFS: time-effect/reverb presets have a quiet delay/reverb BUILDUP at the start AND a decay TAIL the full capture integrates, so early-exit, tail-drop, OR a preroll-skip each shift the measured loudness preset-dependently (clean +0.30 / delay +0.16 / reverb −0.02 LU; saving 2.4–4.7 s). Do NOT re-attempt the "obvious" capture-shortening optimization as a drop-in. The adaptive early-exit capture exists but is OPT-IN only (`audio::MeasureOpts::adaptive`); the leveling default is `MeasureOpts::full` (validated full capture). **Validate any measurement change against the full-capture oracle (`probe --measure-adaptive` / `--measure-prefix-sweep`), NOT a level→verify round-trip that uses the same method — that's self-consistent and HIDES the offset.** Adopting adaptive is a product decision (re-baseline). **Noise floor — don't chase a phantom re-baseline:** HW LUFS varies ~0.12 LU run-to-run on these non-stationary presets, so an apparent offset across a handful of samples is almost always noise, not a systematic bias (a live-emit-loop "offset" once looked like a re-baseline and dissolved after more blind runs landed it mid-band). Only conclude a bias from a many-sample A/B against the oracle, never from 2–3 captures.

## Dialogs/overlays go through the ONE DS `Dialog` (`ui/Dialog.tsx`) — never roll a per-view `position:absolute` scrim

- An `absolute, inset:0` backdrop resolves against the nearest positioned ancestor (the view body BELOW the 46px tab bar), so it fails to cover the menu AND the flex-centered card gets pushed off a too-tall parent and CROPS (this was a real bug across all 4 dialogs). `Dialog`'s backdrop is `position:fixed` (viewport) + the card is `maxHeight: calc(100vh-32px)` with `DialogBody` owning the scroll, so it dims the whole window and scrolls instead of clipping. Anchored dropdowns/context menus use the ONE `ui/Menu` (Scrim + anchored card; fill with `MenuItem`/`MenuDivider`); search/filter fields use `SearchInput`. ## `connect_device` releases any old HID seize before enabling the monitor

- It does not acquire a UI-owned session; it clears `AppState.session`, sets `MONITOR_ENABLED`, and waits for the monitor's startup snapshot. Acquiring before releasing collides with a stale handle → `kIOReturnExclusiveAccess` (`0xe00002c5`), mis-surfaced as "close Pro Control" even when PC is closed. **The same `0xe00002c5` also fires on CONCURRENT device commands** — the TMP is single-connection exclusive-HID, so firing two device-touching commands at once (e.g. `Promise.all([listSongs(), readSetlists()])`) collides; every device read/write must be **serialized** (`await` sequentially). Front-end serialization alone is insufficient — `with_released_seize`'s release→work→reconnect churn lets two _operations_ overlap across a tab switch because `AppState.session`'s `Mutex<Option<Session>>` only guards the slot, not the whole open→work→close→reconnect lifecycle. So it is enforced by a process-global **`DEVICE_OP_LOCK`** acquired inside every device command's `spawn_blocking` (`lib.rs`); a bounded `IOHIDDeviceOpen` retry in `hid.rs` covers the residual intra-operation kernel-release lag; there is no `disconnect_device` command (a sync command can't hold the gate without stalling the main thread). Operational: heavy rapid open/close cycling multiplies chances to land in the open LOCKOUT below (once believed a distinct "congested state" needing a power-cycle — DISPROVEN, see the lockout bullet), and the gate's serialization amplifies the cost on multi-read pages: keep device opens few and spaced.

## HID open-lockout model (HW-isolated, fw 1.8.45)

- After a session closes, the device accepts a QUICK re-open (≤~800 ms — the leveller's 400 ms gaps and the bench's 800 ms gaps both work) but then LOCKS OUT exclusive opens (`0xe00002c5`) for tens of seconds, and **every failed open attempt appears to RESET the lockout** — hammering retries NEVER recovered across hundreds of HW attempts while a long quiet did. `hid.rs` therefore retries at TWO levels: the same-ref fast lane (6×80 ms, the normal seize-recycle), then full RE-ENUMERATION retries (fresh manager + device copy — a stale device ref fails forever) at 3×8 s QUIET backoff. Teardown unschedules from the run loop before `IOHIDDeviceClose` (spec order) — but do NOT add a "drain until quiet" pump before close: pumping ~1.5 s without heartbeats on a live-cadence session reliably wedged the next open (HW A/B'd both ways). A `probe` invocation can also HANG pre-output with ZERO lines printed (`hid.rs` `rx.recv()` has no timeout) when its open lands in this lockout — that's a wedged connect, not a solver loop; kill it, wait a quiet gap, retry once (the identical retry succeeds). **Diagnosing `0xe00002c5` — three causes, check in THIS order (a real session mis-ordered them):** (1) **believe the error text first** — Pro Control genuinely holding the device is the most common cause, and "PC connects and drives the unit flawlessly" is NOT evidence against it (PC working while our exclusive open fails is exactly what PC-holds-the-seize looks like); (2) **this open-lockout** — the tell is a fresh open failing shortly after a session close; the in-process retry ladder does NOT ride it out (HW-observed: an open ~5 s after a handshake close failed through 41 s of ladder retries — each attempt resets the window), while ≥60–90 s of TRUE quiet followed by a SINGLE attempt usually succeeds (still capricious: one attempt failed even minutes after the last op). A plain `probe` list succeeding proves the device is free and healthy — reach for it before any heavier theory; (3) there is NO third "congested state needing a power-cycle" — that theory was DISPROVEN (HW 2026-07-17): a night of apparent monotonic degradation was really (a) `list_my_presets_strict` failing on the interleaved responses back-to-back lean sessions produce (tolerant reads returned the full 504-entry bank all night; strict returned truncated 190–236-record fallbacks whose re-arm retries themselves armed the lockout) + (b) this lockout re-armed by every retry — long TRUE quiet + a SINGLE attempt recovers, Pro Control worked flawlessly throughout, and no power-cycle was ever needed. Corollaries: seed/sweep/in-place-write list reads are TOLERANT + a completeness floor (never `list_my_presets_strict`, which stays correct only for the snapshot/monitor paths); the online e2e seeds via a fresh `probe --seed-scenario` process BEFORE the server starts with spaced retries (see `scripts/e2e.sh`).

## `connect_for_discovery` (field-78) is effectively DEAD on fw 1.8.45

- Beyond drowning the field-3 push at connect, field-78 kills field-3 delivery for its WHOLE session (3/3 handshakes + a re-load + dense-heartbeat coax all failed to produce field-3 on a field-78 session). Block/graph discovery must use a RICH lean session instead: heartbeat warmup → `send_and_collect` LoadPreset (NOT `load_preset` — `transact_eager` discards the reports the 125/field-3 pushes ride on) → pump → `current_preset_value()` from the accumulated push bodies (the monitor's graph-from-push-bodies approach; `prepass_scene_docs` + the bench intel session are the references). The device pushes field-3 only on a CHANGE or at connect — an idle session gets nothing to harvest. **This affects `list_level_blocks` (HW):** `connect_for_discovery` on 1.8.45 → ZERO amp candidates → FS-scene leveling silently SKIPS every scene. So `discover_blocks_rich` (heartbeat warmup → `send_and_collect(load_preset)` → pump → `current_preset_blocks()` from push bodies) is the primary; the field-78 path stays only as an older-firmware fallback.

## Boot-window `IOHIDDeviceSetReport failed: 0xe00002d6` (kIOReturnTimeout) is NOT an error — it's "device not ready yet"

- On a cold boot the TMP's HID interface enumerates (so `IOHIDDeviceOpen`/seize succeeds AND the hotplug watcher fires) ~20 s before its USB stack accepts reports, so the first handshake _send_ times out (observed live: 3 such failures over ~20 s, then connect). `connectError.ts` classifies `IOHIDDeviceSetReport failed` (and `no TMP found`) as the friendly "power it on" gate, NOT the red banner — only the actionable `IOHIDDeviceOpen … close Pro Control` (exclusive-access) gets the red banner. Do not "fix" the timeout with a retry/debounce keyed on a _count_ (the window spans several retries); classify by error instead. (The red banner shows backend `Result<_, String>` text verbatim — classification is string-match in `connectError.ts`; if you reword a backend HID error, update the matcher.)

## Scene policy is pure-lazy, no cache

- There is no eager `scan_all_scenes` startup sweep and non-active preset rows show no scene badge. The ACTIVE preset's drawer stays live from field-3 (`scenes[].sceneName` + `lastLoadedScene` + `ftsw`). LevelDialog rows source scenes from the startup backup scan (`BackupPresetRow.scenes`, complete `presetJson`) — the batch sweep `scan_preset_scenes(list_indices, Channel)` (ONE dedicated lean session reading every selected preset's field-8 JSON back-to-back, the `scan_all_scenes`/`probe --scenes-passive` recipe; HW-measured at ~0.66 s/preset steady-state, ~21 s for 24, streaming so rows could render progressively; `cancel_scene_scan` covers Skip/close) is kept as the backend API but is UI-ORPHANED. NON-DESTRUCTIVE — zero LoadPreset (HW-verified: the active preset survived two full 25-preset sweeps); scene/preset CHANGES on the device are allowed only in the post-disclaimer leveling RUN, never at startup or during setup. The dialog scan is scenes-only: per-preset `listLevelBlocks` (LoadPreset + discovery, ~4 s/preset, destructive) must NEVER run on dialog open — block pickers stay role-based (LEVEL_ROLES) and resolve when the run loads each preset. Single-preset reads keep `read_preset_scenes(list_index)` (also UI-orphaned; monitor metadata lane, ~1.6 s incl. contention; batches must use the sweep — the lane also provokes per-read `connectionError` spam on the heartbeat session). The whole-bank passive sweep is available as `probe --scenes-passive`; the destructive LoadPreset→`sceneListResponse`(125) sweep as `probe --scenes` benchmark. Load-bearing protocol facts behind field-8 reads: (1) the device answers exactly **ONE data request per burst state**; a re-sent `connection_request` **re-arms** that state on the open connection. (2) A read fired mid-flood is **dropped device-side** — fire reads on a quiet line. The re-arm in (1) is REQUIRED only on a QUIET/dedicated session; on an ALREADY-LIVE session (the monitor's dense heartbeat) it is harmful — the device answers it with a per-read `connectionError`, so the live callers use `read_slot_preset_json_live` which skips it (HW `probe --slotread-live`). (3) A batch-bearing `preset_list_request` is NOT answered on a minimal burst (the device only answers it inside the recognized full handshake). (4) The field-9 stream ends in a `0x35` final frame, so harvests must try both `streams()` and `streams_final()`.

## Preset-list reassembly also needs both stream rules

Leveller/probe/clear call sites stay on tolerant `list_my_presets` (they shape their own bursts; a re-arm would clobber their timing).

## CodeRabbit: progressive review is automatic — post NO command on a reviewed PR

- Pushing fix commits or replying to threads is enough; the incremental review picks them up on its own. **`@coderabbitai review` and `@coderabbitai resume` are the only two commands postable on the agent's own judgment**, each under its one condition. **`review`**: ONLY once a review limit has been _lifted_ (CodeRabbit said "Review limit reached — next review available in N minutes" AND that window has elapsed); ambiguous silence is not a lifted limit, so quiet means keep watching. **`resume`**: only when CodeRabbit has AUTO-PAUSED — after `reviews.auto_review.auto_pause_after_reviewed_commits` reviews (default 5; unset in `.coderabbit.yaml`, and PR #119 tripped it at 7 reviews / 16 commits) it stops reviewing silently and announces it ONLY inside the walkthrough comment's BODY as a `> [!NOTE]` "Reviews paused" block naming `resume` (re-enable automatic reviews) and `review` (one-shot). So diagnose a silent PR by READING that comment body in full — grepping it for rate-limit strings and reading only its first ~150 chars missed this for 7 hours on #119. **`@coderabbitai full review` is NEVER posted** (nor `@coderabbitai resolve` / a manual "Resolve conversation" — resolving is CodeRabbit's own acknowledgment that it accepted a fix or a rebuttal, so doing it by hand forges the receipt). Fix the valid findings, reply-with-reason on the invalid ones, resolve nothing. **Observed across this repo's whole history (49/49 approvals landed with EXACTLY ZERO unresolved threads):** CodeRabbit's approval is a verdict flip on THREAD STATE, not the output of a review round (#118 and #119 both approved within ~20 s of their last thread clearing) — GitHub's ruleset sets `required_review_thread_resolution: false`, but that is GitHub's gate, not CodeRabbit's, so ONE permanently-unresolved thread blocks approval indefinitely (#119 sat un-approvable ~5 h). A thread clears ONLY when CodeRabbit itself resolves it — posting `review` can only ADD threads, never clear one, so a "wait out the rate limit, then post `review`" loop cannot terminate. **Never argue CodeRabbit out of its own close-out:** when it offers to open a tracking issue for a deferred finding, ACCEPT it (declining because "a notes file already tracks it" removed its only way to resolve that thread; re-accepting produced issue #124, and linking it from the note cleared the thread in seconds). **Findings arrive in TWO channels and a thread-based loop sees only one:** inline review threads, AND "Outside diff range comments" that exist ONLY in a review BODY — no thread id, no `--json` field, not repliable or resolvable per-thread. Read them with `gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[].body'` (bodies ACCUMULATE — a finding raised in review 2 is not repeated in review 5, so sweep every one). PR #119 carried 20 such findings across 5 bodies; 5 were never addressed, incl. a Critical destructive-save guard. **`@coderabbitai approve` is NEVER posted on the agent's own judgment:** `reviews.request_changes_workflow` is ENABLED here (`.coderabbit.yaml:13`), so CodeRabbit submits a real review that counts toward "protect main" — posting `approve` self-approves the repo's own merge gate. (`resolve` changes no formal review state itself — it unblocks only by clearing threads so the thread-state flip fires: that rescues a verdict blocked on OPEN confirmed-fixed threads, the user-authorized #161 recovery below, but does nothing for a verdict already stuck with ZERO open threads, where `approve` is the lever.) **The ONE exception is owner-authorized, for a STALE verdict** (exercised on #160, 2026-08-30): CodeRabbit had withdrawn its only finding in-thread and resolved every thread, yet `CHANGES_REQUESTED` never flipped — breaking the 49/49 ~20-s pattern above, and a 10-hour watch proved it never self-heals. The verdict being CodeRabbit's own retracted position, the owner directed `approve`; it flipped to APPROVED and auto-merge landed the PR in seconds. So a stale-verdict escalation must NAME `approve` as the remedy the user can authorize — a PR author cannot approve their own PR on GitHub, so "dismiss and approve manually" is not an available alternative. **CodeRabbit's own resolve can FAIL platform-side** (#161, 2026-08-30): it confirms the fix in-thread, then replies "I couldn't resolve this review thread ... Please retry or resolve it manually." That invitation is the HUMAN's, and hand-resolving on GitHub strands the verdict anyway — the APPROVED flip reads CodeRabbit's OWN thread state, not GitHub's (hand-resolve, verdict stayed CHANGES_REQUESTED; had to unresolve). Recovery: reply in-thread asking it to retry → it answers that resolve works only as a top-level command → the USER picks and authorizes `resolve` or `approve`. On #161 the user's top-level `resolve` cleared both threads as CodeRabbit's own acknowledgment and the verdict flipped to APPROVED in seconds. Known trap: a rate-limited attempt can mark head commits _processed_, making a later plain `review` no-op in seconds ("does not re-review already reviewed commits") — verify a review actually RAN by formal-review + inline-comment counts, never ack timing (PR #51: an ack edited to "finished" was still a no-op; the ONE walkthrough comment is edited in place, so only the latest attempt shows). A proven no-op escalates to a HUMAN, never to a second command. Every rebase/force-push and same-day dependabot/auto-merge PR drains the same shared per-developer quota, and each push trips a FRESH rate-limit window that LENGTHENS (33 → 41 → 42 min on #119) — thread replies do not: they cost no quota and are served in ~15–30 s even while review quota is exhausted. A reply is the cheap move; a push is the expensive one. CodeRabbit skips DRAFT PRs (no quota) — iterate in draft, mark ready when settled.

## Auto-merge arms ONLY for `main`-targeted PRs

- **`.github/workflows/arm-auto-merge.yml`, since PR #52.** The "protect main" ruleset (1 approving review MANDATORY + `require_last_push_approval` + build-test/commitlint/e2e; `bypass_actors` deliberately EMPTY — don't re-add) covers only `~DEFAULT_BRANCH`, so auto-merge armed on any other base had nothing to wait for and merged the instant a PR left draft — that's how a stacked child (#50) merged with zero review into its already-merged parent, stranding its work off main. Stack/side-branch PRs merge only by deliberate manual action. **Corollary of `require_last_push_approval`: never push while an approval is pending or landed** — the push dismisses the approval AND can re-arm CodeRabbit's auto-pause counter, so batch fix commits and push BEFORE the review lands, never after. Companion setting: `delete_branch_on_merge` is ON — GitHub's child-PR retarget cascade fires on branch DELETION (not on the parent's merge), so keep it on; never `gh pr merge --delete-branch` a stacked parent (the client-side delete races the retarget and closes the child). **Auto-merge MUST arm with a GitHub App token, never `GITHUB_TOKEN` (since PR #62):** GitHub's anti-recursion rule suppresses every downstream workflow (`release.yml`/`ci.yml` `on: push`) for a merge attributed to the default `GITHUB_TOKEN` (`github-actions[bot]`), because native auto-merge attributes the eventual merge push to whoever ENABLED it. A `GITHUB_TOKEN`-armed merge therefore lands on `main` and cuts NO release — the silent-backlog trap that lost 3 sessions (v1.6.0 had to be hand-cut via `workflow_dispatch`). `arm-auto-merge.yml` mints an App token (`actions/create-github-app-token`, secrets `AUTOMERGE_APP_ID`/`AUTOMERGE_APP_PRIVATE_KEY`, App installed with Contents+PRs write) so the merge is the App bot's push, which DOES fire `on: push`. Do NOT revert arming to `GITHUB_TOKEN`. Fail-loud safety: if the App is uninstalled/under-permissioned the mint step goes red and the PR just won't merge — never a silent release miss.

## Fully automatic connection

- There are no manual Connect/Disconnect buttons. On mount the frontend calls `connect()` (no `is_connected` probe; that command was dropped) and then retries every `RETRY_MS` (3 s) on a guarded `setInterval` until the device is found, so plugging the TMP in later connects on its own; the interval goes inert once connected. `connect_device` starts the monitor and returns the monitor snapshot's firmware + graph; `listPresets` then resolves from the same snapshot. If no device is present (`connect_device` errors with "no TMP found") the red alert is suppressed and a friendly **"Connect your unit over USB-C … it connects on its own"** banner prompts instead (gated on a one-shot `attempted` flag so it never flashes on first paint); actionable errors (e.g. "close Pro Control") still surface as a red alert, and the header `DeviceStatus` indicator shows `disconnected` (hollow) / `reading firmware…` (amber pulse) / `connected · <fw>` (green, the unit's firmware version). **Connection-loss detection IS implemented**: `watcher.rs` emits `tmp://device-{attached,detached}` — on macOS via a non-seizing IOHIDManager (near-instant), on Linux by polling `hid::device_present()`'s sysfs walk once a second (hidraw has no matching-callback equivalent reachable without a `udev` crate dependency). On detach App.tsx flips to disconnected + clears the firmware/snapshot state, and the 3 s retry interval stays armed (no longer cleared on first connect) so a replug auto-reconnects. Calibration from the Settings window is unaffected because every device command releases + re-acquires the seize (`with_released_seize`).
  The full first-connect **handshake is load-bearing** — the device only answers after seeing the captured Pro Control sequence (`connection_request` + preset lists + product profile + current-preset/settings/userir requests). Don't trim it without testing.

## An engage after a naked scene recall latches silence — break the idle with heartbeats

- **A re-amp engage whose LAST-command→engage idle gap exceeds ~300 ms is DEAD: the capture reads the device's stationary output floor, not the stimulus.** HW, fw 1.8.45, 2026-08-18, interleaved matrix on a real unit, 7/7 reproducible. SILENT: `probe --measure-scene 407 8` (base-sentinel recall, no write) ×3; `probe --measure-scene 400 {8,0,1,2,3}` (base + heavy amp-flip scene recalls) 5/5. LOUD: `probe --measure-scene 407 0` (light real-scene recall); `probe --channels 407` (the SAME recall plus a `presetLevel` write round-trip — which returned in 253 ms — before the engage); `probe --measure-current` (no recall at all); and every leveling capture (recall + reference-level write), including the SAME heavy scene recalls on slot 400. The discriminator is GAP-BASED, not presence-based: it is the LAST-command→engage idle duration, not merely whether anything was SENT between the recall and the engage.
  - **2026-08-31 bisect corrects the "any command rescues it" reading of the matrix above.** A zero-write `--measure-pair` base reading (`arm_pair_measurement`'s old shape: `arm_measurement`'s own trailing settle immediately followed by a second settle, nothing sent between them) latched the floor 2/2 at a ~600 ms gap — and those failing runs DID have an intervening `presetLevel` write earlier in the sequence, so "a command happened somewhere before the engage" was never the deciding factor. A single write added to the same shape kept the gap at ~300 ms and passed 1/1. The rule is: keep every last-command→engage idle gap ≤300 ms; ~600 ms latches.
  - **Two candidate mechanisms; the fix is designed to cover both.** (1) The per-command idle-gap cliff (see the `SETTLE_AFTER_SCENE_EDIT_MS` comment block in `src-tauri/src/leveller.rs`): the device silently drops a command whose preceding per-command idle gap exceeds ~400–450 ms, and the engage is just another such command — in the failing shape it arrives after two back-to-back 300 ms settles, one 600 ms idle gap with nothing sent since the recall. (2) A heavy recall leaves the DSP muted for 600–850 ms and an engage inside that window latches the mute. In every working shape either a write round-trip broke the idle AND pushed the engage to ~850 ms post-recall, or there was no recall to begin with. One wrinkle mechanism (1) explains better: `measure_scene_asis` (the scene-leveling prepass) engages a bare `load_scene → 300 ms → engage` shape — a single 300 ms gap, engage well inside any mute window — and measured the same heavy scenes LOUD.
  - **The fix** lives in `leveller::capture_on_session`: when there is neither a force-bypass write nor a reference level (the naked shape), interleave `Session::heartbeat` — the designed keep-alive, writes nothing — into the pre-engage settles, giving recall → 300 → heartbeat → 300 → heartbeat → 300 → engage. That is every idle gap ≤300 ms and the engage ~900 ms post-recall, i.e. both sides of the spec at once, mirroring the proven `--channels` timing. Write-bearing paths (any bypass entry or a reference level) skip it deliberately: their writes already break the idle and their timing is HW-validated green, so it is left untouched. A caveat on the evidence: every write-rescue in the matrix was a `transact` ROUND-TRIP, while a heartbeat is a pure send — post-fix verification covers BOTH arms — the base sentinel (`407 8`: −13.196 LUFS, 3/3, was 3/3 silent) and the heavy amp-flip recalls (the HBE validation re-run's 6 re-measure rows on slot 400, every one loud and within 1.0 LU of target where the pre-fix run read 5/5 silent). `measure_scene_asis` and `arm_pair_measurement`'s zero-write base arm (2026-08-31) hand-roll the SAME cadence for their own pre-engage shapes.
  - **Scene weight appears to matter.** On the doctor-oracle preset a LIGHT real-scene recall (`407 0`) survived the ~600 ms shape, while the base sentinel (`407 8`) and the amp-flip scenes on slot 400 died — consistent with mechanism (2), where a recall that swaps amps holds the DSP muted longer than one that nudges a few params. Do not read a single surviving light recall as evidence the cliff is gone.
  - **Untested hypothesis for why the online e2e never hit this.** The e2e server holds a monitor session with dense ~250 ms heartbeats. If the cliff is PER-DEVICE rather than per-session, that traffic would keep the unit from ever sitting idle, so a capture session's own 600 ms gap would never be a gap from the device's point of view — which would independently explain why production strict scene rows passed 9/9 on the same day the probe path (no monitor running) failed 0/6. Unverified: nobody has run the probe shape with and without a live monitor session to isolate it.

## A footswitch row whose block is ON in the base is only correct when it is the batch's ONLY row

- **`plan_footswitch_jobs` used to build the isolation for a base-on block as `siblings_off_excluding` alone, never asserting the block's own bypass** — on the reasoning that a block already on in the base is part of the base sound and so needs nothing said about it. That holds for a one-row batch and nothing else. A SIBLING row's isolation writes this block's `bypass = true` into the device's working copy, and every capture's `recall_base` re-asserts that mutated copy, so the row measured with the very block it was levelling switched OFF. Its handle then has no authority over loudness, `solve_param_secant` sees an unmoving reading, takes its flat-response branch and reports a reason-less `clamped scene_ceiling`. HW, fw 1.8.45, 2026-08-19, slot 26 "Plumes+BD2+OCD" (`ACD_Plumes` is the only block on in that base, and was the only row that failed):

  | batch                        | switch 5 = `ACD_Plumes.level`, target −23  |
  | ---------------------------- | ------------------------------------------ |
  | switch 5 alone               | `0.3634` → −22.95 LUFS, converged, 7 iters |
  | switches 5,6,7,8             | `0.75` → −26.96 LUFS, CLAMPED, 3 iters     |
  | switches 6,5 (swapped)       | `0.25` → −26.96 LUFS, CLAMPED, 3 iters     |
  | switches 6,5 (after the fix) | `0.3634` → −22.95 LUFS, converged, 7 iters |
  - **Order was never the factor.** Switch 6 converged whether it ran first or second; switch 5 clamped in both positions. The discriminator is solely whether any other row shares the batch.
  - **The `measured_lufs == predicted_lufs` tell.** In every failing case the low-bound reading and the achieved reading agree to four decimals (−26.9648 vs −26.9641). Two independent captures cannot agree that closely on a knob that moved — that equality IS the signature of a row measuring a state its handle does not reach.
  - **The ceiling prepass was right the whole time** (−21.13 LUFS, `unreachable=false`), because it goes through `footswitch::switch_states`, which DOES assert the switch's own nodes. So the solver was contradicting the feasibility check that had just cleared the row. The fix makes the plan build that same list, and `plan_on_in_base_still_asserts_its_own_block_bypass` asserts the two are equal rather than merely similar.
  - **Why the correct value looks like a no-op.** Slot 26's base sound IS switch 5's engaged sound (Plumes on, every sibling bypassed in base), so once base is leveled the right answer for that row is the authored value it already had — 0.3634 against an authored 0.36. A row solving back to roughly where it started is the expected outcome for a base-on block whose target matches base's, not evidence that nothing happened.
  - **`run_e2e_server` had no logger installed at all**, so `log::*` from every shared module was dropped and an ONLINE run's server log carried only its two startup lines. Installing `probe`'s minimal stderr logger is what made the `fs prepass switch=N ceiling=…` lines visible, and those lines are what separated "the prepass is wrong" from "the solve is wrong".

## A scene renders the base chain's ON blocks — an all-false `ftswStates` does NOT bypass them

- **Levelling a footswitch's handle moves every SCENE of the same preset, by the same dB**, whenever that switch's block is one the preset leaves ON in its base state. HW, fw 1.8.45, 2026-08-31, online arc on `E2E Friedman 3S` (410) — `ACD_TubeScreamer` `bypass:false` in base, three FULL-overlay scenes whose overlays carry only `ACD_MarshallPlexi`:

  | moment                                             | scene 0 | scene 1 | scene 2 |
  | -------------------------------------------------- | ------- | ------- | ------- |
  | target                                             | −29.33  | −29.33  | −29.33  |
  | re-measured right after the scene batch's own save | −29.33  | —       | —       |
  | re-measured after the footswitch lane ran          | −31.34  | −31.34  | −31.34  |

  The footswitch lane had cut `ACD_TubeScreamer.level` by exactly 2.0 dB (as-is −21.31 → target −23.31). Every solved scene overlay was correct and persisted (`0.3972` = a clean 2 dB cut from the authored `0.5`), and every lane reported `clamped:false`, `saved:true`, `persist_mismatch:false` — so nothing in the run's own reporting was wrong. The scenes simply render a chain the later lane then changed underneath them.
  - **`ftswStates: [false, …]` in a scene overlay is not a bypass instruction.** All three scenes carry an all-false `ftswStates`, and all three still heard the base-ON screamer — the 2.0 dB shift is the proof. Reading that array as "these pedals are off in this scene" is what makes this failure invisible on inspection; a scene renders the base chain's own state for anything its overlay does not itself carry.
  - **BASE is immune, and that is what hides it.** A base capture forces every footswitch-owned block off (`doctor_force_bypass`), so base re-measured exactly on target through the whole run while all three scenes drifted.
  - **The bracket is the diagnostic.** One extra re-measure of a single scene IMMEDIATELY after its own batch save, before any later lane writes, is what separates "this row was mis-solved by its own batch" from "this row was moved by a later lane". Without it the two are indistinguishable at the end of a run, and two full online runs were spent on the wrong half.
  - **The fix is ORDER, not a re-solve.** The dependency is one-way: a footswitch row is measured in BASE context, so a scene's own amp overlay can never move it back. The order is PER-ROW (`views/level/leveling.ts`'s `runRank`): base, then BASE-CONTEXT
    footswitches, then scenes, then SCENE-CONTEXT footswitches. A blanket "footswitches before
    scenes" held only while every row was measured in base context; a scene-context row must run
    AFTER its scene is on target. Both halves are HW-measured — see `runRank`'s own doc.

## A capture must re-assert the run's own `presetLevel` — the freshness barrier is not enough

- **Every capture's `recall_base` re-runs the device's OWN level-apply, which serves the COMMITTED `presetLevel`** — and that store commits lazily (T+45–100 s, `danger.md`). The footswitch lane used to pass no intended level, relying on `ensure_fresh_load` to have made committed and saved equal by the time captures ran. On a preset with NO scenes the base save and the footswitch batch are seconds apart, squarely inside that window, and the whole batch measured a chain **5.53 dB** quieter than the one the user had just leveled. HW, fw 1.8.45, 2026-08-19, slot 26 "Plumes+BD2+OCD" — the arithmetic closes exactly:
  - base saved `presetLevel` **0.51009**, independently verified at **−23.0002 LUFS**
  - the FS batch measured switch 5's ceiling (handle at max) at **−24.44**
  - the identical state re-measures **−18.91** once committed (on that preset base and switch 5 are the same sound, agreeing to four decimals)
  - gap = **5.53 dB = 20·log10(0.51009 / 0.26999998)**, and 0.26999998 is the preset FILE's original `presetLevel` — i.e. the captures rendered at the pre-save value
- **Every row then failed `fs_target_beyond_ceiling` and clamped a target it was comfortably within.** Post-fix the prepass ceilings land on the independently re-measured truth: switch 5 −18.91 vs −18.9126, 6 −18.27 vs −18.2737, 7 −18.43 vs −18.4303, 8 −17.76 vs −17.7591.
- **Do not diagnose this from the log.** Two of `ensure_fresh_load`'s four exits are silent (no registry entry; first-harvest match), so which one a run took is not recoverable after the fact. That is the reason the capture must not DEPEND on the barrier: it re-asserts the preset's own saved level itself, from the field-8 read (the fresher of the device's two stores — run 5's four ceilings matching truth to ~0.01 dB is the evidence for that ordering, and it is one observation of a race, so a firmware change to either store's commit latency is what would break it).
- The scene lane had the same exposure whenever no headroom trade held a level, and got the same treatment. Gated offline by `a_capture_renders_at_the_saved_preset_level_not_the_stale_committed_one`, which reproduces the incident against SimDevice's lazy-commit model — the sim already reverts the working level on a recall once the slot has been saved, so no hardware is needed to keep this fixed.
- **THE PREPASS AND THE SOLVE ARE COUPLED — an invariant neither module states alone.** `prepass_scene_ceilings` produces the as-is reading that `correct_iter` takes as its `measured0`, and compares against a post-apply capture. If the two render at DIFFERENT `presetLevel`s, the first "response" is the level difference rather than the knob's, and the solve reads authority where there is none. Found offline while gating the fix above: passing the saved level to the solve captures but not the prepass put 9.9 dB into that response on fixture 403, which swamped `no_authority`'s 0.3 LU tolerance and turned an amps-at-zero scene's actionable routing clamp ("route it to USB 1/2") into a reason-less headroom clamp. Both sides now go through the ONE seam, `leveller::scene_capture_level` — do not re-inline either. Note the asymmetry that makes this easy to get wrong: the prepass runs BEFORE the headroom trade decides anything, so it passes `hold = None` and gets the preset's saved level, while the solve passes the real hold; that is deliberate, and the two agree whenever no trade lands.
- **`no_authority`'s 6 dB floor is about the STEP, and the step is sized by the solve — so the verdict needed a probe of its own.** The check is "a move of at least `NO_AUTHORITY_MIN_DB` produced less than `KNOB_TOL_LU` of response", but the first applied move is whatever the open-loop solve asked for. A scene sitting 4 dB from its target gets a 4 dB move, so a knob with LITERALLY ZERO authority fell through to the secant, stalled on a flat slope, and reported a reason-less headroom clamp — the user told "couldn't get there" instead of "this amp doesn't reach USB 1/2", which is the one thing they could act on. `correct_iter` now takes ONE confirmation capture when the first move produced a flat response: step DOWN a full `NO_AUTHORITY_MIN_DB` and look again. Downward only — a raise can clip, and a saturating limiter makes an upward non-response ambiguous. If the probe moves the capture after all, it is a better secant seed than the flat base point, so it is used as one. A healthy knob moves ~1 LU per dB, so this never fires on a working solve. Surfaced by `level-trade.spec.ts`'s zero-authority taxonomy spec at target −21, which had been passing only because the prepass under-rendered and inflated the step to 14 dB.
- **A pure-logic gate exists for the scene lane's choice** (`a_scene_batch_captures_at_the_saved_level_when_no_trade_holds_one`) because that half is NOT observable offline: SimDevice only reverts a recall's level for a slot the run has already saved, and the scene specs level slots they never saved first. Reverting that arm alone leaves the entire offline suite green.

## A post-save re-read that cannot answer must say UNCONFIRMED, never "did not persist"

## The Doctor's envelope correlator has a PEAKLESS curve on a wash/reverb chain — a floor-relative energy step is the deterministic primary

- **HW, fs13 `ACD_TMLargePlate` (65%-wet, decay 0.7), `probe --doctor-fs 407 13`, fw 1.8.45, 2026-08-24.** 10 logged captures read `estimate_onset: not confident … at lag 130–204 ms`, landing the legacy un-aligned split at `tail=-8.8`; one unlogged run (the first after ~2 h idle) read `tail=-10.5` with `washed` silently absent — the e2e flake. The correlator's lag on this chain is noise, so it lands on either side of the 120 ms gate at random. Offline replay of the dumped captures found the correlation curve FLAT — 0.27–0.37 across every lag 0–250 ms, no peak — so its confidence gate (a corr floor + lag ceiling) cannot detect the peakless shape; it either rejects the capture or accepts an arbitrary wrong lag equally well.
- **The energy onset is deterministic across every chain observed, wet or dry, because the Doctor stimulus always carries a played silent pad ahead of the body** (`leveller::DOCTOR_PAD_MS`): the first 2 ms hop that steps up from the pre-signal floor by ~60 dB lands at 230–232 ms in all 11 captures (wet fs13 ×6, dry fs12, dry fs1) — a true inject latency of ~30 ms. `leveller::doctor_onset` now tries this energy step first, falling back to the correlator only when the step doesn't fire in-band, and to the legacy un-aligned split when neither does.
- **Split sensitivity** (`tail_energy_ratio`): a sustained reverb tail decays ~25 dB/s right after the body, so the split-onset location moves `tail_ratio_db` by ~0.8 dB per 32 ms on the fs13 fixture — 0 ms (un-aligned) → −8.85, 32 ms (true) → −9.6, 48 ms → −10.1, 120 ms → −11.5. A wrongly-confident correlator lag anywhere past ~48 ms is enough to flip `washed` on a marginal wash preset. Separately, the capture's tail LENGTH is wall-clock (`reamp_capture` keeps whatever frames arrive in `play + tail` ms, observed 4.715–4.747 s) and moves the ratio ~0.3 dB per 100 ms — which is why the tail window is now PINNED to the recipe's tail (`DOCTOR_TAIL_MS`) after the body end.
- **Post-fix HW (2026-08-25, `probe --doctor-fs 407 13` ×5, energy step on every run, no WARN):** at the old fixture (mix 0.65 / decay 0.7) the aligned tail read −9.6 warm but −9.9 on the FIRST capture after another session's activity — a real device-side cold-first-capture offset (~0.3 dB, not alignment) leaving 0.1 dB over the −10 gate. The oracle fixture was re-seeded (`#r8`) at mix 0.9 / decay 0.9: −8.3…−8.4 on all five runs including the cold one (σ ≈ 0.05 dB, 1.6 dB margin). Mix alone barely helps (0.9 mix at decay 0.7 read −9.0…−9.2, cold −8.6) because the body gets wetter with the tail; decay is the lever.
