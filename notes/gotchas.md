Companion to `CLAUDE.md`'s Gotchas section. That section states every rule; this file carries the
evidence, the failure each rule prevents, and the protocol detail — for the entries too long to keep
inline. **Concise rules stay in `CLAUDE.md` only and are deliberately not duplicated here.**

Read the entry in full before changing the behaviour it governs.

## LIVE per-node structural edits (the protocol behind the block-edit features)

- **LIVE per-node structural edits (the protocol behind the block-edit features).** These wire facts are driven by **TWO** commands: `bulk_replace_live` (one replace across a selection) and **`copy_apply`** (the Copy tab — an ordered replace/insert/remove op list PER target preset, from `copyModel.diffToOps`; reuses `session::{replace_node,insert_node,remove_node}` + the held-session machinery, same `nodeReplaced(40)`/`nodeRemoved(36)`/`nodeInserted(33)` confirm gate, never-save-on-`presetError`(53), first-edit-after-load retry-harden). Replace any block across selected presets with a stock model (`replaceNode` 39), a user saved block / dual cab (`replaceNodeWithBlock` 100, +library index), or a user IR (`replaceNode`→`ACD_UserIRTMS` + a string `changeParameter` on the node's `file` param), or REMOVE it (`removeNode` 35), or ADD a block (`insertNode` 34 — sent BARE, NO `nodeJsonRequest` preamble, `groupId` is the group KEY; HW-confirmed + UI-wired via Copy; field-2 = the SAME-group FenderId to insert BEFORE the named node (omit = append; a cross-group anchor is silently dropped), entry points `probe --insert-active`/`--insert-map`) — on ONE held session re-armed per preset; confirm on `nodeReplaced`(40)/`nodeRemoved`(36)/`nodeInserted`(33), **never save on `presetError`(53) or an unconfirmed edit** (a wrong-content save corrupted a real slot), stoppable via `cancel_bulk_replace`. Firmware-aware palette (stock models filtered to `since` ≤ connected fw; user IRs + saved blocks are read live so they're inherently fw-correct). **Two INVARIANTS for ANY block-mutation code (`audiograph.rs`):** (1) **A block lives in THREE differently-keyed places — touch ALL or leave dangling state:** `audioGraph.{guitarNodes,micNodes}` (the roster, by FenderId), `scenes[].<group>.<FenderId>` (per-scene overrides, by FenderId), `ftsw[i][].nodes[].nodeId` (footswitch assignments, by EXACT nodeId). Miss the scene path → stale inert overrides; miss ftsw → a footswitch ghost-toggles a block that's gone. `drop_scene_overrides`/`retarget_ftsw` handle 2+3 for `remove_block`/`replace_block` — `create_variant` drops the old block's per-scene overrides via the same shared helper. (2) **The backend matches by EXACT FenderId** — the CabIR/Convolution suffix-normalization (`resolveDeviceId`, see the amp-id-matching gotcha below) is FRONTEND-ONLY, so a frontend-normalized id passed into an OpSpec silently fail-matches (no error, no replacement). **Offline-impossible:** saved blocks are metadata-only (`blockPresetsMap` = 5 keys, no params; `product_profile.json` carries zero default params), so a faithful saved-block/IR insert is LIVE-ONLY — there is no offline payload to reconstruct (don't re-attempt an offline splice). **Form-blind catalog trap:** the same amp `block_id` is catalogued as BOTH a combo and a head (identical `block_name`) — art keyed by `block_id` alone can't tell them apart, and dedup-by-`block_id` silently DROPPED ~45 head amps from the replacer (Amp Heads 48→3). Fixed by threading a `form` prop (combo/head/half_stack) through `BlockArt` (`AMP_FORM_ICON`) + appending "(Combo)/(Head)" to dual-form names (`catalog.ts` `displayName`). **Saved-block palette speed (unrealized fix):** `read_backup_archive` extracts only `normalDb.db3` and DISCARDS the backup's `settings.json`, which already holds `blockPresetsMap` as plaintext — so saved blocks are re-read LIVE at palette open even though the ~22 s startup backup fetched that exact data; parsing it out of `settings.json` is the deeper fix (the current path cache-prefetches the live reads on the quiet post-backup line instead).

## Requests must REUSE `batchStatus` in Pro Control's groups, not increment per request

- **Requests must REUSE `batchStatus` in Pro Control's groups, not increment per request.** The handshake grouping is `preset_list(1)=1`, then favorite/preset_list(4)/preset_list(3)/product_profile/current_preset_info/settings66/userir all=`2`, `current_preset_data_request=3`, `current_preset_data_json_request=4`. If you increment the batch on every request, the device answers only the first couple (the preset lists) then **goes silent** — so leveling's `list_my_presets` works but nothing else (product profile, current-preset data, preset JSON) ever arrives. Mirror the device's exact values. (HW-confirmed.)
  - **Preset JSON / block enumeration:** the preset JSON arrives as `currentPresetDataChanged` (PresetMessage field 3, LZ4-block), triggered by sending `currentPresetDataJsonRequest` (field 78) right after `current_preset_data_request` (field 2) **inside the handshake burst** — a standalone request later gets no reply. It's a ~1.5 KB-compressed PARTIAL (decompresses ~3.4 KB, truncates at `"scenes"`); `audioGraph.guitarNodes` survives in the prefix (tolerant brace-match to recover it). **NUANCE (`probe --dump-currentpresetdata`): the ~3.4 KB truncation is the LEAN/stale-connection behavior — a HEALTHY dense-heartbeat session (the `monitor.rs` live-listener) delivers ~17 KB including the complete `ftsw` (byte ~4330) + all scene NAMES, truncating only at the final scene's `uuid`.** So it is session-health-dependent, not a hard limit; FS-tags parse `ftsw` out of this live field-3. Still not byte-complete (final scene cut), so the OFFLINE `.preset` stays the canonical FULL-read source for write paths. Hence `Session::connect()` is lean (leveling) vs `connect_for_discovery()` (sends field 78 for block enumeration, ~2 s). **On fw 1.8.45 field-78 actively HURTS first paint** — its multi-packet reply drowns the field-3 push. Startup uses the monitor's single `connect_with_firmware()` session: firmware, preset list, and common-case graph are assembled into `StartupSnapshot`; if the graph is absent after bounded heartbeat warmup, the fallback is a non-destructive field-8 read of the active slot. **No startup path sends LoadPreset.**
  - **Slot-addressed read + full-read verdict (RESOLVED on 1.7.75):** a _slot-addressed_ partial is available via `presetDataRequest` (PresetMessage field **8**) → `presetDataChanged` (field **9**, `presetJson` = field 3, **plaintext** — not LZ4). Same in-burst rule, but it must carry **no `batchStatus`**. See `proto::preset_data_request` / `session::connect_with_burst_request` + `harvest_slot_read`, driven by `probe --export <listEnum> <slot>`. It is a **device-truncated PARTIAL** (per-slot-deterministic size — e.g. slot 1 = 17264 B with all 8 sceneNames, cut inside the final scene). Fired on a quiet line with the `connection_request` re-arm (`read_slot_preset_json`) it answers 26/26 reliably on fw 1.8.45 (the loss seen under the handshake flood was device-side request-dropping, not reassembly). The UI reads it via the LevelDialog batch sweep `scan_preset_scenes` (one session, selected presets only) or `read_preset_scenes(list_index)` for a single preset, never as an eager startup sweep. Still a partial, so the OFFLINE `.preset` remains the canonical FULL-read source for write paths. `exportPresetRequest` (field **115**) gives the companion **no response** (replaying the byte-identical frame a live Pro Control capture showed PC sending gets nothing) — but it is **not "unimplemented":** PC's export-to-file sends 115 standalone no-batch and writes a complete `.preset`, almost certainly from PC's own in-memory model, not a USB round-trip. Characterise as "not companion-replayable as a full read." **Verdict: no reliable complete-preset read over USB — the companion app's canonical full-preset source is OFFLINE `.preset` files** (see `notes/write-safety.md`).

## Live setters + import framing (byte-exact from a real Pro Control capture)

- **Live setters + import framing (byte-exact from a real Pro Control capture):** `renameCurrentPreset`(13){displayName=f1} — and a PC rename is **rename(13) + saveCurrentPreset(14){slot=f1}** (save-under-new-name; send both to persist); `moveUserPreset`(16){old=f1,new=f2} (persists alone); `clearUserPreset`(15){slot=f1}; all single-packet no-batch. **Outbound multi-packet framing = `0x33` start / `0x34` continue / `0x35` final**, each `MAGIC 00 LEN ≤60B` (symmetric with inbound). `importPresetRequest`(117){presetJson=f1} where **`presetJson` = LZ4-block(raw `.preset` file bytes)** = LZ4(XOR-encoded compact JSON); the device follows with `loadPreset`. **A `saveCurrentPreset` chained before a `loadPreset` on the SAME connection is SILENTLY DROPPED** (the load lands, the save doesn't, no `presetError` — HW `probe --save-load-test`, fw 1.8.45): a save must end its connection (the leveling/doctor timing budget + adopted speedups live in `notes/perf.md`).

## Slot addressing: device userSlot = list index + 1

- **Slot addressing: device userSlot = list index + 1** (HW-confirmed 1.7.75). `list_my_presets` is 0-based; the slot-addressed setters (`loadPreset.presetSlot`, `saveCurrentPreset.userSlot`, `clearUserPreset`, `moveUserPreset`) and the Song read's `userPresetSlot` are all **1-based**. `session.rs` owns this translation (`load_preset`/`save_current_preset`/`clear_user_preset`/`move_user_preset` take a **0-based list index** and send `+1`); callers pass list indices. This **fixed a latent off-by-one in the leveller** (it sent the 0-based index straight through, so it loaded/levelled/saved the _previous_ preset — verified post-fix: `load_preset(2)`→"Cello", `(3)`→"Synth"). The list's empty-slot marker is **`--`** (also "Empty"). `requestNextEmptyPresetSlot` (81→82) is **dead** on 1.7.75. The Song-preset read (`songMessage` 11 → `songPresetListResponse` 13) only replies **in-burst with a top-level `batchStatus`** (preset reads are batch-bearing; setters omit it). **In-place edit + Song links:** overwriting a song-bound slot with a _different-identity_ preset empties the Song row — link-safe editing must preserve `info.preset_id` + scene structure (LIVE `changeParameter`+save, or identity-preserving OFFLINE re-import). See `notes/write-safety.md`.

## The scene-context rule: a bare write/measure with no preceding `loadScene` lands in whatever scene the connection currently holds, never base by default

- **The scene-context rule: a bare write/measure with no preceding `loadScene` lands in whatever scene the connection currently holds, never base by default.** A preset loads into its SAVED `lastLoadedScene` (HW-confirmed, fw 1.8.45: scratch slot 30 with `lastLoadedScene = 3` — a bare `changeParameter` landed in scene 3's overlay, untouched base). Every base-context write or measure must therefore explicitly recall base (`session::BASE_SCENE_SLOT`) first, hoisted to the top of its connection before that connection's first write (a recall AFTER a write reverts the write — see the re-amp latch nuances above). `leveller.rs`'s `capture_full_at`/`set_knob`/`set_knobs`/`write_footswitch_values` and `commands/doctor.rs`'s `apply_ops_under_scene` all do this; `SimDevice` models the same `lastLoadedScene` behavior offline (`sim_device.rs`) so the omission is gate-catchable.

## Scene leveling is ONE-SHOT open-loop on the active amp's `outputLevel`

- **Scene leveling is ONE-SHOT open-loop on the active amp's `outputLevel`** — the app command `level_scenes_apply_batched` calls `leveller::level_scenes_oneshot` (measure each scene AS-IS via an ISOLATED fresh re-amp capture → `solve_level` → `apply_level`, bounded secant correction that always lands the best point). Hard rules: level Base via `presetLevel` FIRST (a GLOBAL multiplier over ALL scenes — never raise it to boost a quiet scene); change ONLY the amp `outputLevel` (preamp/master/volume forbidden; the exact param allowlist + the `ACD_TMRumbleV3` nuance live in `notes/leveling.md`); enable Scene Edit then write QUICKLY (**enabling Scene Edit is not itself harmless** — `set_node_scene_edit(node, true)` alone reseeds that node's ENTIRE scene overlay from base, silently wiping any other already-scene-edited param on that node; so the enable is sent ONLY for a node with NO overlay in the target scene, where the reseed has nothing to lose — `set_knobs` reads that per-node state from the run's ONE field-8 read (`scene_jobs::scene_overlay`) and REFUSES the write when the answer is unknown (truncated read / no read), since the alternative is corruption. The earlier repair-by-diff mitigation, which re-wrote the wiped siblings in the same batch, is deleted: it was unnecessary in both branches and never landed on HW (8/8)) — the device silently drops a scene write after a ~400–450 ms PER-COMMAND IDLE GAP (HW: `probe --bisect-scene` + the Hiwatt slot-31 discriminating run — a 450 ms gap dropped 6/6 bare writes at only ~450 ms since `loadScene`, refuting the earlier "~700–750 ms total window" reading; no presetError, nothing persists; same session-lapse family as the idle re-amp-OFF drop), so every pre-write gap stays ≤300 ms (`SETTLE_AFTER_SCENE_RECALL_MS`=150 + `SETTLE_AFTER_SCENE_EDIT_MS`=300, the latter slept ONLY when an enable was actually sent; scene settles down to 50 ms still land on the scene overlay, never the base), plus a ONE-shot dropped-write retry (`apply_first_verified`: a ≥2 dB intended move reading back ~flat re-applies once before any clamp verdict); a ≥6 dB knob change that doesn't move the USB 1/2 capture is an honest `no_authority` off-branch clamp, never a success; the device pushes NO field-3 while re-amp is engaged, so knob picks resolve in an un-engaged pre-pass — which serves the ALREADY-ACTIVE scene (the preset's saved `lastLoadedScene`) from the post-load doc instead of recalling it (field-3 pushes only on a CHANGE; a no-change recall harvests nothing → a roaming per-scene "can't classify routing" build fail that follows the preset's last save) and is ALSO the runners' preset load (`level_scenes_oneshot`/`level_scenes_rebalance` never re-load the preset; the UI batches adjacent same-preset scene rows sharing instrument+target into ONE `level_scenes_apply_batched` call — the old per-scene dispatch flashed the unit back to base twice per scene). **ONE save per preset:** scene writes accumulate UNSAVED (`LevelOptions.defer`) and the runner saves ONCE at batch end (`save_deferred_scene_writes`: recall the prepass's original `lastLoadedScene` first so the save stamps the pre-run base/scene/FS state, save on a clean never-re-amped connection, retry once; also fired on cancel) — HW `probe --defer-scenes`: unsaved scene-edit writes survive scene recalls/reconnects, a re-recall does NOT revert them, one save persists all accumulated overlays. Footswitches mirror it (`write_footswitch_values`: measure every switch first, then ALL confirm-gated writes on ONE live-edit session + ONE save; any unconfirmed write aborts before the save; the UI batches a preset's adjacent FS rows into one `level_footswitches_apply` call). A scene that can't reach target clamps honestly ("clamped at <LUFS>"). The retired closed-loop **BatchedLive** harness (`level_scenes_live_batched`, kept only for `probe --bench-scene-leveling`) MIS-MEASURES on its shared stream — mechanics + evidence in `notes/leveling.md`.

## `outputLevel`=0 is DEEP DIGITAL SILENCE on the real TMP, and `leveller::loudest_loudness` ERRORS ("no signal captured") on a silent capture

- **`outputLevel`=0 is DEEP DIGITAL SILENCE on the real TMP, and `leveller::loudest_loudness` ERRORS ("no signal captured") on a silent capture** — a finite LUFS isn't recoverable from silence. So a both-lanes-muted rebalance floor (`probe --mute-floor`) reads as silence (the IDEAL mute, no bleed → trustworthy equal-solo balance), and any code that measures a deliberately-muted state must treat the "no signal captured" error as a sentinel deep floor (`leveller::MUTE_FLOOR_SILENT_LUFS`), NOT propagate it — else it aborts the scene. Corollary for off-branch detection: a `gtrSplit` amp can sit in the PRE-SPLIT TRUNK (e.g. preset 028's G1), so it always reaches USB 1/2 and never trips the no-authority clamp — the off-branch positive case is unit-tested, not HW-reproducible on 028.

## Re-amp engages reliably only ONCE per connection

- **Re-amp engages reliably only ONCE per connection.** Fresh-connect per engage. **Re-tested 2026-07-28 (`probe --reamp-multi-engage`, 6 arm variants × 3 cycles): the rule cannot be relaxed — nothing WEAKER than the full production composite even engages ONCE.** On a session outside that composite (own-connection fresh `load_preset` → reconnect → arm (`recall_base` + setter) → engage, with the floor-guard retry), the engage is silently ignored: bare engage, heartbeat-then-engage, recall-then-engage, setter-then-engage (the floor observably SCALED with the setter, so the write landed while the engage didn't), the exact `arm_measurement` triple, and a fresh pre-load each read the stationary floor from cycle 1 — while interleaved `--levelpreset` runs measured perfectly every time. Whatever arms the engage lives in the full composite, not any single command; treat the composite as atomic and do NOT budget for engine-side connection-count optimizations here. Its `ReAmpModeChanged` echo is flaky and is NOT proof of engagement — a finite captured loudness is. (BatchedLive honors this: one lean engage-connection per scene; only the preset load and the audio streams are shared across scenes.) **DO NOT re-engage on a held connection** (disengage → settle → re-engage): a `probe --held-reengage` test produced 2 valid distinct readings then WEDGED the device's re-amp AND triggered a USB crash that REBOOTED the Mac. Pro Control holds ONE session only because it never re-amps; so only the measurement PREPASS must reconnect (one engage/scene) — the leveling APPLY (set presetLevel + per-scene `outputLevel` + save, all pure SENDS) runs on ONE persistent session, no reconnect.

## A silent/failed re-amp inject reads as the device's STATIONARY OUTPUT FLOOR, and `measure_c` would accept it as a valid `C` without the production floor guards below

- **A silent/failed re-amp inject reads as the device's STATIONARY OUTPUT FLOOR, and `measure_c` would accept it as a valid `C` without the production floor guards below.** In a rapid 20-engage `probe --stim-ab` sweep, 19/20 captures measured the post-DSP floor, not the stimulus. The tell: `dynamic_spread_lu ≈ 0.01` (a plucked stimulus through ANY chain shows spread ≫ 0) + a preset-INDEPENDENT `C` (identical −24.16 across 9 very different presets at ref 0.5 — the floor is post-DSP, so `presetLevel` scales it and the `20·log10` C-model still "holds"). A full `--levelpreset` solve+verify landed 0.00 LU error while measuring ONLY the floor — **solve/verify self-consistency does NOT prove inject health**. Seen only under the rapid multi-cycle sweep (the open-churn/stream-churn fragility above); isolated 1–2-engage runs injected fine; root cause not pinned. The production leveller now guards every measurement (`leveller::measure_floor_guarded`/`require_live`, `FLOOR_TRIP_LU` = 0.08 with a stimulus-aware disarm for near-stationary EBow captures, quiet-gap retry + `measure_c`'s level-shift confirm); `probe --stim-ab` stays the diagnostic sweep. **The DISTINCT deep-silence class (`"no signal captured"`, peak ≈ −93 dBFS) is a silently DROPPED `set_reamp_mode(true)` — never a wedged device, and a power-cycle is NEVER the cure** (HW-root-caused 2026-07-18: `probe --measure-scene <slot>`'s two back-to-back full handshakes + early engage fail in a post-run churn streak that survives a power-cycle, while `--channels`/`--measure-current` read healthy chain audio mid-"wedge"; production paths are `connect_lean` single-handshake and unaffected — full story in `notes/leveling.md` "Re-amp protocol facts").

## Amp-id matching must be CHECK-FIRST then strip (CabIR/ConvRvb)

- **Amp-id matching must be CHECK-FIRST then strip (CabIR/ConvRvb).** A discovered amp block can carry merged cab/IR/convolution suffixes the catalog's bare bid lacks (e.g. `ACD_HiwattDR103CanModCabIR` → strip `CabIR` → `ACD_HiwattDR103CanMod`), so an amp+cab combo silently SKIPS FS scenes (HW, preset 006). BUT reverb amps are catalogued WITH the suffix (`ACD_PrincetonReverb68CabIRConvRvb` IS a catalog bid) — so match CHECK-FIRST (try the id, then strip one canonical suffix at a time, re-check), NEVER greedy-strip (that breaks the catalogued-with-suffix amps). `is_amp_model_id` (Rust) + `resolveDeviceId` (TS, shares `blockArt.ts` `SUFFIX`) both do this; the suffix set is `ConvRvb|CabIR|NoCab|Cab|IR` (NoFx is part of base ids, not stripped — but after a failed strip the resolver APPENDS `NoFx` once and re-checks: a device wet-amp id e.g. `ACD_DeluxeReverb65BlondeVibratoCabIRConvRvb` strips to a bare `…BlondeVibrato` the catalog only carries as `…BlondeVibratoNoFx`. Both TS resolvers (`resolveBlockArt`/`resolveDeviceId`) go through a shared `resolveCatalogId` helper in `blockArt.ts`; keep it in lockstep with Rust `is_amp_model_id`. This also covers the ~6 catalogued-`NoFx` reverb amps for per-scene-leveling amp detection).

## 48 kHz stimulus required

- **48 kHz stimulus required** — that is the **host Core Audio rate** the device must be set to, NOT "the device clock". Measured on a real unit: **a 44.1 kHz stage IS in the USB-in → DSP → USB-out path** — flat-noise re-amp captures collapse to the float noise floor above ~22.05 kHz on two presets with _opposite_ spectral tilts (one rising +17 dB at 12–16 kHz, one ending in a 10.5 kHz cab LPF whose own skirt under-predicts the drop by 48–77 dB), host confirmed at 48 kHz so no host-side SRC. Capture content above ~22 kHz is anti-alias skirt, not preset tone. Relevant to spectrum/EQ-match/Doctor-PSD work. Global settings (incl. a user-changeable `sampleRate`, the mixer strips, and `sceneChangeBehavior`) are readable from the backup's `settingsBackup` JSON — the live `MixerMessage` path (TMS 5) reads as unserved; no write route to it (`SetMasterLevel`, `sceneChangeBehavior` on TMS 3 field 83) has been confirmed either. See `.claude/skills/tmp-companion-data-model/references/open-questions.md` A1/A2/A6.

## Output Assign is per-preset and is applied to the global mixer on every preset LOAD

- **Output Assign is per-preset and is applied to the global mixer on every preset LOAD.** Loading a preset overwrites the unit's output-assign matrix from that preset's `outputMixerSettings` (`USB12Input→usb12Active`, `instrumentOutput→instrumentActive`, `comboOutput→micActive`; all 9 cells verified). **The measurement tap's routing is therefore NOT stable across a batch** — a leveling pre-flight that checks mixer routing must re-check it **per preset**, not once at startup. The master volume knob is NOT in the USB 1/2 path (0.001 LU across 50 %→80 %); the USB 1/2 channel _fader_ is (−6.48 LU at its −10 dB mark). See `open-questions.md` A1/B0.

## The leveling capture WINDOW (6 s stimulus + 0.8 s tail) is LOAD-BEARING — trimming it is a ≤0.3 LU re-baseline, not a free speedup (HW-A/B'd, `probe --measure-adaptive`)

- **The leveling capture WINDOW (6 s stimulus + 0.8 s tail) is LOAD-BEARING — trimming it is a ≤0.3 LU re-baseline, not a free speedup (HW-A/B'd, `probe --measure-adaptive`).** TMP presets are NOT stationary under gated-integrated LUFS: time-effect/reverb presets have a quiet delay/reverb BUILDUP at the start AND a decay TAIL the full capture integrates, so early-exit, tail-drop, OR a preroll-skip each shift the measured loudness preset-dependently (clean +0.30 / delay +0.16 / reverb −0.02 LU; saving 2.4–4.7 s). Do NOT re-attempt the "obvious" capture-shortening optimization as a drop-in. The adaptive early-exit capture exists but is OPT-IN only (`audio::MeasureOpts::adaptive`); the leveling default is `MeasureOpts::full` (validated full capture). **Validate any measurement change against the full-capture oracle (`probe --measure-adaptive` / `--measure-prefix-sweep`), NOT a level→verify round-trip that uses the same method — that's self-consistent and HIDES the offset.** Adopting adaptive is a product decision (re-baseline). **Noise floor — don't chase a phantom re-baseline:** HW LUFS varies ~0.12 LU run-to-run on these non-stationary presets, so an apparent offset across a handful of samples is almost always noise, not a systematic bias (a live-emit-loop "offset" once looked like a re-baseline and dissolved after more blind runs landed it mid-band). Only conclude a bias from a many-sample A/B against the oracle, never from 2–3 captures.

## Dialogs/overlays go through the ONE DS `Dialog` (`ui/Dialog.tsx`) — never roll a per-view `position:absolute` scrim

- **Dialogs/overlays go through the ONE DS `Dialog` (`ui/Dialog.tsx`) — never roll a per-view `position:absolute` scrim.** An `absolute, inset:0` backdrop resolves against the nearest positioned ancestor (the view body BELOW the 46px tab bar), so it fails to cover the menu AND the flex-centered card gets pushed off a too-tall parent and CROPS (this was a real bug across all 4 dialogs). `Dialog`'s backdrop is `position:fixed` (viewport) + the card is `maxHeight: calc(100vh-32px)` with `DialogBody` owning the scroll, so it dims the whole window and scrolls instead of clipping. Anchored dropdowns/context menus use the ONE `ui/Menu` (Scrim + anchored card; fill with `MenuItem`/`MenuDivider`); search/filter fields use `SearchInput`. The DS owns chrome (DialogHeader/Body/Footer padding via `DIALOG_PAD_X`) — callers never hand-set per-dialog padding, and widths are the `sm`/`md` size scale, never raw px.

## `connect_device` releases any old HID seize before enabling the monitor

- **`connect_device` releases any old HID seize before enabling the monitor.** It does not acquire a UI-owned session; it clears `AppState.session`, sets `MONITOR_ENABLED`, and waits for the monitor's startup snapshot. Acquiring before releasing collides with a stale handle → `kIOReturnExclusiveAccess` (`0xe00002c5`), mis-surfaced as "close Pro Control" even when PC is closed. **The same `0xe00002c5` also fires on CONCURRENT device commands** — the TMP is single-connection exclusive-HID, so firing two device-touching commands at once (e.g. `Promise.all([listSongs(), readSetlists()])`) collides; every device read/write must be **serialized** (`await` sequentially). Front-end serialization alone is insufficient — `with_released_seize`'s release→work→reconnect churn lets two _operations_ overlap across a tab switch because `AppState.session`'s `Mutex<Option<Session>>` only guards the slot, not the whole open→work→close→reconnect lifecycle. So it is enforced by a process-global **`DEVICE_OP_LOCK`** acquired inside every device command's `spawn_blocking` (`lib.rs`); a bounded `IOHIDDeviceOpen` retry in `hid.rs` covers the residual intra-operation kernel-release lag; there is no `disconnect_device` command (a sync command can't hold the gate without stalling the main thread). Operational: heavy rapid open/close cycling multiplies chances to land in the open LOCKOUT below (once believed a distinct "congested state" needing a power-cycle — DISPROVEN, see the lockout bullet), and the gate's serialization amplifies the cost on multi-read pages: keep device opens few and spaced.

## HID open-lockout model (HW-isolated, fw 1.8.45)

- **HID open-lockout model (HW-isolated, fw 1.8.45):** after a session closes, the device accepts a QUICK re-open (≤~800 ms — the leveller's 400 ms gaps and the bench's 800 ms gaps both work) but then LOCKS OUT exclusive opens (`0xe00002c5`) for tens of seconds, and **every failed open attempt appears to RESET the lockout** — hammering retries NEVER recovered across hundreds of HW attempts while a long quiet did. `hid.rs` therefore retries at TWO levels: the same-ref fast lane (6×80 ms, the normal seize-recycle), then full RE-ENUMERATION retries (fresh manager + device copy — a stale device ref fails forever) at 3×8 s QUIET backoff. Teardown unschedules from the run loop before `IOHIDDeviceClose` (spec order) — but do NOT add a "drain until quiet" pump before close: pumping ~1.5 s without heartbeats on a live-cadence session reliably wedged the next open (HW A/B'd both ways). A `probe` invocation can also HANG pre-output with ZERO lines printed (`hid.rs` `rx.recv()` has no timeout) when its open lands in this lockout — that's a wedged connect, not a solver loop; kill it, wait a quiet gap, retry once (the identical retry succeeds). **Diagnosing `0xe00002c5` — three causes, check in THIS order (a real session mis-ordered them):** (1) **believe the error text first** — Pro Control genuinely holding the device is the most common cause, and "PC connects and drives the unit flawlessly" is NOT evidence against it (PC working while our exclusive open fails is exactly what PC-holds-the-seize looks like); (2) **this open-lockout** — the tell is a fresh open failing shortly after a session close; the in-process retry ladder does NOT ride it out (HW-observed: an open ~5 s after a handshake close failed through 41 s of ladder retries — each attempt resets the window), while ≥60–90 s of TRUE quiet followed by a SINGLE attempt usually succeeds (still capricious: one attempt failed even minutes after the last op). A plain `probe` list succeeding proves the device is free and healthy — reach for it before any heavier theory; (3) there is NO third "congested state needing a power-cycle" — that theory was DISPROVEN (HW 2026-07-17): a night of apparent monotonic degradation was really (a) `list_my_presets_strict` failing on the interleaved responses back-to-back lean sessions produce (tolerant reads returned the full 504-entry bank all night; strict returned truncated 190–236-record fallbacks whose re-arm retries themselves armed the lockout) + (b) this lockout re-armed by every retry — long TRUE quiet + a SINGLE attempt recovers, Pro Control worked flawlessly throughout, and no power-cycle was ever needed. Corollaries: seed/sweep/in-place-write list reads are TOLERANT + a completeness floor (never `list_my_presets_strict`, which stays correct only for the snapshot/monitor paths); the online e2e seeds via a fresh `probe --seed-scenario` process BEFORE the server starts with spaced retries (see `scripts/e2e.sh`).

## `connect_for_discovery` (field-78) is effectively DEAD on fw 1.8.45

- **`connect_for_discovery` (field-78) is effectively DEAD on fw 1.8.45** — beyond drowning the field-3 push at connect, field-78 kills field-3 delivery for its WHOLE session (3/3 handshakes + a re-load + dense-heartbeat coax all failed to produce field-3 on a field-78 session). Block/graph discovery must use a RICH lean session instead: heartbeat warmup → `send_and_collect` LoadPreset (NOT `load_preset` — `transact_eager` discards the reports the 125/field-3 pushes ride on) → pump → `current_preset_value()` from the accumulated push bodies (the monitor's graph-from-push-bodies approach; `prepass_scene_docs` + the bench intel session are the references). The device pushes field-3 only on a CHANGE or at connect — an idle session gets nothing to harvest. **This affects `list_level_blocks` (HW):** `connect_for_discovery` on 1.8.45 → ZERO amp candidates → FS-scene leveling silently SKIPS every scene. So `discover_blocks_rich` (heartbeat warmup → `send_and_collect(load_preset)` → pump → `current_preset_blocks()` from push bodies) is the primary; the field-78 path stays only as an older-firmware fallback.

## Boot-window `IOHIDDeviceSetReport failed: 0xe00002d6` (kIOReturnTimeout) is NOT an error — it's "device not ready yet"

- **Boot-window `IOHIDDeviceSetReport failed: 0xe00002d6` (kIOReturnTimeout) is NOT an error — it's "device not ready yet".** On a cold boot the TMP's HID interface enumerates (so `IOHIDDeviceOpen`/seize succeeds AND the hotplug watcher fires) ~20 s before its USB stack accepts reports, so the first handshake _send_ times out (observed live: 3 such failures over ~20 s, then connect). `connectError.ts` classifies `IOHIDDeviceSetReport failed` (and `no TMP found`) as the friendly "power it on" gate, NOT the red banner — only the actionable `IOHIDDeviceOpen … close Pro Control` (exclusive-access) gets the red banner. Do not "fix" the timeout with a retry/debounce keyed on a _count_ (the window spans several retries); classify by error instead. (The red banner shows backend `Result<_, String>` text verbatim — classification is string-match in `connectError.ts`; if you reword a backend HID error, update the matcher.)

## Scene policy is pure-lazy, no cache

- **Scene policy is pure-lazy, no cache.** There is no eager `scan_all_scenes` startup sweep and non-active preset rows show no scene badge. The ACTIVE preset's drawer stays live from field-3 (`scenes[].sceneName` + `lastLoadedScene` + `ftsw`). LevelDialog's on-open scan is `scan_preset_scenes(list_indices, Channel)` — ONE dedicated lean session reading every selected preset's field-8 JSON back-to-back (the `scan_all_scenes`/`probe --scenes-passive` recipe; HW-measured at ~0.66 s/preset steady-state, ~21 s for 24) streaming each result so rows render progressively; `cancel_scene_scan` covers Skip/close. NON-DESTRUCTIVE — zero LoadPreset (HW-verified: the active preset survived two full 25-preset sweeps); scene/preset CHANGES on the device are allowed only in the post-disclaimer leveling RUN, never at startup or during setup. The dialog scan is scenes-only: per-preset `listLevelBlocks` (LoadPreset + discovery, ~4 s/preset, destructive) must NEVER run on dialog open — block pickers stay role-based (LEVEL_ROLES) and resolve when the run loads each preset. Single-preset reads keep `read_preset_scenes(list_index)` (monitor metadata lane, ~1.6 s incl. contention; batches must use the sweep — the lane also provokes per-read `connectionError` spam on the heartbeat session). The whole-bank passive sweep is available as `probe --scenes-passive`; the destructive LoadPreset→`sceneListResponse`(125) sweep as `probe --scenes` benchmark. Load-bearing protocol facts behind field-8 reads: (1) the device answers exactly **ONE data request per burst state**; a re-sent `connection_request` **re-arms** that state on the open connection. (2) A read fired mid-flood is **dropped device-side** — fire reads on a quiet line. The re-arm in (1) is REQUIRED only on a QUIET/dedicated session; on an ALREADY-LIVE session (the monitor's dense heartbeat) it is harmful — the device answers it with a per-read `connectionError`, so the live callers use `read_slot_preset_json_live` which skips it (HW `probe --slotread-live`). (3) A batch-bearing `preset_list_request` is NOT answered on a minimal burst (the device only answers it inside the recognized full handshake). (4) The field-9 stream ends in a `0x35` final frame, so harvests must try both `streams()` and `streams_final()`.

## Preset-list reassembly also needs both stream rules

- **Preset-list reassembly also needs both stream rules.** `list_my_presets` tries `streams()` (interleaved-0x35-safe mid-flood) and `streams_final()` (terminal 0x35 tail frame) and keeps the longest decoded record set. This fixes the live "Empt" tail truncation class where the last record's final byte rides the closing 0x35 frame. **But tolerant longest-wins still silently accepts a TAIL-truncated list** (observed live: a monitor reconnect right after a heavy field-8 sweep snapshot'd 371 of 504 records). The SNAPSHOT path therefore uses **`list_my_presets_strict`** (monitor `assemble_startup_snapshot` + the `list_presets` monitor-disabled fallback): `harvest_preset_list_strict` (streams_final + `proto::preset_list_records_strict`, the songs/setlists strict pattern; missing displayName → "" not dropped, preserving `userSlot = index + 1`) → up to 2 re-arm retries on the open session (quiet line → `connection_request` → `preset_list_request`, WITHOUT `raw.clear()` — the startup graph is harvested from the same accumulated reports afterwards) → tolerant fallback + `log::warn` (a warned short list beats a failed connect; truncation is tail-only so present entries keep correct slots). Leveller/probe/clear call sites stay on tolerant `list_my_presets` (they shape their own bursts; a re-arm would clobber their timing).

## CodeRabbit: progressive review is automatic — post NO command on a reviewed PR

- **CodeRabbit: progressive review is automatic — post NO command on a reviewed PR.** Pushing fix commits or replying to threads is enough; the incremental review picks them up on its own. **`@coderabbitai review`** is the ONLY postable command, and ONLY once a review limit has been _lifted_ (CodeRabbit said "Review limit reached — next review available in N minutes" AND that window has elapsed); ambiguous silence is not a lifted limit, so quiet means keep watching. **The ONE other postable command is `@coderabbitai resume`, and only when CodeRabbit has AUTO-PAUSED** — after `reviews.auto_review.auto_pause_after_reviewed_commits` reviews (default 5; unset in `.coderabbit.yaml`, and PR #119 tripped it at 7 reviews / 16 commits) it stops reviewing silently and announces it ONLY inside the walkthrough comment's BODY as a `> [!NOTE]` "Reviews paused" block naming `resume` (re-enable automatic reviews) and `review` (one-shot). So diagnose a silent PR by READING that comment body in full — grepping it for rate-limit strings and reading only its first ~150 chars missed this for 7 hours on #119. **`@coderabbitai full review` is NEVER posted** (nor `@coderabbitai resolve` / a manual "Resolve conversation" — resolving is CodeRabbit's own acknowledgment that it accepted a fix or a rebuttal, so doing it by hand forges the receipt). Fix the valid findings, reply-with-reason on the invalid ones, resolve nothing. **Observed across this repo's whole history (49/49 approvals landed with EXACTLY ZERO unresolved threads):** CodeRabbit's approval is a verdict flip on THREAD STATE, not the output of a review round (#118 and #119 both approved within ~20 s of their last thread clearing) — GitHub's ruleset sets `required_review_thread_resolution: false`, but that is GitHub's gate, not CodeRabbit's, so ONE permanently-unresolved thread blocks approval indefinitely (#119 sat un-approvable ~5 h). A thread clears ONLY when CodeRabbit itself resolves it — posting `review` can only ADD threads, never clear one, so a "wait out the rate limit, then post `review`" loop cannot terminate. **Never argue CodeRabbit out of its own close-out:** when it offers to open a tracking issue for a deferred finding, ACCEPT it (declining because "a notes file already tracks it" removed its only way to resolve that thread; re-accepting produced issue #124, and linking it from the note cleared the thread in seconds). **Findings arrive in TWO channels and a thread-based loop sees only one:** inline review threads, AND "Outside diff range comments" that exist ONLY in a review BODY — no thread id, no `--json` field, not repliable or resolvable per-thread. Read them with `gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[].body'` (bodies ACCUMULATE — a finding raised in review 2 is not repeated in review 5, so sweep every one). PR #119 carried 20 such findings across 5 bodies; 5 were never addressed, incl. a Critical destructive-save guard. **`@coderabbitai approve` is NEVER posted either:** `reviews.request_changes_workflow` is ENABLED here (`.coderabbit.yaml:13`), so CodeRabbit submits a real review that counts toward "protect main" — posting `approve` self-approves the repo's own merge gate. (`resolve` is no substitute for it: `resolve` only marks comments resolved and leaves a `CHANGES_REQUESTED` review standing, so it can never unblock a stuck PR.) Known trap: a rate-limited attempt can mark head commits _processed_, making a later plain `review` no-op in seconds ("does not re-review already reviewed commits") — verify a review actually RAN by formal-review + inline-comment counts, never ack timing (PR #51: an ack edited to "finished" was still a no-op; the ONE walkthrough comment is edited in place, so only the latest attempt shows). A proven no-op escalates to a HUMAN, never to a second command. Every rebase/force-push and same-day dependabot/auto-merge PR drains the same shared per-developer quota, and each push trips a FRESH rate-limit window that LENGTHENS (33 → 41 → 42 min on #119) — thread replies do not: they cost no quota and are served in ~15–30 s even while review quota is exhausted. A reply is the cheap move; a push is the expensive one. CodeRabbit skips DRAFT PRs (no quota) — iterate in draft, mark ready when settled.

## Auto-merge arms ONLY for `main`-targeted PRs

- **Auto-merge arms ONLY for `main`-targeted PRs** (`.github/workflows/arm-auto-merge.yml`, since PR #52). The "protect main" ruleset (1 approving review MANDATORY + `require_last_push_approval` + build-test/commitlint/e2e; `bypass_actors` deliberately EMPTY — don't re-add) covers only `~DEFAULT_BRANCH`, so auto-merge armed on any other base had nothing to wait for and merged the instant a PR left draft — that's how a stacked child (#50) merged with zero review into its already-merged parent, stranding its work off main. Stack/side-branch PRs merge only by deliberate manual action. **Corollary of `require_last_push_approval`: never push while an approval is pending or landed** — the push dismisses the approval AND can re-arm CodeRabbit's auto-pause counter, so batch fix commits and push BEFORE the review lands, never after. Companion setting: `delete_branch_on_merge` is ON — GitHub's child-PR retarget cascade fires on branch DELETION (not on the parent's merge), so keep it on; never `gh pr merge --delete-branch` a stacked parent (the client-side delete races the retarget and closes the child). **Auto-merge MUST arm with a GitHub App token, never `GITHUB_TOKEN` (since PR #62):** GitHub's anti-recursion rule suppresses every downstream workflow (`release.yml`/`ci.yml` `on: push`) for a merge attributed to the default `GITHUB_TOKEN` (`github-actions[bot]`), because native auto-merge attributes the eventual merge push to whoever ENABLED it. A `GITHUB_TOKEN`-armed merge therefore lands on `main` and cuts NO release — the silent-backlog trap that lost 3 sessions (v1.6.0 had to be hand-cut via `workflow_dispatch`). `arm-auto-merge.yml` mints an App token (`actions/create-github-app-token`, secrets `AUTOMERGE_APP_ID`/`AUTOMERGE_APP_PRIVATE_KEY`, App installed with Contents+PRs write) so the merge is the App bot's push, which DOES fire `on: push`. Do NOT revert arming to `GITHUB_TOKEN`. Fail-loud safety: if the App is uninstalled/under-permissioned the mint step goes red and the PR just won't merge — never a silent release miss.

## Fully automatic connection

- **Fully automatic connection** — there are no manual Connect/Disconnect buttons. On mount the frontend calls `connect()` (no `is_connected` probe; that command was dropped) and then retries every `RETRY_MS` (3 s) on a guarded `setInterval` until the device is found, so plugging the TMP in later connects on its own; the interval goes inert once connected. `connect_device` starts the monitor and returns the monitor snapshot's firmware + graph; `listPresets` then resolves from the same snapshot. If no device is present (`connect_device` errors with "no TMP found") the red alert is suppressed and a friendly **"Please connect your Tone Master Pro … it will connect automatically"** banner prompts instead (gated on a one-shot `attempted` flag so it never flashes on first paint); actionable errors (e.g. "close Pro Control") still surface as a red alert, and the header `DeviceStatus` indicator shows `disconnected` (hollow) / `reading firmware…` (amber pulse) / `connected · <fw>` (green, the unit's firmware version). **Connection-loss detection IS implemented**: `watcher.rs` (a non-seizing IOHIDManager) emits `tmp://device-{attached,detached}`; on detach App.tsx flips to disconnected + clears the firmware/snapshot state, and the 3 s retry interval stays armed (no longer cleared on first connect) so a replug auto-reconnects. Calibration from the Settings window is unaffected because every device command releases + re-acquires the seize (`with_released_seize`).
  The full first-connect **handshake is load-bearing** — the device only answers after seeing the captured Pro Control sequence (`connection_request` + preset lists + product profile + current-preset/settings/userir requests). Don't trim it without testing.
