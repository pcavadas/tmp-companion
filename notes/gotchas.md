# Gotchas — the HW evidence behind the rules

The evidence appendix for the repo's always-loaded rules. This file carries each rule's full
statement, the hardware evidence behind it, and the failure it prevents.

Where a rule is stated in more than one place, the split is deliberate:

- **`.claude/rules/danger.md`** — the danger rules in full (data loss, device wedging, machine
  crashes). Always loaded, re-injected after compaction.
- **`CLAUDE.md`** — the traps that fire while _running_ a command rather than editing a file,
  plus a one-line index of the rules below.
- **the OTHER `.claude/rules/*.md`** (every one except `danger.md` above) — path-scoped
  conventions that load only when you edit a file the rule's `paths:` glob matches.
- **This file** — the long form. Where both state a rule, this one is the fuller text; they do
  not contradict.

Read the entry in full before changing the behaviour it governs. Evidence tags name the firmware
the fact was measured or read on; fw 1.8.58 is the support floor.

## Linux hidraw transport: inbound reports carry their own leading `0x00`, and there is no open lockout

- **The leading `0x00` on inbound frames is the DEVICE's byte, not a report-ID artifact of the reading API.** Inbound frames parse as `[0x00, magic, _, body_len, …]` while outbound frames put the magic at index 0 (`proto::make_envelope`). On Linux every report arrives as `n=64` beginning with a literal `0x00`, exactly as on macOS (HW, fw 1.8.58), so `hid.rs`'s Linux `imp` pushes reports **RAW** and `proto.rs` plus its golden vectors stay byte-identical across platforms. Do not add a report-id normalization layer; `hid.rs`'s `a_real_inbound_report_needs_no_report_id_fixup` test pins the measured shape. No filtering is needed at the transport either: `proto::reassemble_streams` already skips anything failing `len >= 4 && data[0] == 0x00`.

- **No open-retry loop on Linux.** There is no device-side open lockout (see the `0xe00002c5` entry below), there is no seize, and nothing competes for the unit (Fender ships no Pro Control for Linux); back-to-back `probe` sessions reconnect at once. A retry loop would only make a genuine error slow to surface. Re-measure before importing any macOS timing constant here.

- **hidraw is NOT exclusive, so exclusivity has to be enforced.** Two `probe` processes launched together both opened the node and both proceeded (HW), where the second would fail `0xe00002c5` on macOS — and interleaved writes from two openers are exactly how a slot gets a wrong-content save. The Linux `imp` therefore takes an advisory `flock(fd, LOCK_EX | LOCK_NB)` immediately after `open` and reports `EWOULDBLOCK` as "already in use by another TMP Companion process". Advisory is sufficient because every path into the device goes through that one function and nothing else on Linux speaks this protocol; the lock releases on close, including on abnormal exit. **Do not remove it believing hidraw is exclusive.**

- **`/dev/hidraw*` is root-only, so first run fails `EACCES` until a udev rule lands.** `packaging/udev/70-fender-tone-master-pro.rules` tags the node `uaccess`, which grants the logged-in user via a POSIX **ACL** (`getfacl` shows `user:<name>:rw-`) rather than a group — verify with `getfacl`, not `ls -l`, since the mode bits still read `crw-------`. `udevadm trigger` re-applies it to an already-connected unit, so **no replug is needed**. The unit enumerates **two** interfaces, `1ed8:0044` and `1ed8:0047`; only `0044` carries this protocol (`hid::PID`), and the rule tags both so the whole device is consistently owned. The device node is found by walking `/sys/class/hidraw/*/device/uevent` for `HID_ID=<bus>:<vid>:<pid>` (zero-padded uppercase hex) — no `udev` crate, no C `hidapi`.

## Linux ALSA re-amp audio: the TMP's `hw:` interface is I32-only, on the OPPOSITE USB product id from HID, and PipeWire will fight you for it

- **The TMP's audio interface is USB id `1ed8:0047` — NOT `0044`, which is HID's id.** `/proc/asound/cardN/usbid` shows `0044` as a MIDI-only card (no PCM device) and `0047` as the real 4-in/4-out USB-audio-class card. `audio.rs`'s Linux `find_device` resolves by walking `/proc/asound` for the Fender-vendor (`0x1ed8`) card that has a `pcm*` entry, not by a specific product id.

- **`hw:CARD=<id>,DEV=0` is `S32_LE` (I32) ONLY — no F32 at any channel count** (HW, fw 1.8.58: `aplay --dump-hw-params` and cpal's `SupportedStreamConfigRange` agree: `FORMAT: S32_LE`, `CHANNELS: 4`, `RATE: [44100 96000]`). `audio.rs`'s `pick_config` accepts I32 as a fallback, converting to/from f32 at the stream-callback boundary with `dasp_sample`'s exact `2^31` scaling (`f32_to_i32`/`i32_to_f32`) — a different scale factor (e.g. `i32::MAX`) would silently mis-calibrate every LUFS reading captured over this path.

- **`plughw:` is NOT a safe substitute for `hw:`, despite offering F32.** `plughw:` reports channels `1..64` (ALSA's `plug` layer converts channel COUNT as well as format), so `pick_config`'s "smallest channel count that fits ≥3" would get exactly 3 channels through `plug`'s own unverified remix, not the 1:1 mapping `REAMP_INSTRUMENT_OUT_CH` depends on for USB-In-3 routing. `hw:` only advertises the physical channel count. Chosen for that risk, not measured broken.

- **Resolve the device by ALSA pcm_id, never by name.** cpal's Linux enumeration lists a non-functional `usbstream:CARD=Pro` hint named `"Tone Master Pro"` (0 channels) ahead of the real `"Tone Master Pro, USB Audio"` PCM, so a name-substring match picks the hint. `find_device`'s Linux `imp` matches the exact pcm_id (`description().driver()`, e.g. `hw:CARD=Pro_1,DEV=0`) against the vendor-id-resolved card. Likewise `audio::enumerate()` keys its device map on `(name, driver)`: several ALSA PCMs share one display name, and merging by name alone unions their ranges into a device that does not exist.

- **PipeWire/WirePlumber holds the TMP's PCM persistently, and that blocks `hw:`'s exclusive open with `EBUSY`** (`fuser /dev/snd/*` shows `wireplumber` on `pcmC4D0p` with nothing streaming). The fix is a WirePlumber rule (`~/.config/wireplumber/wireplumber.conf.d/`) matching `device.vendor.id = "0x1ed8"` + `device.product.id = "0x0047"` with `update-props = { device.disabled = true }` — see `CONTRIBUTING.md`'s "Developing on Linux". It is machine-level config outside the app's control; `audio.rs`'s `stream_error` appends the rule to the busy stream-build failure so the error names its own fix (as `hid.rs` turns `EACCES` into the `udevadm` commands).

- **HW-validated end to end (fw 1.8.58):** `probe --measure-current` (repeatable across runs), `probe --levelpreset` (full measure → solve → apply, pre-measurement state restored) and `probe --doctor` (a real, non-degenerate spectral profile) all run on Linux, with the `danger.md` re-amp rules holding unchanged.

## Windows: Win32 HID reports carry a report-id byte BOTH ways, WASAPI shared mode is capped by the Sound-panel default format, and three test-harness traps that only fire on this platform

- **The descriptor declares 65-byte reports in AND out (HW, `HidP_GetCaps`).** Windows carries the report ID as a leading byte in both directions and insists every `WriteFile`/`ReadFile` buffer is exactly `OutputReportByteLength` / `InputReportByteLength`. So the 63-byte outbound frame is written as `0x00` + frame, zero-padded to 65; the inbound 65 is `0x00` report id + the device's own 64-byte report — whose first byte is ALSO `0x00` (the Linux entry above). The Windows `imp` strips exactly ONE leading byte, keyed on the descriptor length rather than the value, so reports reach `proto.rs` byte-identical to macOS/Linux. **Do not "fix" the double zero by stripping two.**

- **`CreateFileW` with share mode 0 is the seize.** Against a running Pro Control the open fails `ERROR_SHARING_VIOLATION` (os error 32), surfaced with the "close Pro Control" hint, and nothing wedges (HW). Pro Control ships for Windows, so contention is a first-class user-facing path here.

- **WASAPI shared mode offers ONLY the endpoint's Windows default format.** With Fender's Thesycon driver installed the unit enumerates as `Speakers (Fender Tone Master Pro)` = **2 channels** at 16 rates and `Line (Fender Tone Master Pro)` = 4 channels at **44100 Hz only** (`probe --audio-devices`). Those are the Sound-control-panel settings, not the hardware, and cpal 0.18 has no exclusive-mode path, so re-amp (output channel 3 at 48 kHz) fails until the user sets _Quadraphonic_ + 48000 Hz on the output and a 4-ch/48000 default on the input. `audio::host_config_hint` names the fix in the error; `CONTRIBUTING.md` carries the click path. The class-driver `Tone Master Pro` (`PID_0044`) endpoint disappears once the Thesycon driver binds `PID_0047`.

- **A Rust unit-test executable has no application manifest, and `tauri/test`'s MockRuntime imports comctl32 v6.** Without one the `--features e2e` lane dies at process load with `STATUS_ENTRYPOINT_NOT_FOUND` (`TaskDialogIndirect`) before one test runs — `cargo test` reports only "test failed", no `test result:` line. tauri-build embeds a manifest for app binaries only, and `cargo::rustc-link-arg-tests` covers integration-test targets, not the lib harness. `build.rs` therefore passes `/MANIFEST:EMBED /MANIFESTINPUT:tests.manifest` to every target and cancels it on bins with a later `/MANIFEST:NO` (link.exe keeps the last one; a second manifest on the bins is `LNK1123`).

- **Tauri's local IPC origin is `http://tauri.localhost` on Windows, not `tauri://localhost`.** With the macOS/Linux form hard-coded, the ACL judges every bridged invoke a REMOTE origin and the `e2e_server_spike` tests fail with "`<cmd>` not allowed. Plugin not found" — an error that reads like a missing capability, not a wrong URL. `e2e_server::local_app_url` is the one place that knows the platform form.

- **Shared-mode WASAPI applies the Windows endpoint volume to the re-amp inject and capture.** With the "Speakers (Fender Tone Master Pro)" slider at 8 % (−38 dB), a clean scene measured −34.6 LUFS through the inject while the same dry level played live read −14.3; driven scenes hid the loss behind their own compression (HW). `audio::endpoint_volume` HOLDS the unit's own endpoints (matched by name, never the user's speakers) at 100 %/unmuted for each re-amp session and restores the previous values on drop, with a WARN whenever it changed something. Pinning 100 % permanently is wrong: the same slider can be what keeps a Windows monitoring loop ("Listen to this device", a DAW echo) quiet, and a pinned version audibly doubled the user's live guitar. macOS/Linux have no such layer. The unit's physical MASTER knob does NOT scale the USB 1/2 tap (−23.8 LUFS at zero, −23.6 up; HW), so "quiet leveling" is: master down on the unit, and the app handles the Windows slider itself.

- **Three smaller Windows shapes:** `profiles::save_to_path`'s parent-directory fsync is `cfg(unix)` (Windows refuses opening a directory as a file, `ERROR_ACCESS_DENIED`); `probe_api::stimulus::dump_processed_capture` must not join paths with a literal `/`; and SQLite access is in-process `rusqlite` on every platform (there is no `sqlite3` CLI on Windows).

## A batched scene-leveling save can revert the ONE scene it just leveled, if that scene is also `restore_scene` — a pre-existing, platform-agnostic bug, not a Linux-audio defect

- **What happens.** `level_scenes_oneshot`'s final save (`save_deferred_scene_writes` → `recall_reassert_save` → `recall_original_scene`) recalls `restore_scene` (the preset's on-load scene) right before `saveCurrentPreset`. When that scene is the one the batch just levelled, the save has stored the scene's OLD value: `probe --level-scenes 404 -17 guitar-humbucker 0 --commit` on the "E2E Hiwatt 3S" scenario preset (stored `lastLoadedScene` 0) solved scene 0's `outputLevel` to 1.0 and saved 0.96, twice, byte-identical (HW, fw 1.8.58). The solve is correct; only the persisted value is wrong.
- **Not silent.** `persist_mismatches` / `verify_persisted_writes` stamp `persist_mismatch` on the outcome, and the online re-measure of the saved state reads it as a miss.
- **Mechanism unresolved.** Under MAINTAIN CHANGES a recall — a re-recall of the active scene included — keeps that scene's unsaved edits (static RE, fw 1.8.58). Two causes fit: the unit was set to DISCARD CHANGES, where every `loadScene` rebuilds base and every overlay from the stored preset (the probe path skips the app's up-front `SkipKind::SceneChangeDiscards` refusal); or the write's overlay entry had one key, so it landed on base and the recall re-applied the overlay's old value (see the Scene-Edit entry below). A post-save `presetDataRequest` (field 8) read separates them: under the second, base holds 1.0 next to the overlay's 0.96 (open: notes/open-questions.md).
- **A fix must cover three save paths.** `recall_original_scene` is shared by `apply_levels`, `save_deferred_scene_writes` and `write_fs_values_on_session`; `recall_reassert_save` already re-applies `presetLevel` after the recall, and nothing re-applies a per-scene block write.

## LIVE per-node structural edits (the protocol behind the block-edit features)

- **The ops.** `copy_apply` (the Copy tab — an ordered replace/insert/remove op list PER target preset, from `copyModel.diffToOps`) drives `session::{replace_node,insert_node,remove_node}` on ONE held session re-armed per preset: `replaceNode` (39) for a stock model; `replaceNodeWithBlock` (100, + library index) for a user saved block or dual cab; `replaceNode` → `ACD_UserIRTMS` + a string `changeParameter` on the node's `file` param for a user IR; `removeNode` (35); `insertNode` (34) — sent BARE (no `nodeJsonRequest` preamble), `groupId` = the group KEY, field 2 = the SAME-group node id to insert BEFORE (omitted = append; an anchor the group lacks aborts the server, see [the abort entry](#an-insert-with-a-missing-anchor-or-over-the-cpu-budget-aborts-the-device-server)). Probe entry points: `probe --insert-active` / `--insert-map`; the probe's replace arms use `replace_many_held`. The palette is firmware-aware (stock models filtered to `since` ≤ connected fw; user IRs and saved blocks are read live).
- **The confirm gate.** Confirm on `nodeReplaced` (40) / `nodeRemoved` (36) / `nodeInserted` (33); **never save on `presetError` (53) or an unconfirmed edit** (a wrong-content save corrupted a real slot). No handler drops a correctly framed structural edit: each confirms or fails loudly, so a missing confirm is one still queued behind the load's pushes, a lapse, a backup freeze or an insert abort (static RE, fw 1.8.58). An unconfirmed edit is read back from the working copy and re-sent only when it visibly did not land, never blindly.
- **Two INVARIANTS for ANY block-mutation code (`audiograph.rs`).** (1) **A block lives in THREE differently-keyed places — touch ALL or leave dangling state:** `audioGraph.{guitarNodes,micNodes}` (the roster: each node carries its model `FenderId` and its instance `nodeId`), `scenes[].<group>.<nodeId>` (per-scene overrides, keyed by the request's INSTANCE id — static RE, fw 1.8.58; not device-checked with two same-model blocks carrying scene edits), `ftsw[i][].nodes[].nodeId` (footswitch assignments, by EXACT nodeId). The firmware mints instance ids per group as the model id, then `_1`, `_2`… (`audiograph::mint_node_id`; HW + static RE, fw 1.8.58), so for duplicate blocks the two keys differ. Miss the scene path → stale inert overrides; miss ftsw → a footswitch ghost-toggles a block that's gone. (2) **Model-level ops (bulk replace, counts) match by EXACT FenderId through `audiograph::Node::matches_model`; instance-level ops (live edits, anchors, overlays, footswitch refs) by `Node::matches_instance`.** The backend never normalizes ids — the CabIR/Convolution suffix-normalization (`resolveDeviceId`, see the amp-id-matching entry below) is FRONTEND-ONLY, so a frontend-normalized id passed into an OpSpec silently fail-matches (no error, no replacement).
- **Saved-block and IR inserts are LIVE-ONLY.** Saved blocks are metadata-only (`blockPresetsMap` = 5 keys, no params; `product_profile.json` carries no default params), so there is no offline payload to reconstruct — don't re-attempt an offline splice.
- **The Copy read-back is a field-2 re-prompt of the working copy taken BEFORE the save — never a buffer scrape.** `read_working_copy` sends `Session::live_preset_value` (`clear_raw` + `currentPresetDataRequest` (field 2, batch 3) + heartbeat-pumped slices) after the last confirmed op and BEFORE the rename/save; the re-prompt answers with the post-edit working copy (HW, `probe --reprompt-map`). The `expected_roster(pre-edit roster, acked ops)` oracle compares per-group MULTISETS (the projected order of chained same-model inserts is unreliable; the adopted read carries the device's real order) and is both the completion predicate (a partial keeps pumping until the roster matches, then the payload must hold still for two slices) and the adoption guard. The verdict line `[copy_apply] slot N: working-copy read …` distinguishes `adopted`, `== the PRE-edit roster` (logged, never blocks the save), `truncated` (fewer nodes), other mismatch, and `no working-copy reply`. An edit the roster cannot see — a same-model re-stamp — is UNVERIFIABLE, so no read is spent and `copy_apply` omits the graph (the backend alone decides adoptability). The read goes through `current_audio_graph`, so a document cut before a complete `template` is refused rather than adopted with a default series shape. Offline, `SimDevice` renders its field-2 reply from a working copy that CONFIRMED structural edits mutate.

## Live setters + import framing (byte-exact from a real Pro Control capture)

- `renameCurrentPreset`(13){displayName=f1} — and a PC rename is **rename(13) + saveCurrentPreset(14){slot=f1}** (save-under-new-name; send both to persist); `moveUserPreset`(16){old=f1,new=f2} (persists alone); `clearUserPreset`(15){slot=f1}; all single-packet no-batch. **Outbound multi-packet framing = `0x33` start / `0x34` continue / `0x35` final**, each `MAGIC 00 LEN ≤60B` (symmetric with inbound). `importPresetRequest`(117){presetJson=f1} where **`presetJson` = LZ4-block(raw `.preset` file bytes)** = LZ4(XOR-encoded compact JSON); Pro Control follows it with `loadPreset`. **A `saveCurrentPreset` chained before a `loadPreset` on the SAME connection is SILENTLY DROPPED** (the load lands, the save doesn't, no `presetError` — HW `probe --save-load-test`; not re-run on fw 1.8.58): a save must end its connection.

## `saveCurrentPreset` is durable when it returns; a same-slot `loadPreset` right after it is a no-op (fw 1.8.58)

- **There is no time-dependent commit.** `presetDataRequest` (field 8), the field 3 of a real reload (load another slot → load the target) and a capture all showed the just-saved value at T+0.5, 2, 10 and 40 s, for a same-slot save and for a save made while another slot was loaded (HW, fw 1.8.58); save, a same-slot load 3.5 s later, an edit and another save read back intact at T+200 s.
- **The one stale path is the same-slot short-circuit.** A same-slot `loadPreset` with the dirty flag clear is a no-op: it keeps the live working copy and DSP (it still pushes field 3, so a push does not prove a reload). After the host's own save those equal the stored row, so nothing is stale; after another writer's save they are. An unsaved `setPresetLevel` sets the dirty flag and makes the same-slot load a real reload of the stored row (~0.3 s); a `changeParameter` and an `insertNode` set it too (below). Otherwise load another slot, then the target (~0.6–1.0 s). Never a time wait.
- **What counts as "same slot" and "an edit" (static RE, fw 1.8.58, unless marked).** The skip compares the load identity (the last loaded slot, or the slot of the last save, even a save to another slot) and the current scene against the stored `lastLoadedScene`; no `preset_id`, name or content. The dirty flag is set by `setPresetLevel`, `changeParameter` (non-empty change list), every `loadScene` and every `removeNode` (even a failed one), `setNodeSceneEdit` outside the base scene, `setFootswitchAssignment`, a successful `clearFootswitchAssignment`, a rename to a new name (a rename to the current name sets nothing) and insert/replace; it is cleared by a real load and by a save. A move sets nothing: a move of the loaded slot only repoints the load identity. SimDevice models these rules, except that it marks every rename dirty (`same_slot_load_tests`).
- **Device-checked dirty setters (HW, fw 1.8.58, 2/2 each; re-check with `probe --restore-check`).** `setPresetLevel`, `changeParameter` (bool `bypass` and float `level`) and an `insertNode` append each read `isDirty=true` afterwards, and a same-slot load then REVERTED the edit in both the field-3 push and a working-copy re-prompt.
- **An import that lands on the CURRENTLY LOADED slot reloads it** (HW, fw 1.8.58, two runs, 3- and 15-block bodies; static RE agrees). The working copy on the import's own connection and on a fresh one carried the imported name, `preset_id` and blocks, so the same-slot short-circuit cannot leave the old working copy over a fresh import. Re-check with `probe --import-reload-check <file.preset>` (it saves nothing and clears the slot only when its stored row and list entry carry the check's own name).
- **Landings are proven from the stored row; never wait on the import echo.** `importPresetResponse` (118) did not arrive within 5 s (HW, fw 1.8.58). An import always lands in the LOWEST empty user slot (static RE + HW, fw 1.8.58), so every caller predicts that slot and requires its field-8 row to be the empty template before the import and the file's `preset_id` and name after it (`replace_inplace::StoredProof`). A stored row cannot show a body rejected at LOAD, so a caller that saves after the import also runs `load_and_prove`.
- **`isDirty` is readable, but slowly.** `currentPresetInfoChanged` (field 22) carries it (`Session::active_preset_dirty`). A lean handshake carries no field 22, and a `currentPresetInfoRequest` is answered a fixed ~1.1 s later (HW, 10/10, with or without a `connectionRequest`) — dearer than the reload it would save.
- **Enforcement.** `leveller::restore_saved_preset` always loads a neighbour slot, then the target: 1.67 s against the bare load's 1.33 s (HW, 5 each), and it holds even when the flag is clear over a stale working copy (another writer, a lost DSP result). `make_current` stays a bare load: its harvest callers only need the target current. Gated by `restore_loads_a_neighbour_before_the_target`.
- **The field-9 carrier trap.** `Session::latest_json_payload` takes the LATEST harvested carrier, and `(9,3)` is the field-9 `presetDataChanged` reply to a field-8 read — so on a session that has issued one, the "current" document can be the STORED row rather than the working copy. `raw.clear()` before a harvest that must see the working copy (`session/tests.rs::latest_json_payload_from_reports_takes_a_later_field9_reply`).

## Slot addressing: device userSlot = list index + 1

- **HW-confirmed.** `list_my_presets` is 0-based; the slot-addressed setters (`loadPreset.presetSlot`, `saveCurrentPreset.userSlot`, `clearUserPreset`, `moveUserPreset`) and the Song read's `userPresetSlot` are all **1-based**. `session/preset.rs` owns this translation (`load_preset`/`save_current_preset`/`clear_user_preset`/`move_user_preset` take a **0-based list index** and send `+1`); callers pass list indices. The list's empty-slot marker is **`--`** (also "Empty"). `requestNextEmptyPresetSlot` (81) is answered by a broadcast field 82 (−1 when the library is full) (static RE, fw 1.8.58); the app does not use it, because an import always lands in the lowest empty slot. Song reads ride the handshake burst with batch 3 (`song_io.rs`). **In-place edit + Song links:** overwriting a song-bound slot with a _different-identity_ preset empties the Song row — link-safe editing must preserve `info.preset_id` + scene structure (LIVE `changeParameter`+save, or identity-preserving OFFLINE re-import). See `notes/write-safety.md`.

## The first connection after a load can echo the slot loaded BEFORE it (fw 1.8.58, HW)

- **The symptom (HW, fw 1.8.58).** `load_and_prove` loaded an import's scratch landing on one connection and opened another to confirm it; that connection's `PresetLoaded` echo named the slot loaded before, so the confirm refused (`slot echo Some(10)`) and left the scratch behind, although a later `probe --active-slot` showed the load had landed. A second stale echo came 1.25 s after another load; one 50 s later was right.
- **Not the name, not a dropped load, not a list misread.** The echo is identity, so `Session::active_matches` lets a disagreeing echo win over a matching name. That is right and stays: a unique name would have been refused the same way.
- **Likely cause (cause unresolved):** the inherited reply queue ([a session opened within 0.75 s of the last one inherits its reply queue](#a-session-opened-within-075-s-of-the-last-one-inherits-the-rest-of-its-reply-queue-ahead-of-its-own-replies-fw-1858-hw)). The load's connection closed inside the unit's 0.75 s drop, so the confirm's connection received that queue ahead of its own replies.
- **The fix:** every load → reconnect → confirm path ends the load's connection with `Session::lapse` (as `load_preset_isolated` does), and confirms through `Session::connect_confirmed`, which lapses a refused connection and retries on a fresh one, three in all. The echo still decides every attempt. A save-over refused anyway takes its scratch back off the unit only after the stored row re-proves the landing (`replace_inplace::rollback_scratch`), never by name: the scratch, the original and any older leftover share a name and `preset_id`. Gate: `session::tests::{a_stale_load_echo_is_retried_on_a_fresh_connection, an_echo_that_keeps_naming_another_slot_still_refuses}`.

## A preset-list read on a session that just streamed a large preset body comes back SHORT — and an empty name makes the backup fallback refuse

- **`list_my_presets()` issued on the SAME session that has just completed a large field-8 preset read can come back without the slot you are asking about.** `slot_read::read_slot_preset_sections` needs the occupant's NAME only to guard the backup fallback's slot mapping, and `read_slot_preset_complete` REFUSES outright when that name is empty: _"the preset list did not answer with the slot's name, so a backup re-read cannot be addressed safely."_ To the user that read as "Couldn't read this preset's controls" on a preset that was fine (HW).
- **The name never comes from a same-session list read.** The chain is `monitor::startup_preset_name` (the startup snapshot the UI shows — no device I/O, no device lock) → the partial's own `info.displayName` (a cut in `scenes` spares `info`) → a list read on a FRESH session. A name is identity, not freshness: the snapshot is refreshed on connect.
- **Diagnostic tell:** the error names the SECTION that was cut (`its scenes section(s) were cut off`) AND blames the list read in the same sentence. Two different failures wearing one message — check whether the backup itself was reachable before concluding the preset is too large.

## A device backup is bounded by a STALL budget, not a whole-transfer cap

- **The backup stream is device-paced at ~28 KB/s (one report per 2.14 ms) whatever the library holds, and the archive is mostly `acdDefaultsBackup` plus the user's IR files, not presets** (HW, fw 1.8.58). A whole-transfer cap cuts a large archive on every caller — the startup library read and the truncated-scene repair included. `Session::device_backup`'s `max_secs` bounds the time between progress events (chunk, state change, build tick), so leave the callers' 60 and do not reintroduce a wall-clock cap.

## Address spaces: `read_library_via_backup` reports the 1-BASED device slot, the leveling commands take the 0-BASED list index

- **A guard that compares the two raw checks the NEIGHBOUR preset.** `read_library_via_backup`'s rows carry `.slot` as the **device** slot (what the UI shows, what `preset_json_from_backup` addresses by), while `level_preset` / `level_scenes_apply_batched` / `level_footswitches_apply` all take the **0-based list index** — the same index the app logs as `slot=26`. They differ by one, in the same direction as every other pair in this codebase (see the slot-addressing entry above). Put the guard in the SAME address space as the mutation (`danger.md`): a guard in device space over a write in index space verifies one preset and then levels another.

## The scene-context rule: a bare write/measure with no preceding `loadScene` lands in whatever scene the connection currently holds, never base by default

- A preset loads into its SAVED `lastLoadedScene`, and a bare write then lands in that scene's context, not base's (static RE + HW; where it is recorded is the Scene-Edit entry below). Every base-context write or measure must therefore explicitly recall base (`session::BASE_SCENE_SLOT`) first, hoisted to the top of its connection before that connection's first write: under DISCARD CHANGES a later recall discards the write, and a base re-recall reverts an unsaved `presetLevel`. `leveller`'s `capture_full_at`/`set_knob`/`set_knobs`/`write_footswitch_values` and `commands/doctor.rs`'s `apply_ops_under_scene` all do this; `SimDevice` models the same `lastLoadedScene` behavior offline (`sim_device.rs`) so the omission is gate-catchable.

## The Scene-Edit flag state decides where an enable-less scene write lands — not whether the overlay carries the param

- **The device rule (static RE, fw 1.8.58; not device-checked).** The Scene-Edit state IS the overlay's shape: an entry with more than one key is ON; a one-key entry (a `{bypass}`-only overlay) or no entry is OFF. A scene-context `changeParameter` with no `setNodeSceneEdit` lands in the overlay when the param is `bypass` on an existing entry, or when the entry has more than one key (insert-or-assign: a Full overlay that lacks the param gains it, its siblings survive and base is untouched — HW). Otherwise it lands on BASE, so the write changes every scene that shares the node's knobs (HW: a write against a `{bypass}`-only overlay moved base gain 2.5 → 7.0). Enabling Scene Edit reseeds the overlay from base; disabling shrinks it to `{bypass}`.
- **The app's classifier uses a different threshold.** `scene_jobs::scene_overlay` (`SceneOverlay::{Full,BypassOnly,Absent,Unknown}`) calls an overlay OFF when every key is in the bypass family (`BYPASS_ONLY_KEYS`), not when it has one key, so a `{bypass, bypassType}` overlay and a one-key `{outputLevel}` overlay classify opposite to the device rule. `leveller::set_knobs`' per-node write-shape decision and `SimDevice` follow the classifier (open: notes/open-questions.md).

## Scene leveling is ONE-SHOT open-loop on the active amp's `outputLevel`

- **The app command `level_scenes_apply_batched` calls `leveller::level_scenes_oneshot`**: measure each scene AS-IS via an ISOLATED fresh re-amp capture → `solve_level` → `apply_level`, a bounded secant correction that always lands the best point. Hard rules: level Base via `presetLevel` FIRST (a GLOBAL multiplier over ALL scenes — never raise it to boost a quiet scene); change ONLY the amp `outputLevel` (preamp/master/volume forbidden; the exact param allowlist + the `ACD_TMRumbleV3` nuance live in `notes/leveling.md`).
- **Enabling Scene Edit is not itself harmless.** `set_node_scene_edit(node, true)` reseeds that node's ENTIRE scene overlay from base, silently wiping any other already-scene-edited param on it. So the enable is sent ONLY for a node with NO overlay in the target scene, where the reseed has nothing to lose — `set_knobs` reads that per-node state from the run's ONE field-8 read (`scene_jobs::scene_overlay`) and REFUSES the write when the answer is unknown (truncated read / no read), since the alternative is corruption.
- **Write QUICKLY.** A write after 750 ms of host OUT silence is dropped — no `presetError`, nothing persists (HW, fw 1.8.58). Every pre-write gap stays ≤300 ms (`SETTLE_AFTER_SCENE_RECALL_MS`=150 + `SETTLE_AFTER_SCENE_EDIT_MS`=300, the latter slept ONLY when an enable was actually sent), plus a ONE-shot dropped-write retry (`apply_first_verified`: a ≥2 dB intended move reading back ~flat re-applies once before any clamp verdict). A ≥6 dB knob change that doesn't move the USB 1/2 capture is an honest `no_authority` off-branch clamp, never a success.
- **Knob picks are resolved before any engage.** For the scene already active (the saved `lastLoadedScene`), the pre-pass reads the post-load document instead of recalling it, because a recall that changes nothing pushes no field 3 and would leave that scene unclassifiable (field 3 and `sceneLoaded` (102) are pushed only on a scene change; static RE, fw 1.8.58). The pre-pass is also the runners' preset load: `level_scenes_oneshot`/`level_scenes_rebalance` never re-load the preset, and the UI batches adjacent same-preset scene rows sharing instrument + target into ONE `level_scenes_apply_batched` call.
- **ONE save per preset.** Scene writes accumulate UNSAVED (`LevelOptions.defer`) and the runner saves ONCE at batch end (`save_deferred_scene_writes`: recall the pre-pass's original `lastLoadedScene` first so the save stamps the pre-run base/scene/FS state, save on a clean never-re-amped connection, retry once; also fired on cancel). Under MAINTAIN CHANGES unsaved scene-edit writes survive scene recalls and reconnects, and one save persists all accumulated overlays (HW `probe --defer-scenes`; static RE). Footswitches mirror it (`write_footswitch_values`: measure every switch first, then ALL confirm-gated writes on ONE live-edit session + ONE save; any unconfirmed write aborts before the save; the UI batches a preset's adjacent FS rows into one `level_footswitches_apply` call). A scene that can't reach target clamps honestly ("clamped at <LUFS>"). The scene verify capture stays: it is also the correction-pass trigger and the leak-to-base detector. The closed-loop **BatchedLive** harness (`level_scenes_live_batched`, kept only for `probe --bench-scene-leveling`) MIS-MEASURES on its shared stream — mechanics in `notes/leveling.md`.

## `outputLevel`=0 is DEEP DIGITAL SILENCE on the real TMP, and the leveling measurement ERRORS ("no signal captured") on a silent capture

- **A finite LUFS isn't recoverable from silence.** So a both-lanes-muted rebalance floor (`probe --mute-floor`) reads as silence (the IDEAL mute, no bleed → trustworthy equal-solo balance), and any code that measures a deliberately-muted state must treat the "no signal captured" error as a sentinel deep floor (`leveller::MUTE_FLOOR_SILENT_LUFS`), NOT propagate it — else it aborts the scene. Corollary for off-branch detection: a `gtrSplit` amp can sit in the PRE-SPLIT TRUNK, so it always reaches USB 1/2 and never trips the no-authority clamp — the off-branch positive case is unit-tested, not HW-reproduced.

## Re-amp engages reliably only ONCE per connection

- **Re-engaging on a held connection is safe on fw 1.8.58, but only the FIRST capture per engage is accurate (HW, attended).** In one 17-min session heartbeated every 200 ms (10 runs, 4 re-engages, 5 ON→OFF toggles) every engage applied, with no wedge and no USB or Mac fault (static RE: the engage path is three byte stores, no ALSA or USB code). The first capture after an engage read within 0.04 LU of an isolated capture; later captures on one engage read 0.00–0.29 LU low, worse the longer re-amp sits engaged without stimulus; a re-engage per capture reads 0.06–0.09 LU low. So the app keeps one engage per capture on a fresh connection, for accuracy.
- **The `ReAmpModeChanged` echo is NOT proof of engagement** — a finite captured loudness is; read the real state with Mixer `reAmpModeRequest` (4). Only the measurement PREPASS reconnects (one engage per scene); the leveling APPLY (`presetLevel` + per-scene `outputLevel` + save, all pure sends) runs on ONE persistent session.

## A silent/failed re-amp inject reads as the device's STATIONARY OUTPUT FLOOR, and `measure_c` would accept it as a valid `C` without the production floor guards below

- In a rapid 20-engage `probe --stim-ab` sweep, 19/20 captures measured the post-DSP floor, not the stimulus. The tell: `dynamic_spread_lu ≈ 0.01` (a plucked stimulus through ANY chain shows spread ≫ 0) + a preset-INDEPENDENT `C` (identical across very different presets). The floor is post-DSP, so `presetLevel` scales it and the `20·log10` C-model still "holds": a full `--levelpreset` solve+verify landed 0.00 LU error while measuring ONLY the floor — **solve/verify self-consistency does NOT prove inject health**. The production leveller guards every measurement (`leveller::measure_floor_guarded`/`require_live`: `FLOOR_TRIP_LU` = 0.4 on the 400 ms momentary-loudness spread, a stimulus-aware disarm for near-stationary EBow captures, and a quiet-gap retry; a still-flat read is refused). `probe --stim-ab` stays the diagnostic sweep.
- **The DISTINCT deep-silence class (`"no signal captured"`, peak ≈ −93 dBFS) is a silently DROPPED re-amp engage — never a wedged device, and a power-cycle is NEVER the cure** (HW; mechanics in `notes/leveling.md`).

## A stuck re-amp survives a USB unplug — restarting the unit clears it (fw 1.8.58, static)

- **What the user hears:** re-amp REPLACES Inputs 1 and 2 with the USB re-amp feed, so a unit left re-amp-ON plays no guitar — the run's "input-muted" is literally the instrument input being unheard. That is the state a run-end OFF that never reads back OFF leaves behind (`leveller::reamp_off_guaranteed`, its ladder exhausted).
- **A USB unplug/replug does NOT clear it; a restart does.** Nothing on the unit resets re-amp when a connection closes, and the firmware forces it off at boot (static RE, fw 1.8.58). So the user-facing recovery is "Restart your Tone Master Pro" — `leveller::REAMP_STILL_ON_WARNING`'s text and the Summary's wording — and the developer recovery stays `cargo run --bin probe -- --reamp-off`, which sends the Settings OFF without a restart.
- **The frontend reads the TYPED flag, never the text:** every leveling result carries `reamp_still_on` (and a failed leveling command's typed error `reampStillOn`) beside the `reamp_warning` text, which is for the log and the bug report. A batched command returns the verdict beside its rows (`reampStillOn`), so a batch that returns no rows still carries it.
- **Not yet checked on a unit** (static RE, fw 1.8.58): leave re-amp ON, unplug and replug the USB cable and confirm the guitar is still unheard; restart the unit and confirm it is back (open: notes/open-questions.md).

## Amp-id matching must be CHECK-FIRST then strip (CabIR/ConvRvb)

- A discovered amp block can carry merged cab/IR/convolution suffixes the catalog's bare bid lacks (e.g. `ACD_HiwattDR103CanModCabIR` → strip `CabIR` → `ACD_HiwattDR103CanMod`), so an amp+cab combo silently SKIPS FS scenes (HW). This also covers the ~6 catalogued-`NoFx` reverb amps for per-scene-leveling amp detection.

## 48 kHz stimulus required

- **48 kHz is a host and app convention, not a device requirement.** The stimulus WAVs are 48 kHz, and `audio.rs`'s `pick_config` opens both streams at the stimulus rate; on Windows, shared mode additionally needs both endpoints' default format at 48000 Hz (`host_config_hint`).
- **The device runs a fixed 44.1 kHz.** The global `sampleRate` setting is only stored and echoed; it reaches no audio path. The DSP and its I²S run at 44.1 kHz, and the USB side converts the host rate (44.1/48/88.2/96 kHz) to and from it with a fixed-ratio synchronous SRC, pitch-exact and slip-free at all four rates (static RE + HW, fw 1.8.58). So capture content above ~22.05 kHz is anti-alias skirt, not preset tone (HW: flat-noise captures collapse to the float floor above it on presets of opposite spectral tilt) — relevant to spectrum/EQ-match/Doctor-PSD work.
- **Global settings** (`sampleRate`, the mixer strips, `sceneChangeBehavior`) are readable from the backup's `settingsBackup` JSON, and live over the Settings and Mixer reads in `notes/protocol.md`. No write route for the master level is known.

## Output Assign is per-preset and is applied to the global mixer on every preset LOAD

- Loading a preset overwrites the unit's output-assign matrix from that preset's `outputMixerSettings` (`USB12Input→usb12Active`, `instrumentOutput→instrumentActive`, `comboOutput→micActive`; all 9 cells verified, HW). **The measurement tap's routing is therefore NOT stable across a batch** — a leveling pre-flight that checks mixer routing must re-check it **per preset**, not once at startup. The master volume knob is NOT in the USB 1/2 path (0.001 LU across 50 %→80 %); the USB 1/2 channel _fader_ is (−6.48 LU at its −10 dB mark).

## The leveling capture WINDOW (6 s stimulus + 0.8 s tail) is LOAD-BEARING — trimming it is a ≤0.3 LU re-baseline, not a free speedup (HW-A/B'd, `probe --measure-adaptive`)

- TMP presets are NOT stationary under gated-integrated LUFS: time-effect/reverb presets have a quiet delay/reverb BUILDUP at the start AND a decay TAIL the full capture integrates, so early-exit, tail-drop, OR a preroll-skip each shift the measured loudness preset-dependently (clean +0.30 / delay +0.16 / reverb −0.02 LU; saving 2.4–4.7 s). Do NOT re-attempt the "obvious" capture-shortening optimization as a drop-in. The adaptive early-exit capture exists but is OPT-IN only (`audio::MeasureOpts::adaptive`); the leveling default is `MeasureOpts::full`. **Validate any measurement change against the full-capture oracle (`probe --measure-adaptive` / `--measure-prefix-sweep`), NOT a level→verify round-trip that uses the same method — that's self-consistent and HIDES the offset.** Adopting adaptive is a product decision (re-baseline). **Noise floor:** HW LUFS varies ~0.12 LU run-to-run on these non-stationary presets, so an apparent offset across a handful of samples is almost always noise. Only conclude a bias from a many-sample A/B against the oracle, never from 2–3 captures.

## Dialogs/overlays go through the ONE DS `Dialog` (`ui/Dialog.tsx`) — never roll a per-view `position:absolute` scrim

- An `absolute, inset:0` backdrop resolves against the nearest positioned ancestor (the view body BELOW the toolbar), so it fails to cover the menu AND the flex-centered card gets pushed off a too-tall parent and CROPS. `Dialog`'s backdrop is `position:fixed` (viewport) + the card is `maxHeight: calc(100vh-32px)` with `DialogBody` owning the scroll, so it dims the whole window and scrolls instead of clipping. Anchored dropdowns/context menus use the ONE `ui/Menu` (Scrim + anchored card; fill with `MenuItem`/`MenuDivider`); search/filter fields use `SearchInput`. The DS owns chrome (DialogHeader/Body/Footer padding via `DIALOG_PAD_X`) — callers never hand-set per-dialog padding, and widths are the `sm`/`md` size scale, never raw px.

## `connect_device` releases any old HID seize before enabling the monitor

- It does not acquire a UI-owned session; it clears `AppState.session`, sets `MONITOR_ENABLED`, and waits for the monitor's startup snapshot. Acquiring before releasing collides with a stale handle → `kIOReturnExclusiveAccess` (`0xe00002c5`), mis-surfaced as "close Pro Control" even when PC is closed. **The same `0xe00002c5` also fires on CONCURRENT device commands** — the TMP is single-connection exclusive-HID, so firing two device-touching commands at once (e.g. `Promise.all([listSongs(), readSetlists()])`) collides; every device read/write must be **serialized**. Front-end serialization alone is insufficient — `with_released_seize`'s release→work→reconnect churn lets two _operations_ overlap across a tab switch because `AppState.session`'s `Mutex<Option<Session>>` only guards the slot, not the whole open→work→close→reconnect lifecycle. So it is enforced by a process-global **`DEVICE_OP_LOCK`** (`device_gate.rs`) acquired inside every device command's `spawn_blocking`; a bounded `IOHIDDeviceOpen` retry in `hid.rs` covers the residual intra-operation kernel-release lag; there is no `disconnect_device` command (a sync command can't hold the gate without stalling the main thread).

## `0xe00002c5` means another handle holds the seize — the "open-lockout model" was a host-side misdiagnosis

- **There is no device-side open lockout.** One long-lived process opened, used and closed the unit 1,060 times at 0 ms–3 s gaps (200/200 at 0 ms), and again after a 42.6-min idle — every open succeeded first try, zero `0xe00002c5` (HW, fw 1.8.58). A stale macOS IOHIDDevice reference can keep failing `0xe00002c5` while a fresh enumeration succeeds at once.
- **The real hazards are all one exclusive seize.** `0xe00002c5` appears only while another handle holds it — Pro Control, or a second `Session` in the same process — and clears the moment that handle closes; a failed open arms nothing. `Hid::open`'s error names any other handle in the process still live.
- **The code reflects this.** Sessions reopen with no fixed gap (the UI's drop-then-reopen waits on `hid::wait_released`); `hid.rs` retries the same ref 6×80 ms, then re-enumerates 3×400 ms (`ENUM_RETRY_DELAY_MS`); `scripts/e2e.sh` has no rests (a failed seed retries after 2 s).
- **Diagnosing `0xe00002c5`, in this order.** (1) **Believe the error text first** — Pro Control genuinely holding the device is the most common cause, and "PC connects and drives the unit flawlessly" is NOT evidence against it (PC working while our exclusive open fails is exactly what PC-holds-the-seize looks like). (2) **An overlapping `Session` in this process** — read `Hid::open`'s error, which names it. A plain `probe` list succeeding proves the device is free and healthy — reach for it before any heavier theory. (3) A strict list failing on back-to-back lean sessions is not a device fault; a plain probe list proves the unit healthy. There is no "congested state needing a power-cycle".
- **Teardown.** Unschedule from the run loop before `IOHIDDeviceClose` (spec order), and do NOT add a "drain until quiet" pump before close. A `probe` invocation that HANGS pre-output with ZERO lines printed (`hid.rs` `rx.recv()` has no timeout) is a wedged connect, not a solver loop; kill it and retry once.
- **Corollaries.** Seed/sweep/in-place-write list reads are TOLERANT + a completeness floor (never `list_my_presets_strict`, which stays correct only for the snapshot/monitor paths); the online e2e seeds via a fresh `probe --seed-scenario` process BEFORE the server starts, so the server's handshake snapshots the seeded presets (see `scripts/e2e.sh`).

## The device drops the HID client after 0.75 s with no inbound frame — and discards the reply in flight (fw 1.8.58, static RE + HW A/B)

- **The rule (static RE + HW, fw 1.8.58).** The unit closes the HID client once 0.75 s pass with no report from the host, and resets its HID send queue: the message being framed AND every queued reply are dropped. Every OUT report refreshes the timer — a `ConnectionHeartbeat` does, without queueing a reply. On a closed client every message except a `connectionRequest` draws `connectionError` and is dropped; a `connectionRequest` on an OPEN client draws `connectionError` (1) and is not dispatched. An engage 740 ms after the last OUT report applied; at 760 ms it was dropped (HW, 2 runs each).
- **Replies never interleave frame by frame:** one thread frames one whole queued message at a time, so a host-side cut is a DROP, not a reassembly race. Treat a stream without its final `0x35` frame as incomplete.
- **Kept alive, reads come back whole (HW, fw 1.8.58).** A kept-alive `presetDataRequest` (field 8) returns the whole stored row — no cap below the 65,535-byte message limit — with its final `0x35`; a lapse cuts it, and its keys are emitted sorted, so `scenes` is lost first. `currentPresetDataChanged` (field 3) is the whole working copy as one LZ4 block; a lapse mid-stream loses the tail, and the lenient `proto::lz4_block_decompress` yields a prefix, so readers still detect a cut. Settings and Mixer reads, `probe --activegraph` (field 78) and the factory list also answer whole on a kept-alive session, where silent waits had cut or lost them. `exportPresetRequest` (115) is answered with `exportPresetResponse` (116): the slot JSON encrypted, then LZ4 — complete but opaque (static RE, fw 1.8.58).
- **List harvests heartbeat until the list is proven**, then pause past the timeout so callers get the lapsed session they expect. `list_my_presets_strict` (the monitor's startup-snapshot read) heartbeats in its waits too, with no lapse — the monitor keeps that session live.
- **The mechanism in code:** `TrackedHid` (`session/link.rs`) tracks host silence; reply waits use `pump_collect_alive` / `pump_until_stable`; `TrackedHid` re-opens with a `connectionRequest` before a write after ≥600 ms of silence (off only via `set_auto_reopen(false)` in the slot-read experiments); deliberate silence is `pump_silent` / `drain_until_quiet` / `lapse`. The same-address-space guards in front of every destructive write stay required.

## A session opened within 0.75 s of the last one inherits the rest of its reply queue, ahead of its own replies (fw 1.8.58, HW)

- The unit keeps sending its reply queue at its normal frame cadence (~0.48 reports/ms, one per ~2.1 ms) whether or not a host has the HID open. Reports sent while nothing is open are lost; what is still queued when the next session opens arrives on that session FIRST, ahead of the replies to its own requests. Once host OUT silence reaches the 0.75 s drop (entry above), the unit discards the queue and the next session gets a clean flood.
- **HW, fw 1.8.58:** a session closed right after its lean handshake sends and reopened after a gap G lost ≈ 1 + 0.48×G ms of reports as one contiguous run, and the old flood's tail — its field-3 copy included — arrived before the new session's own connection reply. A gap of ≥0.75 s gives a clean flood.
- **What it breaks:** a reader that keeps the LONGEST carrier adopts the stale inherited copy (a restore's field-3 copy of the DIRTY working copy shadowed the restored one).
- **The fix, both halves:** `leveller::restore_saved_preset` and `load_preset_isolated` (behind `make_current`) end with `Session::lapse`, so the unit discards the queue before the next session opens; and `Session::latest_json_payload` takes the LATEST preset-JSON carrier instead of the longest, so an inherited copy can never shadow the session's own. The offline fake models the queue as the `queued-handshake-flood` injection (`rig_tests.rs`).

## Boot-window `IOHIDDeviceSetReport failed: 0xe00002d6` (kIOReturnTimeout) is NOT an error — it's "device not ready yet"

- On a cold boot the TMP's HID interface enumerates (so `IOHIDDeviceOpen`/seize succeeds AND the hotplug watcher fires) ~20 s before its USB stack accepts reports, so the first handshake _send_ times out (observed live: 3 such failures over ~20 s, then connect). `connect_device` returns a typed error (`error::AppError`, `{ kind, message }`), and `connectError.ts` classifies the `not_ready` kind (a report write the OS refused during the handshake — macOS `IOHIDDeviceSetReport failed`) and `not_connected` (no TMP enumerated) as the plain "Plug in your Tone Master Pro" page (`DeviceState`), NOT a failure — `busy` (another app holds the unit: a held exclusive open, or the macOS `kIOReturnNotPermitted` / Windows `ERROR_ACCESS_DENIED` refusal, `DeviceError::OpenDenied`) gets "Another app is using your Tone Master Pro", and every other kind "Couldn't connect to your Tone Master Pro". Do not "fix" the timeout with a retry/debounce keyed on a _count_ (the window spans several retries); classify by error kind instead. The UI never shows the backend message — it goes to the log — and the classification never reads it, so rewording a backend HID error is safe.

## Scene policy is pure-lazy, no cache

- There is no eager `scan_all_scenes` startup sweep and non-active preset rows show no scene badge. The ACTIVE preset's drawer stays live from field-3 (`scenes[].sceneName` + `lastLoadedScene` + `ftsw`). LevelDialog rows source scenes from the startup backup scan (`BackupPresetRow.scenes`, complete `presetJson`). The field-8 batch sweep (ONE dedicated lean session reading every selected preset's field-8 JSON back-to-back) survives only as `probe --scenes-passive`, HW-measured at ~0.66 s/preset steady-state. NON-DESTRUCTIVE — zero LoadPreset; scene/preset CHANGES on the device are allowed only in the post-disclaimer leveling RUN, never at startup or during setup. The dialog scan is scenes-only: per-preset `listLevelBlocks` (LoadPreset + discovery, ~4 s/preset, destructive) must NEVER run on dialog open — block pickers stay role-based (LEVEL_ROLES) and resolve when the run loads each preset. The destructive LoadPreset→`sceneListResponse`(125) sweep is the `probe --scenes` benchmark. Field-8 read rules: (1) keep the session alive until the final frame; a read sent during the handshake drain queues behind it (~2.14 ms/report). (2) On a quiet session `TrackedHid`'s re-open re-arms the lapsed client first; on an ALREADY-LIVE session (the monitor's dense heartbeat) a re-sent `connectionRequest` only draws a `connectionError`, so the monitor's graph fallback uses `read_slot_preset_json_live`, which skips it (HW `probe --slotread-live`). (3) The field-9 stream ends in a `0x35` final frame, so harvests try both `streams()` and `streams_final()`.

## Preset-list reassembly also needs both stream rules

- `list_my_presets` tries `streams()` (interleaved-0x35-safe mid-flood) and `streams_final()` (terminal 0x35 tail frame) and keeps the longest decoded record set. This fixes the live "Empt" tail truncation class where the last record's final byte rides the closing 0x35 frame. **But tolerant longest-wins still silently accepts a TAIL-truncated list** (a monitor reconnect right after a heavy field-8 sweep snapshotted a short list). The SNAPSHOT path therefore uses **`list_my_presets_strict`** (monitor `assemble_startup_snapshot` + the `list_presets` monitor-disabled fallback): `harvest_preset_list_strict` (streams_final + `proto::preset_list_records_strict`, the songs/setlists strict pattern; missing displayName → "" not dropped, preserving `userSlot = index + 1`) → up to 2 re-arm retries on the open session (quiet line → `connection_request` → `preset_list_request`, WITHOUT `raw.clear()` — the startup graph is harvested from the same accumulated reports afterwards) → tolerant fallback + `log::warn` (a warned short list beats a failed connect; truncation is tail-only so present entries keep correct slots). Leveller/probe/clear call sites stay on tolerant `list_my_presets` (they shape their own bursts; a re-arm would clobber their timing).

## Auto-merge arms ONLY for `main`-targeted PRs

Companion setting: `delete_branch_on_merge` is ON — GitHub's child-PR retarget cascade fires on branch DELETION (not on the parent's merge), so keep it on; never `gh pr merge --delete-branch` a stacked parent (the client-side delete races the retarget and closes the child). **Auto-merge MUST arm with a GitHub App token, never `GITHUB_TOKEN`:** GitHub's anti-recursion rule suppresses every downstream workflow (`ci.yml` `on: push`) for a merge attributed to the default `GITHUB_TOKEN` (`github-actions[bot]`), because native auto-merge attributes the eventual merge push to whoever ENABLED it. `arm-auto-merge.yml` mints an App token (`actions/create-github-app-token`, secrets `AUTOMERGE_APP_ID`/`AUTOMERGE_APP_PRIVATE_KEY`, App installed with Contents+PRs write) so the merge is the App bot's push, which DOES fire `on: push`. Releases are started by hand (`release.yml` is `workflow_dispatch` only), so a merge never starts one. Fail-loud safety: if the App is uninstalled/under-permissioned the mint step goes red and the PR just won't merge — never a silent CI miss.

## Fully automatic connection

- There are no manual Connect/Disconnect buttons. On mount the frontend calls `connect()` and then retries every `RETRY_MS` (3 s) on a guarded `setInterval` until the device is found, so plugging the TMP in later connects on its own. `connect_device` starts the monitor and returns the monitor snapshot's firmware + graph; `listPresets` then resolves from the same snapshot. Until the first attempt settles the device tabs show "Connecting to your Tone Master Pro…"; after that the last failed connect's typed KIND picks ONE shared page (`views/DeviceState.tsx`): no device or a booting one → **"Plug in your Tone Master Pro"** (+ Connection help), `busy` → "Another app is using your Tone Master Pro" (worded per platform: Linux has no Pro Control), anything else → "Couldn't connect to your Tone Master Pro". The backend message never reaches the screen (it is logged). There is no Scan button either: the 3 s poll and the hotplug attach are the only connect paths, both through the one single-flight `attempt()`. The toolbar's `DeviceStatus` says the same in a few words: "Not connected" (hollow) / "Connecting…" (spinner, also the first 900 ms after a connect) / "In use by another app" / "Connected · firmware <fw>" (green) / "Untested firmware <fw>" (caution). **Connection-loss detection:** `watcher.rs` emits `tmp://device-{attached,detached}` — on macOS via a non-seizing IOHIDManager (near-instant), on Linux by polling `hid::device_present()`'s sysfs walk once a second, on Windows via non-seizing Configuration Manager HID notifications plus one-second SetupAPI presence polls. On detach App.tsx flips to disconnected + clears the firmware/snapshot state, and the 3 s retry interval stays armed so a replug auto-reconnects. Calibration from the Settings window is unaffected because every device command releases + re-acquires the seize (`with_released_seize`).
  The full first-connect **handshake is load-bearing** — the device only answers after seeing the captured Pro Control sequence (`connection_request` + preset lists + product profile + current-preset/settings/userir requests). Don't trim it without testing.

## A preset with NO blocks re-amps as clean passthrough — do not mistake it for a dead chain

- Not every named preset in My Presets carries blocks: a preset can read back over field-8 with the normal graph GROUPS present (7 guitarNodes / 4 micNodes / 2 splitMix) but **zero populated nodes** — no node carries `dspUnitParameters`. Re-amping one returns the stimulus with only level applied, so the capture is a faithful, finite, plausible-looking LUFS that is nevertheless the _stimulus_, not a tone; every such preset returns the SAME loudness, preset-independence that reads as a wedged device (HW, fw 1.8.58: an empty user slot re-amped as a finite, stimulus-shaped capture through every guitar stimulus, −21.2 to −26.2 LUFS). **The discriminator is spectral, and the filters must be steep** — HF(>6 kHz) − LF(<1 kHz) tilt with 6-pole filters was `+3.53 dB` for the dry stimulus, `+3.50 dB` through a no-block preset (unchanged ⇒ passthrough) and `−3.53 dB` through a real chain (7 dB darker ⇒ cab rolloff). 2nd-order bandpasses leak: all four "bands" then measure overall level, and a uniform delta means _quieter_, not _unprocessed_. **Before concluding the hardware is broken, confirm the preset under test actually has blocks** (`probe --slot-json <1-based slot>`, count nodes carrying `dspUnitParameters`). The shipped Doctor calibration reads that flat chain as `fizzy` and `lost` (humbucker, single-coil, acoustic) and `fizzy` alone (active): the stimulus's own mid hole judged against a target that expects distortion to fill it.
  - **Two companion red herrings.** (1) `probe --activegraph` failing with _"no preset JSON in handshake — currentPresetDataChanged absent (is a preset loaded?)"_ does **NOT** mean no preset is loaded: that arm does not open a dense-heartbeat session — `probe --dump-currentpresetdata <idx>` captures the live push. (2) `leveller::is_engaged` keys on the 400 ms momentary spread (`FLOOR_TRIP_LU` = 0.4), so a stationary stimulus (an EBow) can still stamp `FLOOR/SILENT — not a valid measurement (failed inject?)` on a processed capture. Judge engagement spectrally, and don't retune the threshold without a corpus that separates a true failed inject from a stationary-stimulus capture.

## A param-func footswitch without `valueType` makes the firmware silently replace the whole imported preset

- **The imported name showing in the list is not proof the import stuck** (static RE + HW, fw 1.8.58). The import is accepted, and the first real LOAD rejects the body (`valueType` is a required key) — the working copy becomes the empty template (`preset_id` `af08d1ac-…`, 0 blocks) under the imported name, and that `loadPreset` answers `presetError` 6 (the import sends none, nor does its own reload when it lands on the loaded slot). The stored row keeps the imported body, so a `presetDataRequest` (field 8) read shows it intact; see [the rejected-at-load entry](#a-body-rejected-at-load-becomes-a-silent-empty-preset-that-keeps-its-name). The `exp` block's own entries carry a STRING `"valueType": "float"` in real device exports — that shape is real and must NOT be gated or touched; a numeric `"valueType": 2` on every `func: "param"` ftsw entry imports intact.
  - **Enforcement.** `src-tauri/src/fixture_gates.rs`'s `every_param_footswitch_in_every_fixture_carries_a_numeric_value_type` gates every committed fixture's `func: "param"` ftsw entries for a numeric `valueType`, with a negative check (forking a fixture body with `valueType` deleted must flip the same predicate to failing) so the gate can't pass vacuously. `footswitch::validate_import_body` refuses such a body before import, and `replace_inplace_with` loads every import (including one that landed straight on an empty target) and refuses a body that loaded as the template (`replace_inplace::load_and_prove`), clearing a rejected direct landing.

## A dual-entry footswitch row is legal on fw 1.8.58 — it gutted imports on fw 1.8.45

- **A row may carry up to 5 entries and nothing checks combinations** (static RE, fw 1.8.58), and the factory bank ships such rows. On the unit, one imported body with one on-off + param row loaded with its own name, `preset_id`, 8 blocks and 20 rows, and no `presetError`; the row's entries themselves were not compared (HW, fw 1.8.58). `footswitch::validate_import_body` and `fixture_gates` still pin at most ONE entry per row — conservative; relax them only with a HW-checked emitter change.
- **Diagnostic order for "my import changes nothing":** COUNT populated nodes in the LOADED working copy first (field 3 after a real load — field 8 returns a rejected body intact); only a populated graph earns an audio A/B. An empty substitute is the no-blocks clean-passthrough trap above.
- **The firmware FILLS unauthored `dspUnitParameters` with ACTIVE defaults at import — and some defaults process audio.** A hand-authored `ACD_FiveBandParamEQ` carrying only filters 2–4 came back from the device with `filter1`/`filter5` filled in as ACTIVE type-4 filters at 1 kHz (q 0.707, `gaindb` 0, `bypass` false); enabled, the pair cost ~20 dB of level and read as muddy+dark on an otherwise clean chain, invisible to any `gaindb`-based neutrality check (a pass/shelf type ignores `gaindb`). Authoring rule: a fixture that ENABLES a multi-filter block must explicitly pin every filter it does not use (`filterNbypass: true`) — `fx_doctor_oracle_fires_nothing_in_base_and_carries_its_defect_table` asserts this on the oracle.

## An engage after a naked scene recall latches silence — break the idle with heartbeats

- **The device limit is 750 ms of host OUT silence, counted from the last report sent, not the last command** (HW, fw 1.8.58: an engage at 740 ms applied, at 760 ms it was dropped, 2 runs each). A dropped engage captures the device's stationary output floor, not the stimulus. Keep every last-command→engage idle gap ≤300 ms as a safe proxy.
- **The fix** lives in `leveller::capture_on_session`: when there is neither a force-bypass write nor a reference level (the naked shape), a `Session::heartbeat` — the designed keep-alive, writes nothing — breaks the pre-engage idle, giving recall → 150 ms → heartbeat → 100 ms → engage (`leveller::recall_settle_ms`, `breaker_beats`, `pre_engage_settle_ms`; HW, fw 1.8.58: every capture of the 405/410 leveling bench within 0.01 LU of the longer cadence, no floor read). Write-bearing paths (any bypass entry or a reference level) skip it deliberately: their writes already break the idle. `measure_scene_asis` and `arm_pair_measurement`'s zero-write base arm hand-roll the same cadence for their own pre-engage shapes.

## A footswitch row whose block is ON in the base is only correct when it is the batch's ONLY row

- **`plan_footswitch_jobs` must assert a base-on block's own bypass, not only its siblings'.** A SIBLING row's isolation writes this block's `bypass = true` into the device's working copy, and every capture's `recall_base` re-asserts that mutated copy, so a row built from `siblings_off_excluding` alone measures with the very block it is levelling switched OFF. Its handle then has no authority over loudness, `solve_param_secant` sees an unmoving reading and reports a reason-less `clamped scene_ceiling` — in any batch with more than one row, whatever the order (HW).
  - **The `measured_lufs == predicted_lufs` tell.** In every failing case the low-bound reading and the achieved reading agree to four decimals. That equality means the row measured a sound its knob does not affect.
  - **The ceiling prepass is the reference.** It goes through `footswitch::switch_states`, which DOES assert the switch's own nodes; the plan builds that same list, and `plan_on_in_base_still_asserts_its_own_block_bypass` asserts the two are equal rather than merely similar.
  - **Why the correct value can look like a no-op.** When a preset's base sound IS a switch's engaged sound, the right answer for that row once base is leveled is the authored value it already had — not evidence that nothing happened.

## A scene renders the base chain's ON blocks — an all-false `ftswStates` does NOT bypass them

- **Levelling a footswitch's handle moves every SCENE of the same preset, by the same dB**, whenever that switch's block is one the preset leaves ON in its base state (HW: cutting a base-on `ACD_TubeScreamer.level` by 2.0 dB moved all three scenes by 2.0 dB, while every lane reported `clamped:false`, `saved:true`, `persist_mismatch:false`).
  - **`ftswStates: [false, …]` in a scene is not a bypass instruction.** A recall writes the scene's `ftswStates` into the footswitches' `isActive` flags only — each switch's LED and what its next press does; block bypass and audio at the recall come only from the scene's node overlays (static RE, fw 1.8.58; matches the HW result above). A scene renders the base chain's own state for anything its overlay does not itself carry.
  - **BASE is immune, and that is what hides it.** A base capture forces every footswitch-owned block off (`doctor_force_bypass`), so base stays on target while the scenes drift.
  - **The bracket is the diagnostic.** One extra re-measure of a single scene IMMEDIATELY after its own batch save, before any later lane writes, separates "mis-solved by its own batch" from "moved by a later lane".
  - **The fix is ORDER, not a re-solve.** A footswitch row is measured in BASE context, so a scene's own amp overlay can never move it back. The order is PER-ROW (`views/level/leveling.ts`'s `runRank`): base, then BASE-CONTEXT footswitches, then scenes, then SCENE-CONTEXT footswitches — a scene-context row must run AFTER its scene is on target. See `runRank`'s own doc.

## A capture must re-assert the run's own `presetLevel` — a scene recall reverts an unsaved one

- **A recall keeps the unsaved level, with one exception (static RE + HW, fw 1.8.58):** `loadScene(8)` while base is already current, under MAINTAIN CHANGES, re-applies the base snapshot's level — the level of the last load, scene recall or base structural edit, not the saved row — and a save does not refresh that snapshot. HW: a preset levelled and saved with base active played its old level on the base recall and the new one after a real reload. So a `presetLevel` save with base active ends with a real reload (`leveller::reload_after_level_save`); without it the post-run re-measure and the user's own base tap play the old level. Footswitch runs escape: their isolation writes dirty the working copy, so the next same-slot load is a real reload.
- **Every capture re-asserts the run's level** (`leveller::recall_reassert_save` and the capture arms), so a level the run holds UNSAVED (a landed headroom trade's raise) survives that base recall. With no trade the re-assert writes the saved level, read from the batch's field-8 doc. The scene lane gets the same treatment. Gated offline by `a_capture_renders_at_the_run_level_not_the_recall_reverted_one` (an unsaved run level against SimDevice's recall revert, which applies once the slot has been saved this run).
- **THE PREPASS AND THE SOLVE ARE COUPLED — an invariant neither module states alone.** `prepass_scene_ceilings` produces the as-is reading that `correct_iter` takes as its `measured0`, and compares against a post-apply capture. If the two render at DIFFERENT `presetLevel`s, the first "response" is the level difference rather than the knob's, and the solve reads authority where there is none (offline, 9.9 dB of such "response" on fixture 403 swamped `no_authority`'s 0.3 LU tolerance and turned an actionable routing clamp into a reason-less headroom clamp). Both sides go through the ONE seam, `leveller::scene_capture_level` — do not re-inline either. The asymmetry that makes this easy to get wrong: the prepass runs BEFORE the headroom trade decides anything, so it passes `hold = None` and gets the preset's saved level, while the solve passes the real hold; that is deliberate, and the two agree whenever no trade lands.
- **`no_authority`'s 6 dB floor is about the STEP, and the step is sized by the solve — so the verdict needed a probe of its own.** The check is "a move of at least `NO_AUTHORITY_MIN_DB` produced less than `KNOB_TOL_LU` of response", but the first applied move is whatever the open-loop solve asked for. A scene sitting 4 dB from its target gets a 4 dB move, so a knob with LITERALLY ZERO authority would fall through to the secant, stall on a flat slope, and report a reason-less headroom clamp — the user told "couldn't get there" instead of "this amp doesn't reach USB 1/2", which is the one thing they could act on. `correct_iter` takes ONE confirmation capture when the first move produced a flat response: step DOWN a full `NO_AUTHORITY_MIN_DB` and look again. Downward only — a raise can clip, and a saturating limiter makes an upward non-response ambiguous. If the probe moves the capture after all, it is a better secant seed than the flat base point, so it is used as one. A healthy knob moves ~1 LU per dB, so this never fires on a working solve. `level-trade.spec.ts`'s zero-authority taxonomy spec covers it.
- **A pure-logic gate exists for the scene lane's choice** (`a_scene_batch_captures_at_the_saved_level_when_no_trade_holds_one`) because that half is NOT observable offline: SimDevice only reverts a recall's level for a slot the run has already saved, and the scene specs level slots they never saved first. Reverting that arm alone leaves the entire offline suite green.

## A scene doc that cannot answer falls back to the BASE graph, so the run levels the wrong amp

- **The rule.** `classify_scene_knobs` refuses a scene whose live doc answers for no amp at all, rather than classifying it against the BASE graph — a live field-3 doc cut before the amp nodes once drove the base amp in a scene whose own overlay swaps to another (HW). The refusal is then repaired from the saved preset via `read_slot_preset_complete`'s backup-backed read (`audioGraph` + `scenes`); a scene the saved preset cannot answer either is skipped and reported, never leveled against base.
- **Gated by** `a_truncated_swap_scene_levels_its_own_amp_not_the_base_one` (own-amp identity), `a_scene_whose_doc_never_arrived_skips_instead_of_classifying_against_base`, `a_scene_whose_doc_is_partial_skips_instead_of_classifying_against_base`, and `a_scene_whose_saved_overlay_is_unclassifiable_skips_instead_of_losing_its_headroom_silently`.

## A post-save re-read that cannot answer must say UNCONFIRMED, never "did not persist"

- **A truncated read loses `scenes` first, so a missing section is UNVERIFIABLE, not absent.** A false "did not persist" is worse than no check: a scene whose re-measure of the SAVED state read on target was reported as lost (HW), teaching the user to distrust correct results. Both post-save verifiers read through the complete-or-fail reader, AND the grading keeps `Unverifiable` distinct from `Absent` (`SceneOverlay::Unknown` carries the distinction into `persisted_value`). The second line matters because a document can arrive whole and still carry no `scenes`.
- **Not an amnesty.** When the section IS present and covers the slot, a genuinely-absent overlay stays a MISS — the gate exists so a report can never show numbers the save wiped. Pinned by `a_truncated_reread_is_unconfirmed_not_a_lost_write` and its FS twin, which assert both directions.
- **`ftsw` sorts ahead of `scenes`, so it can survive the cut that takes `scenes`** and works as a scene-COUNT oracle (its scene rows name the scenes): the device emits a stored row's keys sorted (static RE, fw 1.8.58). `--slot-json` pretty-prints a PARSED value through `serde_json` without `preserve_order`, so its key order says nothing about wire order either way.

## The Doctor's envelope correlator has a PEAKLESS curve on a wash/reverb chain — a floor-relative energy step is the deterministic primary

- **The correlator cannot place a wash onset.** On a 65 %-wet `ACD_TMLargePlate` the correlation curve is FLAT (0.27–0.37 across every lag 0–250 ms, no peak), so its confidence gate (a corr floor + lag ceiling) either rejects the capture or accepts an arbitrary lag, landing on either side of the 120 ms gate at random and flipping `washed` (HW, `probe --doctor-fs`).
- **The energy onset is deterministic across every chain observed, wet or dry, because the Doctor stimulus always carries a played silent pad ahead of the body** (`leveller::DOCTOR_PAD_MS`): the first 2 ms hop that steps up from the pre-signal floor by ~60 dB lands at 230–232 ms in all 11 captures (wet and dry) — a true inject latency of ~30 ms. `leveller::doctor_onset` tries this energy step first, falling back to the correlator only when the step doesn't fire in-band, and to the un-aligned split when neither does.
- **Split sensitivity** (`tail_energy_ratio`): a sustained reverb tail decays ~25 dB/s right after the body, so the split-onset location moves `tail_ratio_db` by ~0.8 dB per 32 ms on the wash fixture — 0 ms (un-aligned) → −8.85, 32 ms (true) → −9.6, 48 ms → −10.1, 120 ms → −11.5. A wrongly-confident correlator lag anywhere past ~48 ms is enough to flip `washed` on a marginal wash preset. The capture's tail LENGTH is wall-clock (`reamp_capture` keeps whatever frames arrive in `play + tail` ms) and moves the ratio ~0.3 dB per 100 ms — which is why the tail window is PINNED to the recipe's tail (`DOCTOR_TAIL_MS`) after the body end.
- **The first capture after other device activity reads ~0.3 dB off** (a device-side cold-capture offset, not alignment; warm runs spread σ ≈ 0.05 dB). The oracle wash fixture sits at mix 0.9 / decay 0.9 to keep a 1.6 dB margin over the −10 gate on a cold capture; mix alone barely helps because the body gets wetter with the tail — decay is the lever.

## A body rejected at load becomes a silent empty preset that keeps its name

- **The rule (static RE + HW, fw 1.8.58).** An import validates only LZ4 and JSON syntax and stores the JSON verbatim. Shape checks run at the first real LOAD, immediately — never later; a throwing check is caught, the working copy becomes an empty preset (template `preset_id` `af08d1ac-…`, 0 blocks) that keeps the stored display name, and that `loadPreset` answers `presetError` 6. The import sends none, nor does its own reload when it lands on the loaded slot. The stored row keeps the imported body — `presetDataRequest` (field 8) returns it unchanged — so only a load shows the rejection. A later save persists the empty body.
- **Every import → load → save path proves the loaded body.** The in-place re-import path (`replace_inplace_with`: OFFLINE edits, migration, `probe --restore`) loads the scratch import and saves it over the original; slot + name (`confirm_active`) pass on the substitute, so it reads the working copy and refuses the save unless its per-group blocks match the file's (`replace_inplace::load_and_prove`, fail-closed on a short read). An import that landed straight on its empty target (only when no user slot below the target is empty) is loaded and proven the same way, and a proven rejection is cleared: its stored row reads pristine over field 8, so a seed that left it resident would skip it on every later run instead of failing.
- **What the validator refuses.** `footswitch::validate_import_body` enforces the missing-`valueType` shape (the only one fw 1.8.58 rejects) and, conservatively, the dual-entry row (legal on fw 1.8.58). Static RE also names a footswitch row count other than 10 or 20 as a load-time reject; the unit contradicts it — it pads the 9- and 5-row `ftsw` of fixtures 405 and 410 to 20 rows (HW, fw 1.8.58).

## An insert with a missing anchor or over the CPU budget aborts the device server

Static RE, fw 1.8.58; not triggered on the unit.

- **Anchor.** `insertNode` field 2 (`nodeIdInsertLocation`) is looked up in the target group's node map, keyed by node id. A miss throws "nodeIdInsertLocation doesn't exist" before any change; there is no fallback to the FenderId.
- **Budget.** The check fails when `frinta(total + cost) > budget` in float32, so a total of exactly 76.5 fails. The cost table matches `model-cpu.json`; an id the firmware lacks costs 20.
- **What follows.** For an insert, the ControlProxy swallows the exception and returns an empty id; the handler then throws with no catch on the MessageProcessor thread, so `std::terminate` aborts the server. systemd restarts it; the HID session drops; a third start within 60 s is refused. A replace over budget instead gets `presetError` 14.
- **New node ids.** The FenderId, or the first free `<FenderId>_1`… in the group, returned in the `nodeJson` (field 3) of `nodeInserted` / `nodeReplaced`; both confirms are broadcast to every host, and `nodeReplaced.replacedNodeId` echoes the OLD id.
- **Other paths.** `insertNodeAtBlockIndex` (99) aborts the same way; `moveNode` and template switches have no budget check and cannot abort. A LOAD over budget only logs and loads in full, with no error to the host — so an over-budget import or save is not refused by the device either.
- **Guards.** `blockcaps::check_op` (Rust) and `checkOp`/`checkEdit` (TS) apply the budget rule; Copy resolves anchors through `copy_apply`'s `DeviceIds` and refuses one it cannot resolve; the probe's Doctor inject (`probe --doctor-inject`) checks anchors and caps against a live read before applying (the app's Doctor never writes); an unconfirmed insert is read back (`Session::insert_landed`) instead of re-sent blind.
