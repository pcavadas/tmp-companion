# Leveling (Level tab)

Leveling drives the device in **re-amp mode** (no guitar plugged in): it plays a synthetic pickup-shaped stimulus through a preset's full DSP chain, captures the processed USB-Out, and measures integrated (gated) LUFS.

## Preset leveling — one-shot open-loop

`presetLevel` is a linear amplitude control: `captured_LUFS = 20·log10(presetLevel) + C`. So measure once, solve `C`, compute the exact level. Per preset, `leveller::level_preset`:

1. `load_preset(slot)`, settle, drop the seize.
2. fresh connect → `set_preset_level(ref = 0.5)` → engage re-amp once → capture → measure → solve the final level.
3. fresh connect → `set_preset_level(final)` → optional verify capture → optional `save_current_preset`.

`C` (loudness at level 1.0) is each preset's max reachable loudness; a target louder than `C` clamps (surfaced in the UI). The ceiling is preset/model-specific, not a fixed dB rule.

## Scene leveling — one-shot open-loop on the active amp

Amp `outputLevel` is linear in dB with full authority, so each scene is leveled the same way as a preset: measure the scene as-is (isolated re-amp capture), solve `C`, set the scene's active amp `outputLevel`. Level the base scene via `presetLevel` first (it scales all scenes), then each footswitch scene via its amp `outputLevel`. A scene that can't reach the target clamps honestly.

Per-scene rules:

- The amp is picked per scene from the live audioGraph (a bypassed amp's knob measures flat → clamp).
- Amp candidate choice has TWO filters: classify amps by stable `FenderId` / `model_id`, then allow ONLY the amp `outputLevel` parameter (verified against the fw 1.7.75 + 1.8.45 embedded amp schemas). `output` is not an amp control; `level` on `ACD_TMRumbleV3` is an amp knob but NOT the output leveling control — it must not be changed. Preamp/master/volume params (`brightvolume`, `mastervolume`, `normalvolume`, `volume`) are forbidden — they alter the preset's sound. HW-load-bearing: preset 001 Klon's Hiwatt hit `-9.610 LUFS` only once its actual `outputLevel` was at 100%; a first-active-param pick chases earlier volume params and falsely clamps.
- Scene Edit mode (`SetNodeSceneEdit` true) gives FULL per-scene isolation for the param being written — a scene's `outputLevel` write does not touch the base/global value. **But enabling it is NOT itself harmless** — see `probe_api/slot_write.rs`'s `--set-scene-param` doc comment for the HW 3-cell isolation matrix: it RESEEDS that node's entire scene overlay from base, silently WIPING any other already-scene-edited param on the same node. Addressed at the SOURCE: `set_knobs` enables Scene Edit ONLY for a node with NO overlay in the target scene — the one case where the reseed has nothing to lose (an absent overlay renders base values, which is exactly what the reseed seeds). A node that already HAS an overlay is written with the enable DROPPED (the write lands on the overlay anyway, HW), so nothing is wiped. The per-node state comes from the run's ONE field-8 read (`scene_jobs::scene_overlay`, raw `scenes[]` — after `overlay_scene_onto_graph` a base value is indistinguishable from an overlaid one, so the live docs cannot answer it), and an UNKNOWN answer (truncated read, or no read at all) REFUSES the scene write rather than guessing: both write shapes corrupt from there. The earlier mitigation — repair-by-diff, re-writing the top-N divergent siblings in the same batch — is deleted: with the enable correctly gated there is nothing to repair, and the repair writes were HW-observed not to land (8/8). Separately, the leak-by-order issue: a value write landing BEFORE scene mode is enabled hits the BASE scene (which un-scene-moded slots inherit) — a rare too-fast race the verify + correction pass covers. **But the settle must stay SHORT — the drop is a PER-COMMAND IDLE-GAP cliff at ~400–450 ms, not a "time since `loadScene`" window.** The bisect data (`probe --bisect-scene`, fw 1.8.45: `loadScene→300→sceneEdit→400→write` lands; `…→450→write` is SILENTLY DROPPED — no `presetError`, capture unchanged, nothing persists) was first read as a ~700–750 ms total-elapsed window; the discriminating run (Hiwatt slot 31, fw 1.8.45) refuted that: in the enable-dropped branch the back-to-back 150+300 ms settles formed ONE 450 ms idle gap and 6/6 bare scene writes vanished at only ~450 ms total — while every ≤400 ms-gap sequence lands. It is the same session-lapse family as the idle re-amp-OFF drop (`reamp_off_guaranteed`, HW: 300 ms lands, 1 s+ drops). Consequences baked into `set_knobs`: `SETTLE_AFTER_SCENE_RECALL_MS`=150 (post-`loadScene`), `SETTLE_AFTER_SCENE_EDIT_MS`=300 (post-enable) — and the post-enable settle is slept ONLY when an enable actually went out (a settle for a command that wasn't sent is pure idle and rode the cliff). The old `SETTLE_AFTER_SCENE_EDIT_MS`=600 dropped 100% of production writes the same way, surfacing as false "clamped at (as-is)" rows and ZERO persistence; the pre-fix 300+300 pair occasionally dropped a single write on latency jitter (the user-reported _non-deterministic_ false clamp). The LOWER edge is generous: scene settles of 150, 100, and even 50 ms all land ON the scene overlay (never leak to base) and persist.
- The BASE scene's blocks have no scene mode; only CHANGE a scene's `outputLevel` when it actually needs it (pure cleanliness, not safety) — `level_scenes_oneshot` measures each scene AS-IS (`measure_scene_asis`, no write) and skips scenes already at the solved level.
- **A session that has toggled re-amp silently DROPS `saveCurrentPreset`** (HW, fw 1.8.45, `probe --bisect-scene … save`: post-engage same-session save persists NOTHING; the identical save on a fresh connection persists). The written values survive in the device's working copy across reconnects. (The footswitch path is immune to THIS mechanism — it saves on its own dedicated live-edit session — but it WAS bitten by a different one: a stale same-slot preset load landing inside the TMP's lazy `saveCurrentPreset` commit window materialized pre-save bytes into the batch's base state before a single pedal was measured, corrupting every downstream footswitch solve. See the lazy-commit entry in `notes/gotchas.md` and the freshness barrier below.) Symptom when violated: scenes verify on-target during the run but the preset's saved bytes are unchanged.
- **ONE save per preset (deferred writes).** Scene writes accumulate UNSAVED in the working copy (`LevelOptions.defer`: no per-apply save, no restore) and the runner persists them with ONE `saveCurrentPreset` at batch end (`save_deferred_scene_writes`) — which first recalls the preset's original active scene (the prepass's saved `lastLoadedScene`) so the save stamps the same base/scene/FS state the preset was loaded in, then saves on a clean never-re-amped connection (one retry). Also fired on CANCEL so already-reported scenes persist. HW facts making this sound (`probe --defer-scenes`, fw 1.8.45): unsaved scene-edit writes survive scene recalls AND reconnects; re-recalling a written scene does NOT revert its unsaved write; one save persists every accumulated overlay; the save stamps `lastLoadedScene` from the active state. Footswitches mirror it: the batched command measures every switch first (sweep pollution is self-correcting — each job's force list sets every sibling's bypass explicitly, and swept params live on blocks the next job forces off), then `write_footswitch_values` commits ALL switches on ONE live-edit session with ONE save (per-write confirm gates kept; ANY unconfirmed write aborts before the save so nothing half-applied persists). Net: leveling a preset's scenes + footswitches = one save per scene target-group + one save for all its switches, instead of a save per apply/switch.
- `level_scenes_oneshot`/`jointk_one_scene` run a BOUNDED secant correction (`correct_iter`, cap `MEASURE_CORRECT_MAX`=3, ±`BATCH_TRUST_DB` trust region) that always lands+saves the BEST point, so `apply_levels` never persists a worse number than reported. A ≥6 dB `outputLevel` change that doesn't move the USB 1/2 capture (`no_authority`) is an honest clamp with a distinct `clamp_reason` ("off-branch / off-USB"), restoring the amp to base.
- **Dropped-write retry (`apply_first_verified`, `SUSPECT_DROP_MIN_DB`=2):** the first verified apply re-applies ONCE when a ≥2 dB intended move reads back ~unchanged (< `KNOB_TOL_LU`). Rationale: a scene write can drop silently (the acceptance window above) and a verify capture can one-off mis-measure by LU-scale (HW: 1-in-4 bisect captures read 2.9 LU low, same `C` on the other 3) — either way a single flat first verify used to be TERMINAL (flat secant slope → false "clamped at (as-is)"). One retry disambiguates; a genuine no-authority amp stays flat on the retry and takes the honest clamp. Even 6:1 compression passes ~0.33 LU of a 2 dB move, so the signature is not compression.
- The device pushes NO field-3 while re-amp is engaged, so knob picks + per-scene knob values resolve in an un-engaged PRE-PASS (`prepass_scene_docs` + `build_scene_jobs`: one rich session loads the preset and harvests each scene's field-3 doc via loadScene → push). **Active-scene gap:** field-3 is pushed only on a CHANGE, so recalling the scene that is already active (the preset's saved `lastLoadedScene`, materialized by the prepass `load_preset`) gets NO push → an empty doc → a "can't classify scene routing" build fail. Which scene that is follows the preset's last save, so the failure MOVES between runs (HW: the scratch preset failed exactly its saved-active scene, `doc=0B`, and the failing scene changed after each save). The prepass now tracks the active scene and serves it from the last harvested doc instead of sending a doomed no-change recall. **The pre-pass is also the runners' preset load**: `level_scenes_oneshot`/`level_scenes_rebalance` do NOT re-load the preset (caller contract — every caller runs the pre-pass right before), and the UI batches ADJACENT same-preset scene rows sharing instrument+target into ONE `level_scenes_apply_batched` call (`useLevelingFlow`, per-scene progress on the channel). Both halves kill the user-visible churn where the unit flashed back to the preset's base twice per scene (per-scene calls: prepass load + runner re-load, once per dispatched scene).

### Retired: the BatchedLive closed-loop harness

`leveller::level_scenes_live_batched` is retained ONLY for the `probe --bench-scene-leveling` harness (`<slots_csv> <target> <topology> <out.json>`; it streams rows to `<out>.json.jsonl` incrementally — an end-only write once lost a 40-min run to an OOM reboot). Mechanics: the preset loads once, ONE `audio::LiveReamp` stream pair runs for the whole preset (silence between engages), each scene gets a lean engage connection (`set_knob` = scene recall + Scene Edit + start value BEFORE engage), then trust-region slope jumps (`next_live_coord(LiveHybrid)`, clamped ±6 dB/move — unclamped jumps overshoot steep knobs by ~6 LU; pure secant is noise-fragile on ±0.2 LU windows; fixed-gain proportional stalls on compressed responses) against 2 s live windows. HW: 6.7–9.4 s/scene converged (±0.3 LU gate), ~20 s on weak-authority picks.

**Why it was retired — it MIS-MEASURES on its shared stream (fw 1.8.45):** the single continuous `LiveReamp` stream read with `live_window_lufs` windows returns impossible per-scene loudness (preset 001 Klon read `-6.96 LUFS` when that amp `outputLevel`'s true range is `-40…-14`), so the trust-region loop feeds on garbage and clamps (the secant flips to the loud bound on a near-zero/negative slope — no monotonicity guard). The correct method is an ISOLATED fresh re-amp capture per measurement point (the `measure_knob_at` shape, fresh stream pair each point) — and the closed loop is unnecessary anyway: amp `outputLevel` is LINEAR in dB with FULL authority (~25 LU range HW-measured).

**Bank-wide HW validation (2026-07-20):** a dry sweep (`probe --level-preset-scenes`, no-save, −23 LUFS) across 6 presets / 19 sounds confirmed the one-shot open-loop on every GUITAR preset — Base solves ±0.03 LU, every FS scene within ±0.05 LU (001 "Guitar" 8 scenes, 002 "Guitar Boost" 8 scenes, 006 "Reverse Delay" 1 scene, 007/012 no-scene Base-only, 014 "Billy Corgan" 1 scene).

- The two Bass VI presets (009, 010) exposed the documented compressor class: the RAW open-loop model undershoots up to −5.3 LU through their compressed synth chains, error growing with distance from the 0.5 reference and flipping sign with move direction — exactly the "undershoots through a compressor/limiter" class. The PRODUCTION path (`level_scenes_oneshot` → verify → bounded secant, `probe --jointk-scenes`) drove preset 009 correctly: 4/8 scenes converged to −23 within ±0.23 LU (writes=2 = one secant correction), 4/8 honest clamps (scene 0's true ceiling with both parallel amps maxed is −26.3). No silent misses — the raw sweep's misses were the probe arm's simplified path (`probe_level_preset_scenes` has no correction), not a product bug.
- KNOWN GAP: preset 010's scenes were SKIPPED by the production path — "active amp ACD_SVTBlueLineCabIR has no outputLevel control": the param is absent from that preset's harvested node doc (the same amp id leveled fine via outputLevel in preset 009), i.e. amp-knob discovery depends on the param being present in the preset's doc. Follow-up: fall back to the schema/default when the doc omits `outputLevel`.

**Footswitch bracketing:** the secant seeds are `0.25`/`0.75`; a block whose useful range saturates before `0.75` (e.g. a compressor-style knob already flat by then) reads a near-zero slope there and falsely "clamps" even though a much lower value reaches target. `fs_bracket_expansion` retries toward the extreme (0.0 or 1.0) when the seed pair isn't bracketing, keeping the plain secant otherwise (the full false-position/Illinois-damping rewrite was scoped out as the minimum-viable fix) — HW-confirmed 2026-07-26 on preset 28's real Lightspeed switch.

## Footswitch leveling — the chosen block parameter

A block-acting footswitch toggles a block on/off. Each one is leveled one at a time (`level_footswitches_apply`, jobs from `footswitchesPerIndex`) by sweeping the **user-chosen block parameter** (`levGroupId`/`levNodeId`/`levParameterId`) — a secant search in _parameter_ space (not amplitude, since the parameter is not necessarily a linear gain). The solved value is applied either **baked** (a direct `changeParameter` on the block) or **assigned** (the footswitch's param-change function carries it as `valueA`); the backend picks per node (`plan_footswitch_jobs`): **Assign only when baking is genuinely unsafe** — the block is not the sole owner of `(node, param, target)`, or a scene FLIPS the node's bypass vs base (value semantics; unreadable scene data conservatively counts as a flip). A scene overlaying the leveled param does **NOT** force Assign: a full-param overlay MASKS base (HW, Hiwatt slot 31 — the scene overlays governed the DSP while base stayed untouched), so a bake can never leak into it, while an Assign's single `valueA` would trample authored per-scene values (the Hiwatt mutes its trem in one scene with `level: 0.0`). Instead a Bake carries `mirror_scenes` — the scenes whose overlay RESTATES the base value (`scenes_restating_base`, `SCENE_PARAM_EPS`) — and `write_fs_values_on_session` writes the solved value into each of those overlays after the base write (one recall per scene, writes inside the idle-gap window, no Scene Edit enable since the overlay exists), so the bake is effective in every uniform scene and every authored divergence survives untouched (HW-verified end-to-end on the Hiwatt: base+3 restating overlays got the solved value, the `level: 0.0` scene kept it, `ftsw` byte-identical). The write session then recalls the preset's original `lastLoadedScene` before its ONE save (the save stamps the ACTIVE scene; without the restore an FS/base-leveling save silently rewrote the preset's on-load scene to base — HW: 3 → 8). `level_preset`'s save does the same via `LevelOptions::restore_scene`. Method is internal, never surfaced.

Each footswitch levels in **isolation**: every other block-acting footswitch's on/off block is forced off (`siblings_off_excluding`, fed by the `onoff_nodes`/`all_onoff_blocks` helpers) so sibling pedals don't color the capture, while the target switch's own block(s) get their engaged state (`engaged_bypass_for_switch` — **isActive-aware, NOT a plain flip-of-base**: an on-off is a latching toggle whose `isActive` records whether the preset was saved WITH the switch active, so engaged bypass = saved bypass when `isActive`, else the flip. HW, preset 024 "TR+BD2+BMP": BD2 saved ON + `isActive:true` — the old unconditional flip forced BD2 OFF during its own switch's Doctor capture, diagnosing the base sound instead; OCD/Rat, saved off + inactive, happened to flip correctly. The Doctor's `doctor_force_bypass` shares this helper). **"Base" (`level_preset`) means the preset with NO footswitch engaged — every footswitch-owned on-off block is forced OFF**, whatever its saved bypass. The list is `doctor_force_bypass(ftsw, preset, None)` (i.e. `all_onoff_blocks` → `bypass=true`), the SAME derivation the Doctor's base sound and the `e2e_server` validation yardstick use — one definition, three callers. The `ftsw` it is built from must arrive WHOLE: `ftsw` sits at the tail, exactly where a large preset's field-8 read is cut, and a short list silently leaves pedals on and SAVES a `presetLevel` solved for the wrong sound — so the read is `read_slot_preset_complete(slot, &["ftsw"])` (backup re-read on truncation, refuse if that cannot be addressed), and it still supplies the revert anchor (`presetLevel`) and the save's `restore_scene`.

**Why it is a definition, not a measurement (user ruling, 2026-08-20).** Base means base: the preset with nothing switched on. Stating it as a definition is deliberate — it is what stops the next hot reading from re-flipping it.

For one week in August 2026 base was measured AS SAVED instead, argued from an external ffmpeg read of −18.3 LUFS against a −23.0 target on "Plumes+BD2+OCD". That number was real but **confounded**: on that same day, on that same preset, the block's own footswitch row was clamping in every multi-row batch (see the isolation note in `footswitch.rs`), which by itself leaves the recalled sound exactly that hot. With the clamp fixed, re-measurement is unambiguous (HW, 2026-08-20, ffmpeg `ebur128`, the player's own DI, preset 30 / list index 29): base-as-saved and the FS6 row are **the same sound** — both −22.99 LUFS, and FS6's solve converged on the value it started from — while base with the four pedals off sits 4.7 LU away at −27.69, never measured and unreachable by any row the run offered. Measuring base as saved spends one of the run's rows on a duplicate.

Consequence the player owns: a preset that RECALLS with a pedal on will read above the base target on recall unless that switch's own row is leveled too. That is deliberate — no warning, no auto-selection (user directive).

Two consequences of the force list, both unchanged since the pre-2026-08-19 shape: the apply path needs `reload_preset` (forced bypasses persist across HID reconnects, so the edit buffer is reset before the write), and the **verify capture is SKIPPED by design**. Do not "fix" the second by re-isolating for verify: isolation has to be written after the recall and before the engage, which puts those `bypass=true` writes in the very buffer `recall_reassert_save` then saves from — and `recall_base` demonstrably does NOT clear them (that is the sibling-row leak `footswitch.rs` documents). One dropped reload and the run saves _every pedal off_ into the player's preset. The UI falls back to `predicted_lufs`, which is exact for a post-chain linear control, and the external ffmpeg lane is the real check. A safe re-enable exists (reload → re-set `presetLevel` → recall → save, so verify runs on the isolated buffer and the save on a clean one) but it adds a load+write phase to a SAVING path and needs its own HW validation: a deliberate non-goal, not an oversight.

**Where the Doctor diverges — scenes only.** Base leveling, the Doctor's base sound and the `e2e_server` validation yardstick now share ONE derivation (`doctor_force_bypass(.., None)`), so they cannot drift. The remaining deliberate divergence is SCENE sounds: those are measured as-played, riding their saved overlay states, because a scene's own bypass overrides are what define it.

**KNOWN GAP:** the block-handle base lane (`leveller::level_preset_block`, used when the player picks a specific block param as the Base handle) still measures un-isolated — it takes no `force_bypass`. Two definitions of base again, on a lane with thin HW coverage; threading it is a mechanical follow-up, not a redesign.

**Saturated-amp response shape (preset 024 "TR+BD2+BMP", HW-reproduced 2026-08):** a drive pedal (Plumes/BD2/OCD/Rat) feeding a saturated amp ('65 Twin) has a **silent → cliff → plateau** response on its own `level` knob, not the smooth-taper curve the bracketing fix above assumes: silent (no signal) at `level ≤ 0.10`, a **~42 LU cliff** between `0.10 → 0.20`, then a **compressed plateau** (`−20 → −17 LUFS` across `0.3 → 1.0` — the amp's own saturation flattens the rest of the knob's range into a ~3 LU band). Base (all pedals off) stays clean and linear at −29.2 LUFS with the user's calibration capture; with a pedal engaged the gap over base is **+12.35 LU** at calibration drive, narrowing to **+8.72 LU at +6 dB** and **+6.88 LU at +10 dB** hotter playing (~0.55 LU per dB) — the pedal-ON sound is pinned near the amp's compression ceiling while base still tracks input linearly, so the two converge as input gets hotter. The −24/−26 LUFS targets sit ON the cliff, so they ARE reachable — the bug is that the solve never samples it.

**Why "no signal captured" / a false "no authority" clamp happen without the fix:** the `0.25`/`0.75` seed pair (`solve_footswitch`, `leveller.rs`) already lands past the cliff, inside the compressed plateau, so the FIRST measurement is never silent and the seed's own routing probe (NO_SIGNAL → `MUTE_FLOOR_SILENT_LUFS`) never fires. Both plateau points are LOUDER than a −24/−26 target, so the solve must search back DOWN through the cliff toward the genuinely reachable point — and two silence sites downstream mishandle that search:

- the bracket-expansion probe (`fs_bracket_expansion` retrying toward the low extreme, `0.0` — squarely in the silent region below `0.10`) is wrapped in `if let Ok(l_extreme) = require_live(...)`: a silent result is silently DISCARDED, so the correction loop is left extrapolating from the two plateau-only points alone;
- the very next correction-step capture — extrapolated from a ~4–5 LU-apart plateau pair toward a target several LU quieter — lands well below the cliff and reads via a bare `require_live(...)?`, so its silence propagates as a hard `Err` and ABORTS the whole footswitch job (HW trace: seeds 0.25/0.75, first iterate clamped to 0.0, "no signal captured"). This is the DOMINANT shape: the plateau pair's real ~4–5 LU spread is far above `KNOB_TOL_LU`=0.3, so the loop always enters the correction search rather than reading the seed pair itself as flat. When the abort doesn't fire — e.g. a search that stalls with `best_v` pinned at a bound before ever probing the silent zone — `classify_fs_outcome` reports the same reason-less "no authority" clamp (its own test table's "zeroed/maxed, target un-reachable" rows), even though the true cliff position was never sampled.

**The rule: a silent capture at any non-first measurement point is DATA, not a failure.** The FIRST seed keeps its routing-clamp conversion (`NO_SIGNAL_CAPTURED` → the `MUTE_FLOOR_SILENT_LUFS` report + "no signal on USB 1/2"); every LATER silent capture — second seed, bracket-expansion probe, or correction-step — becomes a geometry-only pseudo point at `fs_silent_geometry(min_real)` = `FS_SILENT_GEOMETRY_LUFS` (−50) floored `FS_SILENT_MARGIN_LU` (10) below the quietest real capture of the solve, so the secant has a point to walk the cliff from. Deliberately NOT −120: the literal floor overruns the `FS_CORRECT_MAX` iterate budget (see the constant's doc for the sentinel sensitivity sweep), and the relative floor is what keeps the sentinel BELOW every real capture on whole-curve-quiet chains (a sentinel above a real point inverts the secant's slope). The pseudo point never reaches `improve_best`, and only a REAL capture may satisfy the at-target break — a sentinel near a quiet user target must not fake convergence. (Landed in `leveller.rs::solve_footswitch`; non-regression coverage tracked in `notes/user-journeys.md`'s bug→gate registry.)

**Drive-dependence — why an external meter can disagree with the app's equal target:** because the pedal-ON sound sits on the amp's compression ceiling while base tracks input linearly, the gap between "base at calibration drive" and "pedal-ON at calibration drive" is not a fixed offset — it shrinks the harder the instrument is actually played (`+12.35 → +8.72 → +6.88 LU` at `+0/+6/+10 dB` on preset 24). A one-shot open-loop solve locks in whatever gap the CALIBRATION capture showed; if the player then performs measurably hotter than they calibrated, the two sounds sit closer together in reality than the equal-LUFS solve predicted — which reads as "the app's numbers don't match what I hear/measure on stage." Recalibrating the instrument profile (`calibrate_profile`) at the intensity actually played tightens this: the DI capture becomes the leveling stimulus verbatim (see "Instrument profiles & calibration" above), so the solved values reflect the same drive the gap was measured at, rather than a calibration-drive-vs-stage-drive mismatch.

**Outcome taxonomy (preset & footswitch):** success = target hit; **clamped at X** = any headroom/convergence clamp (the knob has real, measured effect but can't reach target) — `clamped` with NO reason; **not on USB 1/2** = the capture had no signal there (user-configurable output routing) — `clamp_reason` is set ONLY in this case (`"no signal on USB 1/2"`, the silent-first-capture early return) and maps to the UI's `offbranch` outcome. The scene path additionally stamps `clamp_reason` for its no-authority off-branch case (big amp `outputLevel` change, no capture response) — signal present, same `offbranch` label, unchanged by this taxonomy.

**Freshness guard against a stale same-slot load (2026-08-02, the preset-24 incident above).** The TMP commits `saveCurrentPreset` LAZILY — see `notes/gotchas.md`'s lazy-commit entry for the full timing evidence (T+45–100 s observed, bidirectional proof, the two-store model, the field-9 self-compare trap) — so a same-slot `loadPreset` fired inside that window can materialize the PRE-save preset into every downstream measurement, and a load→…→save session inside the window silently REVERTS the earlier save. Every LEVELING load site sitting behind a same-slot save is guarded by a per-slot SAVE REGISTRY + `ensure_fresh_load` barrier (non-leveling save→load flows — import, copy, doctor, in-place replace — are not): each leveling save registers `{at, witness}`, where the witness is the ONE field that save actually changed (`presetLevel` for a base save; the first baked param or assign `valueA` for an FS batch save; one written scene `outputLevel` for a scene deferred save). A load at a registered slot inside the commit window re-loads and re-harvests on the SAME session (heartbeat-interleaved, never a reconnect — HID lockout) until the harvested witness matches the registry value, or the commit window elapses (a time-gated fallback proceeds with an INFO log rather than a hard error in the normal path). Guarded sites: the footswitch batch's own preset load, the pre-write barrier ahead of `write_fs_values_on_session` (on its own session — never inside the live-edit session, which would drop a chunked write), `measure_c`'s load, `apply_levels`'s `reload_preset=true` load (re-run / "Re-run off target" / setlist), the scene lane's `run_batched` prepass load, and the shared block-discovery seam (`probe_api::slot_write::load_then_discover_blocks` — the Level wizard's Base handle picker, `probe --blocks`/`probe_level_block`, the spectrum `bypass_all` walk, and scene leveling's amp-candidate filter all load through it, so the barrier there also covers its non-leveling callers). **`save_deferred_scene_writes` gets NO barrier and must NEVER be preceded by a load of any kind** — it performs no load itself and persists the run's UNSAVED deferred working-copy writes; a load ahead of it would WIPE them, not protect them. While the barrier waits, the wizard's active row shows "waiting for the device to commit the previous save…" (the footswitch progress channel's `message` field) instead of sitting dead for up to ~2 minutes.

**The progress channel's `message` is the active row's CAPTION, and it reads two ways (2026-08-20).** `RunBody`'s `rowStatus` composes it with the live number when a capture is streaming and shows it verbatim when none is, so the same field is a VERB in one phase and a NOTE in the other: the ceiling prepass sends `leveller::PREPASS_ACTIVE_MSG` ("measuring") from inside its measurement loop and the row reads `measuring · −18.9`, while the freshness barrier above sends its sentence with nothing capturing and the row shows it whole. A solve row sends no message and falls back to the default verb, `leveling · −23.1` — that absence is what flips the verb back, so phase 2's `active` must stay message-less. Both lanes emit a prepass tick per row (the FS lane inside PHASE 1, after every arm that skips a capture has returned, so a `BakeShared` sibling and a refused handle stay dark; the scene lane through `scene_progress_item`'s `active_message`). Before this the FS prepass streamed nothing at all and the wizard held row 0 lit for the whole ~10 s-per-row sweep while the unit engaged each switch in turn — the run read as leveling the wrong footswitch (see the registry row).

**FS acceptance tightened to `FS_TOL_LU = 0.1`.** The footswitch lane's `solve_footswitch`/`classify_fs_outcome`/`switch_at_target` acceptance band is now a true ±0.1 LU vs target (FS lane only, iterate budget bumped to compensate) — the scene lane keeps the shared `KNOB_TOL_LU = 0.3` unchanged, and the online HW strict spec (`level.online.spec.ts`) keeps its wider ±1.0 LU footswitch band, which is HW capture noise headroom, not a restatement of the FS lane's own acceptance number (see `notes/user-journeys.md`'s bug→gate registry).

**Post-save persist-verify is an HONEST, narrow contract.** `verify_persisted_writes`/`persist_mismatches` (the post-FS-batch-save field-8 re-read, stamping `persist_mismatch` on each result) detects ONLY "my own writes didn't persist" — a dropped chunked edit, an idle-gap lapse, or a rejection. It does NOT detect staleness or the revert shape above: field-8 is read-your-writes, so it faithfully echoes back whatever is ACTUALLY saved — including a stale-saved value left by the revert shape. Staleness/revert coverage is the freshness barrier's job, not this verify's. The FS-lane verify (`verify_fs_persisted_writes`) additionally checks the run's own earlier base-save `presetLevel` against the same read — the command snapshots that expectation from the registry BEFORE the batch's save overwrites the slot's entry with its own param witness — so a revert of the run's own base save stamps every switch in the batch as mismatched too.

## Parallel-amp rebalance — equalize lanes, then joint-level

Opt-in ("Even out parallel amps"), only on a path MERGE (two amps in parallel that re-merge). For each such scene (`level_scenes_rebalance`): mute one lane (`outputLevel = 0`) and measure the other to get each lane's solo ceiling `C`, set the two `outputLevel`s for **equal solo loudness** (quieter lane pinned at max, louder attenuated), then scale BOTH lanes' `outputLevel` by one joint factor `k` to hit the combined target. If a muted lane bleeds into the solo (small solo-above-floor margin, `probe --mute-floor`), the scene is flagged **verify by ear** — the combined target is still hit, only the lane balance is approximate. Non-mergeable scenes skip the isolation step and use the plain joint-k.

## Verify-by-ear causes & the dynamic-spread flag

The Summary marks a row **verify by ear** for any of THREE causes (`RunItem.verifyByEar`, `"envelope" | "dynamic" | "rebalance"` in `leveling.ts`; the closing footnote spells out only the causes present):

- **dynamic** — `dynamic_spread_lu` (short-term-max − integrated, gain-invariant, reported by every full-capture measure) ≥ `DYNAMIC_SPREAD_LU` = 6 LU: loud/quiet swings make the integrated number an average, so equal-LUFS presets can still feel uneven (the relative-gate bias; the solver still uses integrated only).
- **envelope** — the preset contains an envelope-follower effect (`effect_type: "Envelope Filter"`; expression-driven wahs excluded): its response tracks the stimulus's attack/decay envelope, so the synthetic clip can park it in a different regime than real playing — flagged regardless of how clean the numbers look (`ENVELOPE_BIDS` in `useLevelingFlow.ts`).
- **rebalance** — parallel amps balanced by approximate isolation (mute-lane bleed; see the rebalance section).

Separate from by-ear: a Base row whose PREDICTED true peak (`LevelResult.true_peak_dbtp`, extrapolated from the reference capture — an estimate, never a re-measurement) exceeds the clip threshold earns a "may clip" caveat in the Summary.

## Stop / cancellation

Stop in the Run stage fires all three cancel lanes (`cancel_{preset,scene,footswitch}_leveling` — per-lane `AtomicBool`s read via a `cancelled` closure threaded into the leveller) **and** a process-global abort flag (`device_gate::OP_ABORT`, justified by `DEVICE_OP_LOCK` already serializing device work to one op at a time). A tripped flag returns the `leveller::CANCELLED` sentinel, which the runner treats as a **skip**. The in-flight capture no longer sits out its full ~6–8 s: `sleep_abortable`/`sleep_or_cancel` poll the abort flag on every long wait on the leveling/Doctor path (the re-amp capture window itself, the settles bracketing it, and both floor-retry gaps), each bailing out within one poll tick (`ABORT_POLL_MS` = 50 ms, `device_gate.rs`) instead of sitting out the wait — except past the re-amp engage, which has no early return (a dropped OFF strands the unit input-muted), and the post-cancel preset restore / deferred scene saves, which always run to completion. That bounds only the in-process poll bail-out, not the end-to-end Stop-to-UI latency (UI round-trip, USB/HID, cleanup) — no hardware measurement of the full path exists yet (M-L1, `e2e-test-plan.md`). Contract: levels already written before the stop STAY saved — but the save itself follows each item kind's persistence model, not a uniform "saves as it completes": **preset** (Base, via `presetLevel`) saves per item as it completes; **scene and footswitch** writes are deferred in the working copy and persisted by the single batch-end save (`save_deferred_scene_writes` / `write_footswitch_values`), which the cancel lane also fires so already-reported scenes/switches persist (see "ONE save per preset" above). There is no automatic run-level rollback and no in-app revert of any kind (design-1a removed the Summary's per-row **Restore original** — the backup-acknowledgment checkbox in Set up is the sole revert path: restore from the Pro Control backup). The cancelled item itself persists nothing — `restore_after_unsaved_error` reloads the stored preset to discard the dirty measurement edits (a cancel restores even on the `save=true` path, since it bails before `apply_level`). The UI flips a `stopping` flag for immediate feedback and lands on the Summary via the manual-stop path (Continue button, no auto-advance).

## Common-target leveling

"Level all to a common target" measures every preset's ceiling `C` and levels them all to `min(C) − headroom`, so switching presets/instruments on stage causes no loudness jump.

## Instrument profiles & calibration

A profile links a real instrument to a shipped pickup topology whose stimulus WAV is re-amped when leveling a preset the profile is assigned to. Tier-2 calibration captures the dry instrument (K-weighted LUFS) — and **stores the capture as the profile's leveling stimulus** (`<app_config>/captures/<profile_id>.wav`), re-amped **verbatim** (no scaling; `calibration_lufs` is ignored when the capture resolves). Why: an HW `probe --stim-ab` A/B showed the synthetic stimulus — even LUFS-matched — mis-levels presets by −5.4…+2.2 LU preset-dependently (crest/spectrum/harmonic structure drive nonlinear presets, not integrated LUFS). Fallback for legacy/capture-less calibrations: the topology WAV scaled to the stored loudness. Consistency: `store_capture` unlinks-first and writes temp+rename before the scalar is saved; clipped captures store nothing; `save_profiles` unlinks captures on profile delete or topology change; an activity-ratio gate (500 ms windows, ≥50% within 30 dB of the loudest) rejects mostly-silent takes. The Doctor diagnoses a calibrated profile's DI capture against the same per-family threshold table a synthetic stimulus uses (`StimulusKind::Capture` no longer selects a distinct table — only the fizzy flatness gate still branches on it).

The dry instrument is tapped on **USB-Out 3** (`audio::DRY_INSTRUMENT_IN_CH`). `resolve_stimulus` precedence: e2e env → explicit → profile capture → topology WAV → env → default.

**Why K-weighted, not flat RMS or peak.** Peak is pick-transient-dominated and barely tracks output; flat RMS under-counts bright pickups (a bright guitar that drives the preamp hard reads low in broadband RMS). K-weighting matches perceived drive and unifies the metric with the leveler's output target — loudness in, loudness out.

**Clipping caveat — this one is a user-facing instruction.** The dry-instrument tap has no limiter and **clips at 0 dBFS** for hot guitars or hard playing. **Play EXACTLY as you really play — NEVER roll the guitar volume back:** doing so under-drives the amp versus reality AND darkens the tone (volume-pot HF rolloff), corrupting the very brightness K-weighting exists to capture. Clipping is a capture-path / gain-staging fix, never a playing instruction. `calibrate_profile` clip-gates with a **flat-top run-length detector** (≥4 consecutive full-scale samples) — a lone pick transient at 0 dBFS is NOT clipping, since the DI tap is a bit-exact USB bus with no analog gain to lose. The too-quiet case is guarded separately.

**HW-validated, both gates.** The dry instrument is capturable (`probe --capture-input`), and the re-amp inject is **not AGC'd** — its amplitude drives the chain, and the apparent compression is the amp's own nonlinearity (`probe --agc-test <clean-slot>` linearizes at low drive; a clean Twin gave ~1.65 LU output per 6 dB input). Re-validate with those two `probe` subcommands.

## Playback-level (Fletcher–Munson) compensation

Equal-LUFS is equal-loudness only near one SPL. The store carries a playback level (Quiet / Rehearsal / Stage); below stage volume, bass-instrument targets get a small positive offset so low-frequency energy is not under-credited. Stage is the default (zero offset).

## Capture window

The capture window (≈6 s stimulus + 0.8 s tail) is load-bearing: TMP presets are not stationary under gated-integrated LUFS (delay/reverb buildup + tail), so trimming the window shifts the measured value. The leveling default uses the full capture.

## Metering convention (PR2 re-baseline)

**Companion now measures the processed USB pair as standard 2-channel BS.1770** (`lufs::measure_stereo`, energy sum over capture channels 0/1 — dry channel 2+ excluded), matching an external BS.1770 stereo meter to within 0.009 LU (ground-truthed against ffmpeg's independent `ebur128` at full metadata precision, 2026-08-04). This SUPERSEDES the mono-era "loudest single channel" convention this section used to describe: on the TMP's mirrored dual-mono USB output the two conventions differ by a fixed **+3.0103 dB** (`10·log10(2)`, algebraically exact for identical channels), so every shipped default target, the `TargetRow` slider domain, and every previously-saved user target shifted +3 LU together (`profiles::Store::meter_convention`, one-shot migration) to keep producing the SAME audible loudness. Relative quantities — spreads, deltas, the `presetLevel` solve itself — are invariant to this convention change; only ABSOLUTE reported numbers moved. The INPUT/stimulus side (self-measurement, dry-DI calibration, the floor-guard spread) still uses `lufs::measure_mono` and did not change. **Every other absolute LUFS/dB figure elsewhere in this document (the Klon `-9.610`/`-6.96` HW measurements, the preset-024 saturated-amp response's `-20 → -17` plateau and `-29.2`/`+12.35`/`+8.72`/`+6.88` figures, the `-17.4` channel-forensics reading, etc.) is a HISTORICAL hardware measurement taken under the mono-era single-channel convention and is preserved as recorded — not restated to the new convention.**

**Hardware-validated 2026-08-04 (fw 1.8.45).** Same-day A/B on preset list-index 0
("Guitar", 10 blocks) at the base scene, `guitar-humbucker` stimulus: a `d7a2a2c`-built
probe (mono-era convention) and a branch-built probe (2-ch BS.1770), alternated
baseline/branch/baseline/branch on the same preset. Baseline read **−22.588** on both
runs, branch **−19.578** on both — a delta of **+3.010** against the algebraic
`10·log10(2) = 3.0103`, with **0.000** within-arm spread (the USB path is digital and
deterministic). The processed pair was confirmed mirrored: `ch0 ≡ ch1` to three decimals
on every capture, which is the premise the whole re-baseline rests on.

Doctor was A/B'd in the same session on list indices 0 and 404: **band dB, tilt, air
flatness and fired verdicts are unchanged** between the two builds (|Δ| ≤ 0.002 dB) —
D4's requirement that band analysis stay on the averaged mixdown. Note the dev probe
arm (`probe --doctor`) reports the legacy mono-on-mixdown loudness by design
(`SoundProfile::from_capture_with_psd_loudness` with `stereo_loudness: None`), so its
`integratedLufs` deliberately does NOT shift; the PRODUCTION Doctor path
(`commands/doctor.rs` → `leveller::doctor_capture_with_loudness`) passes the stereo
measure as the override and does. Don't read the probe arm's unshifted number as a
regression.

### Parity harness (dev-only, optional)

`scripts/meter-parity.sh` ground-truths the metering convention above against an
independent BS.1770 implementation — ffmpeg's `ebur128` filter — instead of taking
`lufs.rs`'s own word for it. It is a **developer tool, not a gate**: not wired into
`scripts/gates.sh`, never a CI dependency, and ffmpeg is never linked into or invoked
by the shipped app.

```bash
bash scripts/meter-parity.sh                 # generate deterministic synthetic
                                              # fixtures via ffmpeg lavfi and compare
bash scripts/meter-parity.sh <dir-of-wavs>   # compare an existing directory instead —
                                              # e.g. real captures from `probe --dump-wav`
```

Both arms run the SAME WAV through two independent meters — `probe --measure-wav`
(`lufs.rs`'s production output-side path: `measure_stereo` for a ≥2-ch file, `measure_mono`
for 1-ch) and ffmpeg's `-af ebur128` — and assert `|Δ integrated| ≤ 0.02 LU` per file. The
ffmpeg side is read at FULL precision from the filter's metadata
(`ebur128=metadata=1` + `ametadata=print:key=lavfi.r128.I`, last value emitted), NOT from
the end-of-run summary, which prints one decimal and would cap the comparison at ~0.1 LU
while hiding the true agreement. Measured 2026-08-04: **≤ 0.009 LU** across the six
synthetic fixtures and **0.004-0.006 LU** on real device captures. Two conformant BS.1770
implementations still differ slightly in how the final partial gating block is handled, so
bit-exact equality is not expected and 0.02 is a deliberately tight but achievable bar. If `ffmpeg` isn't on `PATH` the script prints a skip notice and exits 0 —
absence is not a failure.

**What a FAIL means:** `lufs.rs` disagrees with the independent BS.1770 read by more than
0.02 LU on at least one file. Since ffmpeg's `ebur128` is a mature, widely-used
implementation, treat that as a `lufs.rs` regression (channel/hop handling, most likely
the 2-ch true-peak-per-channel or the frame-vs-sample hop math this module's header
documents) first — unless the file came from a real device capture, where device-side
noise or a DC offset is also a plausible explanation.

`probe --dump-wav <dir>` is the add-on that feeds the second arm: passed alongside
`probe --measure-current`/`--measure-scene`, it also writes the captured processed pair
(never the dry channel) to a 32-bit-float WAV in `<dir>`, named from slot/scene, with no
effect on the command's behavior when the flag is absent. The filename is NOT made
unique beyond slot/scene — re-running the same slot/scene overwrites the earlier dump,
so rename a take before re-measuring if it needs to survive a follow-up run.

## Re-amp protocol facts

- Re-amp toggle = `SettingsMessage → reampModeActive`.
- Re-amp latches the preset/scene state at engage: set the level (or recall the scene) BEFORE engaging. `changeParameter` is audible mid-engage; `loadScene` mid-engage is not — so per-scene leveling needs one engage per scene.
- Re-amp engages reliably only once per connection — fresh-connect per engage; never disengage→re-engage on a held connection.
- A leveling run ends with a guaranteed re-amp OFF on a fresh connection (recover a stranded input-muted unit with `probe --reamp-off`).
- A silent/failed inject reads as the device's stationary OUTPUT FLOOR, which `measure_c` accepts as a valid `C`. Tell: `dynamic_spread_lu ≈ 0.01` + a preset-INDEPENDENT `C` (identical across presets; the floor is post-DSP so `presetLevel` scales it and the C-model holds). A full solve+verify can land 0.00 LU error on the floor alone — self-consistency is not inject-health proof. Seen only under a rapid 20-engage `probe --stim-ab` sweep, not isolated runs. The production path now guards every measurement (`leveller::measure_floor_guarded`/`require_live`, `FLOOR_TRIP_LU` = 0.08, stimulus-aware disarm + `measure_c`'s level-shift confirm); `--stim-ab` stays the diagnostic sweep.
- **"no signal captured" at DEEP silence (peak ≈ −93 dBFS) = a silently DROPPED engage in every shape reproduced so far (the two-handshake / idle-gap connection shapes below, HW-root-caused 2026-07-18) — run the `--channels` discriminator before ruling anything else out (an unrelated mute/routing failure would read the same).** Distinct from the stationary-floor class above: deep digital silence is the UN-ENGAGED chain (no instrument input), meaning the `set_reamp_mode(true)` never landed — the same silent command-drop family as the ~400–450 ms idle-gap scene-write cliff and the idle-session OFF drop. Trigger shape: `probe --measure-scene <slot>` runs TWO back-to-back FULL handshakes (load-prelude connection + measure connection, ~800 ms apart) and engages shortly after the second flood; fired right after a heavy run (e.g. `--level-scenes`) the engage is dropped device-side, and every retry with the same shape re-arms the churn — a streak of 6 identical failures reproduced across a POWER-CYCLE (the first post-boot attempt still failed), so a power-cycle is irrelevant, never the cure. Proof the device stays healthy mid-"wedge": `probe --channels <slot>` (lean connects, extra settled writes) read −17.4 LUFS chain audio between two failing `--measure-scene` runs, and `--measure-current` (ONE full handshake, no load prelude) succeeded in the same state. Production is unaffected: every production measure path (`capture_full_at`, `measure_scene_asis`) uses `connect_lean` single-handshake shapes and both full `--level-scenes` runs completed 4/4 while the forensic probe was failing. Diagnosis recipe: on "no signal captured", run `--channels <slot>` — if it reads finite loudness the device is fine and the failing tool's connection shape is to blame; recovery is gentle traffic or ~1–2 min quiet, then a lean/single-handshake shape.
